## 5. env-empty-shadow — 빈 env 변수가 .env의 진짜 값을 가림
- 분류: project
- 셸에 `GOOGLE_API_KEY=`(빈 값 export)가 있어, dotenv의 "이미 존재하는 변수는 안 덮어씀" 기본 동작 때문에 `.env`의 진짜 Google 키가 무시됨 → `googleModels()`가 즉시 `[]` 반환 → 모델 선택기에 Google 모델이 하나도 안 뜸. (OPENAI/ANTHROPIC 키는 셸에 실제 값이 있어 정상.)

- How: `src/config.ts`에서 dotenv 로드 후 `parsed`를 순회하며 `!process.env[key]`(미설정/빈 문자열)인 변수만 .env 값으로 채운다. 새 API 키가 목록/기능에 안 나타나면 먼저 `ps eww <서버PID>`로 실행 프로세스의 실제 env가 비었는지 의심하라.

## 6. stray-server-port — 옛 프로세스가 8787 포트를 점유
- 분류: project
- 람파스 서버가 "코드를 고쳤는데 동작이 안 바뀐다"면 `lsof`/`ps`로 `dist/index.js serve`가 **두 개** 떠 있는지 먼저 확인. 2026-07-07~09 수동 실행된 옛 프로세스가 8787을 점유해, launchd 데몬(io.lampas.harness.daemon, KeepAlive)이 뜰 때마다 `EADDRINUSE`로 웹 리스너만 죽고 큐 워처는 사는 반쪽 상태가 반복됨. 증상: `logs/daemon.out.log`의 EADDRINUSE 줄.
- Why: 재시작·재빌드를 해도 포트를 쥔 옛 프로세스가 계속 서비스를 담당하므로 수정이 반영 안 됨.
- How: ① `ps aux | grep 'index.js serve'`로 중복 확인 ② `logs/daemon.out.log`에서 EADDRINUSE 확인 ③ 옛 프로세스 kill 후 `launchctl kickstart -k gui/$(id -u)/io.lampas.harness.daemon`. 단, 이 대화 자체가 그 서버로 실행되므로 즉시 kill하면 진행 중 턴이 끊긴다 → `nohup bash -c 'sleep 25; …' &`로 지연 실행.

## 7. restart-kills-own-turn — 턴 안에서 서버(8787)를 죽이면 내 턴이 끊긴다
- 분류: project
- 이 Claude 세션이 람파스 웹 채팅으로 실행 중일 때(시스템 프롬프트에 imagegen/scheduler 지시가 주입돼 있으면 그 경우), `dist/index.js serve`를 kill/재시작하면 SDK 자식(나)은 고아로 살지만 부모가 죽어: (1) 권한 프롬프트가 전부 "Stream closed"로 실패, (2) SSE 응답·appendTranscript가 죽은 부모 몫이라 사용자 화면·히스토리에 내 출력이 전달 안 될 수 있음.
- Why: 서버가 Agent SDK 턴을 자기 프로세스에서 spawn하므로, 서버 재시작 = 진행 중 내 턴의 통제 채널 절단.
- How: 턴 안에서 서버 재시작이 필요하면 코드 수정·빌드까지만 하고 재시작은 사용자에게 맡기거나, nohup 지연 스크립트로 분리 실행(detach-long-jobs)하고 최종 답변을 먼저 마친 뒤 재시작되게 하라. 재시작 직후엔 권한 필요 작업(curl, 새 파일 Write 등)이 모두 실패.

## 8. pkill-hits-prod-daemon — pkill -f가 운영 데몬까지 죽임
- 분류: project
- 테스트 인스턴스(`PORT=8899 npx tsx src/index.ts serve`)를 `pkill -f "tsx src/index.ts serve"`로 종료하면 운영 launchd 데몬(io.lampas.harness.daemon)도 명령줄이 같아 함께 죽는다.
- Why: 운영과 테스트가 같은 소스·같은 실행 명령을 써서 -f 패턴으로 구분 불가. launchd KeepAlive가 운영을 즉시 재살리지만 진행 중 턴은 끊긴다.
- How: 테스트 인스턴스는 `/usr/sbin/lsof -ti :8899`로 PID를 특정해 그 PID만 kill(`lsof`는 PATH에 없어 절대경로 필요). 셸 상태가 Bash 호출 간 유지 안 되므로 `kill %1` 같은 잡 제어는 무효 — 이전 인스턴스가 포트를 계속 쥐면 stray-server-port와 같은 EADDRINUSE 증상.

## 9. detach-long-jobs — 장시간 작업은 세션과 분리
- 분류: project
- 이 환경에서 Bash `run_in_background` 작업은 대화 세션이 넘어갈 때(CLI 프로세스 teardown) 함께 죽는다. 2026-07-09 rapid-mlx 모델 다운로드(37GB)가 두 번 연속 8GB 부근에서 끊긴 원인.

- How: 턴을 넘겨야 하는 장시간 작업은 `nohup <cmd> > 로그파일 2>&1 & disown`으로 완전 분리하고, 진행은 로그 tail로 확인. 완료 감지는 `ps aux | grep` 프로세스 생존 폴링.

## 10. rapidmlx-launchd-managed — rapid-mlx는 launchd(KeepAlive) 관리
- 분류: project
- 8000 포트의 rapid-mlx(vllm-mlx) 로컬 LLM 서버는 LaunchAgent `io.lampas.rapidmlx`가 KeepAlive로 관리. 프로세스를 kill하면 launchd가 즉시 옛 plist 설정으로 되살리므로, 실행 인자를 바꾸려면 plist를 고쳐 재배포해야 한다.
- Why: 2026-07-11 `--host 0.0.0.0` 바인딩으로 바꾸려 프로세스를 죽이고 수동 재실행했더니 launchd가 옛 설정 인스턴스를 또 띄워 둘이 포트 경합. stray-server-port와 유사한 함정.
- How: plist 원본은 레포 `launchd/io.lampas.rapidmlx.plist`. 수정 후 `~/Library/LaunchAgents/`로 복사 → `launchctl bootout gui/$(id -u)/io.lampas.rapidmlx` → `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/io.lampas.rapidmlx.plist`. bootout 직후 bootstrap하면 오류 5가 나므로 몇 초 대기 후 재시도. 로그: `logs/rapidmlx.{out,err}.log`. 35B 모델 로드에 5분 가까이 걸리니 포트 오픈은 여유 있게 폴링.

## 13. naver-session-srt-expiry — 글쓰기용 SRT 보안쿠키 ~24h 만료
- 분류: project
- naver-blog-mcp 발행이 "글쓰기 페이지 로딩 실패 → nidlogin.login 리다이렉트"로 실패하면 세션 만료가 원인. 저장 세션(`playwright-state/auth.json`)의 `NID_AUT`/`NID_SES`(둘러보기용)는 오래 살지만, 글쓰기·에디터에 필요한 **`SRT5`/`SRT30` 보안 재인증 쿠키는 약 24시간이면 만료**된다. 그래서 홈은 로그인 상태로 열려도 `/postwrite`만 로그인으로 튕긴다.
- Why: 헤드리스 자동 재로그인은 네이버 **인라인 이미지 캡차**(영수증 사진 보고 숫자 답하기; iframe 아님이라 login.py가 감지도 못 함)에 막혀 불가능. 코드로는 못 고치는, 사람이 풀어야 하는 봇 차단.
- How: 세션 갱신은 headed 브라우저로 캡차를 직접 푸는 방법뿐. `cd mcp-servers/naver-blog-mcp && uv run python tools/manual_login.py` → 뜬 창에서 캡차 풀고 로그인 → auth.json 자동 재저장 → 하네스(헤드리스) 발행이 ~24h 다시 동작.
