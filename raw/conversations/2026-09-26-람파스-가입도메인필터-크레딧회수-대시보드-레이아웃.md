## assistant

세 가지 기능을 모두 구현하고 로컬에서 끝까지 검증한 뒤 커밋했습니다(`a23f94c1`). 운영 배포는 하지 않았습니다. 이유는 아래에 있습니다.

**1. 가입 도메인 필터** (lampas-api `auth`)
- 관리자가 등록한 도메인(하위 도메인 포함, 예: `gehuy.biz.id`)은 그 도메인 이메일 계정이 허용 상한(기본 10, 0이면 전면 차단)에 도달하면 신규 가입이 403으로 거부됩니다.
- 구글·이메일·토스·로컬 가입이 모두 지나는 한 지점에 걸어 두었고, 차단 횟수·마지막 차단 시각을 규칙에 누적합니다.
- 규칙에 없는 도메인은 계정 수를 세지 않으므로 일반 가입 성능에 영향이 없습니다.

**2. 크레딧 회수** (유저 정보 유지)
- 도메인 단위 일괄 회수와 유저 단건 회수 두 가지입니다. 방식은 `보너스만`(가입 보너스 중 미회수분, 잔액 한도)과 `전액`(잔액 0) 중 선택합니다.
- 유저 행·로그인은 그대로 두고 잔액만 차감하며, 원장에 관리자 차감으로 기록됩니다. 재실행하면 회수할 잔액이 없는 계정은 건너뛰어 중복 차감이 없습니다.

**3. 대시보드 이상 가입 감지** (lampas-web-admin)
- 대시보드에 "이상 가입 감지" 섹션을 추가했습니다. 이메일 도메인별 24시간·7일·30일·누적 가입 수와 잔액 합을 보여 주고, gmail 같은 흔한 공급자를 제외한 도메인이 24시간 3개·7일 5개·누적 10개 이상이면 "의심"으로 표시합니다.
- 각 행의 "필터에 추가" 버튼이 도메인을 미리 채운 상태로 새 `/signup-domains` 페이지로 이동합니다. 그 페이지에서 등록·상한 수정·소속 유저 조회·일괄/개별 회수·삭제를 처리하고, 사용자 상세 화면에도 회수 버튼을 넣었습니다.

**검증**
- 유닛 테스트: API jest 21건 추가(전체 admin 46·auth 11 통과), web-admin vitest 5건 추가. 두 앱 빌드 통과.
- 로컬 API 데몬 재기동 후 실제 흐름 확인: 상한 3으로 가입 3개 허용 → 4번째(하위 도메인) 403과 차단 카운트 → 보너스 회수로 3,000 크레딧 회수 → 재실행 시 전부 건너뜀 → 대시보드에 의심·필터 표시 → 원장 기록 확인. 스모크 데이터는 정리했습니다.

**운영 관련 주의**
- 작업 중 다른 세션의 spot 커밋(adb982af)에 제가 추가한 `schema.prisma` 모델이 섞여 들어가 이미 운영 배포(0.1.149)됐습니다. 배포된 코드는 그 모델을 쿼리하지 않아 무해함을 원격에서 확인했습니다.
- 다음 API 배포가 안전하도록 운영 DB에 `signup_domain_rules` 테이블 DDL을 적용해 두었습니다(빈 테이블 생성, 멱등).
