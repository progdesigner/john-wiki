이건 `.env`, SSH 키, DB 설정, PHP 정보 페이지, 백업 파일 등을 무작위로 찾는 **자동 스캐너/봇의 일반적인 정찰 요청**입니다.

현재 전부 `404`라면 **해당 파일이 노출된 정황은 없고 정상적으로 막힌 상태**입니다. 다만 요청량을 줄이고, 혹시 실수로 배포된 민감 파일이 노출되는 일을 방지하려면 Nginx + AWS 앞단을 함께 설정하는 게 좋습니다.

중요한 점은 `172.31.10.37`이 AWS VPC 사설 IP 대역이라는 것입니다. 대개 실제 공격자 IP가 아니라 **ALB / 리버스 프록시 / 컨테이너 네트워크의 IP**입니다. 이 IP를 Nginx에서 차단하면 정상 사용자까지 전부 막힐 수 있으니, IP 자체를 막지는 마세요.

## 1. Nginx에서 민감 경로 즉시 차단

사이트의 `server { ... }` 블록 안에 다음을 추가하세요.

```nginx
# .env, .git, .ssh 등 점(.)으로 시작하는 숨김 파일 차단
# 단, Let's Encrypt 인증용 .well-known 경로는 허용
location ~ /\.(?!well-known(?:/|$)) {
    access_log off;
    log_not_found off;
    return 404;
}

# 설정·백업·비밀키 파일 확장자 차단
location ~* \.(?:env|ini|log|sql|sqlite|bak|backup|old|orig|save|swp|tmp|dist|pem|key|crt|yml|yaml)$ {
    access_log off;
    log_not_found off;
    return 404;
}

# 소스 저장소·CI 설정 파일 차단
location ~* ^/(?:\.git|\.svn|\.hg|\.github|\.gitlab|node_modules)(?:/|$) {
    access_log off;
    log_not_found off;
    return 404;
}

# 흔히 스캔되는 PHP 진단·설정 노출 경로 차단
location ~* (?:^|/)(?:phpinfo|phpversion|iinfo|info|server)\.php$ {
    access_log off;
    log_not_found off;
    return 404;
}
```

`404` 대신 Nginx 연결을 즉시 끊는 `444`를 쓸 수도 있습니다.

```nginx
return 444;
```

다만 운영 중 디버깅, 모니터링, WAF 분석을 위해서는 처음에는 `404`를 권장합니다. `access_log off`를 적용했기 때문에 이런 잡음은 access log에도 쌓이지 않습니다.

설정 문법 검증 후 반영합니다.

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Amazon Linux 등의 환경에서 systemd가 아니라 서비스 명령을 쓰는 경우:

```bash
sudo service nginx reload
```

## 2. Nginx 요청 속도 제한도 추가

스캐너가 수백~수천 URL을 빠르게 훑는 경우에 대비해 rate limit을 걸어두는 것이 좋습니다.

`/etc/nginx/nginx.conf`의 `http {}` 블록 안에 추가:

```nginx
limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=perip_conn:10m;
```

그리고 사이트 `server {}` 블록에 추가:

```nginx
# 한 IP당 초당 10회, 순간 버스트 30회까지만 허용
limit_req zone=perip burst=30 nodelay;

# 동시 연결 수 제한
limit_conn perip_conn 30;
```

단, 현재 access log의 IP가 ALB 같은 프록시 IP라면 `$binary_remote_addr`가 실제 방문자 IP가 아닐 수 있습니다. 그 경우 아래의 **실제 클라이언트 IP 복원 설정**을 먼저 해야 합니다.

---

## 3. ALB 뒤라면 실제 사용자 IP를 Nginx에 복원

`172.31.x.x`가 찍힌다는 것은 AWS ALB가 Nginx 앞으로 요청을 전달하는 구조일 가능성이 높습니다.

ALB만 서버에 접속하도록 Security Group을 구성한 뒤, Nginx에는 ALB가 전달한 `X-Forwarded-For`를 신뢰하도록 설정합니다.

```nginx
# 실제로는 ALB의 서브넷 CIDR 또는 ALB 보안 그룹 기반으로 서버 접근을 제한해야 합니다.
# 아래 CIDR은 예시입니다. 본인의 VPC/ALB 대역으로 정확하게 바꾸세요.
set_real_ip_from 172.31.0.0/16;

real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

이후 Nginx access log의 `$remote_addr`가 실사용자 IP로 바뀌므로 rate limit, fail2ban, IP 차단이 제대로 동작합니다.

> 주의: `set_real_ip_from 0.0.0.0/0`처럼 모든 외부 IP의 `X-Forwarded-For`를 신뢰하면 안 됩니다. 공격자가 헤더를 위조할 수 있습니다. **ALB 또는 신뢰하는 프록시 대역만** 지정해야 합니다.

가장 안전한 네트워크 구성은 다음입니다.

```text
인터넷 → CloudFront 또는 ALB + AWS WAF → EC2/Nginx
```

그리고 EC2의 Security Group 인바운드 80/443은:

```text
허용 대상: ALB의 Security Group
허용 포트: 80 또는 443
```

만 허용합니다. EC2의 80/443을 `0.0.0.0/0`에 공개하지 않는 것이 핵심입니다.

## 4. AWS WAF에서 앞단 차단 권장

ALB 또는 CloudFront에 **AWS WAF Web ACL**을 연결하세요. Nginx까지 요청이 도달하기 전에 차단할 수 있습니다.

우선 활성화할 만한 AWS Managed Rule은 다음입니다.

- `AWSManagedRulesCommonRuleSet`
- `AWSManagedRulesKnownBadInputsRuleSet`
- `AWSManagedRulesAmazonIpReputationList`
- `AWSManagedRulesSQLiRuleSet`
- 가능하면 `AWSManagedRulesBotControlRuleSet`  
  → 유료이지만 자동 스캐너/봇 제어에 효과적

추가로 **Rate-based rule**을 만드세요.

예시:

```text
집계 기준: IP 주소
임계치: 5분당 1,000 요청
초과 시: Block
```

일반 서비스라면 5분당 300~1,000 정도부터 시작하고, 실제 트래픽을 보면서 조정하면 됩니다. API나 이미지 서비스처럼 정상 트래픽이 높은 경로는 별도 예외를 두세요.

WAF에서 URI 조건으로 아래 패턴 요청을 차단하는 커스텀 룰도 추가할 수 있습니다.

```text
/.env
/.git
/.ssh
/phpinfo
/phpversion
/aws-secret
/config/
/backup/
/development/
```

다만 개별 문자열을 끝없이 추가하기보다, 위의 **AWS Managed Rules + rate limit + Nginx 민감 파일 차단** 조합이 유지보수에 더 좋습니다.

```

# VPC 내 인스턴스 목록 확인 (AWS CLI)
aws ec2 describe-instances \
  --filters "Name=instance-state-name,Values=running" \
  --query 'Reservations[*].Instances[*].[InstanceId,PrivateIpAddress,LaunchTime]' \
  --output table
```

혹은 AWS CloudTrail에서 `172.31.10.37`이 어떤 인스턴스인지 확인하거나, EC2 Security Group inbound 규칙을 보면 누가 Nginx로 접근 중인지 파악할 수 있습니다.

**만약 자신의 인스턴스가 아니라면** 누군가 EC2에 침투했거나 네트워크를 타고 스캔 중인 것이므로, 즉시 Security Group을 ALB/특정 IP만으로 제한하고 AWS Support에 신고하세요.
