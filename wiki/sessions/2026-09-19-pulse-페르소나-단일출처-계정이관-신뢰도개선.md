## 배경 요청
사용자가 이미지 첨부와 함께 방향 전환을 지시: "pulse.lampas.io도 로그인 세션 단위로 움직일 수 있게
수정하고(필요 시 기존 데이터 폐기해도 됨), 페르소나를 Copy가 아니라 Pulse에서 만드는 걸로 수정하고,
Copy는 Pulse에서 만든 페르소나를 가져와서 선택하고 그것처럼 Copy를 만들 수 있게 하는 방식으로
방향을 바꾸자."

## 1. Pulse 페르소나 단일 출처 + 로그인 세션 전환 (아키텍처 개편)

### 설계
- **Pulse가 페르소나의 단일 출처**. 새 `pulse_personas` 테이블(메인 DB, 사용자 소유)에 분야+카테고리
  단위로 저장. 분류 체계는 `pulse-taxonomy.ts` 한 곳에서 관리(스포츠 MLB·NBA·KBO·축구, 예능, 뷰티,
  AI·테크로 시작).
- `POST /v1/pulse/personas` — 내 미션에서 수집한 클립 여러 개(`contentIds`)를 한 번에 분석해 페르소나
  4개 생성. 모델이 돌려준 근거 id를 실제 클립으로만 좁혀 `sources` 스냅샷과 타겟 규모 가설을 함께 저장.
- **장면 분석(역기획) 기능 전면 제거**: 컨트롤러·서비스·`analysis_*` 테이블(기동 시 DROP)·pulse 웹의
  분석 탭 모두 삭제.
- **pulse.lampas.io는 Google 로그인 세션 단위로 동작**. 미션은 새 `owner_email` 컬럼으로 귀속되고,
  읽기 API는 JWT 이메일로 필터. 에이전트는 새 env `PULSE_OWNER_EMAIL`을 미션에 실어 보냄. **기존
  미션은 귀속이 없어 로그인 후에도 보이지 않게 됨**(사용자가 사전 승인한 데이터 폐기).
- **Copy**: 클립 → 분야·카테고리(스포츠 MLB/NBA는 클립에서 자동 추론) → Pulse 페르소나를 가로 스크롤
  스트립에서 선택 → 카피 생성. 그 분야·카테고리에 페르소나가 하나도 없을 때만 "이 클립으로 페르소나
  4개 만들기"가 뜨고, 결과는 Pulse 라이브러리에 저장됨(Copy 자체 생성 경로 제거). `POST /v1/copy/runs`는
  `personaId`만 받고 서버가 소유권 확인. `/v1/copy/personas*`·`copy_persona_sets`·`copy_field_personas`
  제거.
- **Reels**: ③ 페르소나 선택 단계도 Pulse 라이브러리에서 고르는 것으로 전환.

### 구현 순서 (병렬 fork 활용)
API(taxonomy lib+spec → Prisma 모델+DDL → pulse DB 서비스/컨트롤러/ingest 사용자 스코프)를 먼저 직접
구현·검증(tsc 클린, 전체 938 스펙 통과)한 뒤, 서로 **독립적인 프론트 3개 + 에이전트 변경**을 fork로
병렬 실행:
- **Fork A (lampas-web-reels)**: persona 관련 API 교체(`fetchPulsePersonas`/`fetchPulseFields`),
  `personaOptions` 라이브러리 전체 기준 중복 제거, "Pulse에서 페르소나 만들기 ↗" 링크
  (`VITE_PULSE_APP_URL/personas`) 추가. vitest 81개, tsc, build 통과.
- **Fork B (lampas-agent)**: `PULSE_OWNER_EMAIL` env(`resolveOwnerEmail`/`warnIfNoOwnerEmail`) 추가,
  미션 생성 페이로드·로컬 DB(`missions.owner_email` 컬럼+인덱스)에 반영. vitest 41개, typecheck 통과.
  env에 `PULSE_OWNER_EMAIL=bacchus.dev@gmail.com` 기록.
- **Fork C (lampas-web-pulse, 신규 정식화)**: `AuthContext`/`RequireAuth`/`LoginPrompt`(Google OAuth),
  분석 탭·컴포넌트 전부 삭제, `/personas` 페이지 신설(분야+카테고리 선택 → 미션 선택 → 클립
  체크박스(조회수 상위 12개 기본 선택) → 페르소나 4개 생성 → 라이브러리 카드). vitest 22개, tsc, build
  통과.
- **Fork D (lampas-web-copy)**: 페르소나 생성 코드 전체 제거, `fetchPulsePersonas`로 대체, 클립→분야·
  카테고리 자동 매핑(`clipToPulse.ts`), 스튜디오 플로우 재배치(클립→분야·카테고리→Pulse 페르소나
  스트립→카피). **다른 세션이 동시에 작업 중이던 "copy hints" 기능(`HintSelect.tsx` 등)을 발견, 그대로
  보존**하고 컴파일·테스트 통과 확인만 함(엔드포인트 실존 여부는 미확인으로 명시). vitest 29개, tsc,
  build 통과.

전체 검증: lampas-api tsc+jest 938, pulse 웹 22, copy 웹 29, reels 웹 81, agent 353 — 모두 통과.
설계 문서 `docs/superpowers/specs/2026-09-19-pulse-field-personas.md`.

### 배포 (사용자 "배포해줘" 승인 후)
순서: ① 운영 메인 DB에 `prisma/manual/2026-09-19-pulse-personas.sql` 적용(기존 페르소나·리서치
테이블 DROP, `pulse_personas` 생성 — 로컬엔 이미 적용됨) → ② API 0.1.102 배포 → ③ pulse/copy/reels
웹 + 에이전트 병렬 배포. 결과: pulse.lampas.io 0.2.1, copy.lampas.io 0.2.1, reels.lampas.io 0.1.22,
lampas-agent 1.0.5(이 머신 launchd 재기동). 확인 사항: Google 로그인 후 미션 목록은 비어 있음(기존
미션 귀속 없음, 예상된 동작) · owner_email 컬럼/analysis 테이블 DROP은 API 기동 시 자동 마이그레이션
(첫 요청이 느릴 수 있음) · 다른 세션의 "copy hints" 변경도 같이 실려 배포됨(별도 DDL 헬퍼로 이미
적용된 것으로 보이나 그 세션에서 별도 확인 필요). **작업 트리는 커밋하지 않음** — 커밋 시 copy hints
작업과 분리 권고.

## 2. 계정간 미션 보내기 ("계정으로 보내기")
후속 요청: "여기서 수집된 것들을 특정 계정 정보를 주면 해당 계정으로 보내는 기능 만들어줘."

- Pulse 미션 목록·상세에 "계정으로 보내기" 버튼 추가. 받는 사람의 lampas 로그인 이메일을 입력하면 그
  계정 소유로 미션이 **복제**됨.
- 복제 범위: 미션 행, 선별 결과, 에이전트 수집 로그. **수집 콘텐츠(클립 등)는 공유 자산이라 그대로
  참조**(복제 안 함). 보내는 쪽의 원본 미션은 그대로 남음(이동이 아니라 복제).
- 복제된 미션의 파라미터에 보낸 사람 이메일·원본 미션 번호를 기록(계보 추적).
- 검증: 이메일 형식 오류·자기 자신에게 보내기는 거부, 가입되지 않은 이메일은 "해당 이메일로 가입된
  lampas 계정이 없습니다"로 차단.
- 구현: API `POST /v1/pulse/missions/:id/send` + DB 복제 트랜잭션 + 순수 검증 로직 `lib/mission-send.ts`
  (스펙 5건). Pulse 웹 `api.sendMission` + `lib/mission-send.ts`(테스트) + 목록·상세 버튼.
  검증: API tsc 통과, pulse 모듈 jest 34개, pulse 웹 vitest 25개·tsc·build 통과.
- 배포(DB 변경 없음, API+pulse 웹만): lampas-api 0.1.103(PM2 재시작 0회, 새 엔드포인트 미인증 401
  확인), pulse.lampas.io 0.2.2(CloudFront 무효화 완료).

## 3. 페르소나 신뢰도 개선 (진단 → 설계 승인 → 구현)
사용자가 이미지 첨부와 함께 "지금 페르소나 카드의 '신뢰도 낮음' 표시, 신뢰도를 높일 방법은?" 질문.

### 진단
당시 "신뢰도 낮음"은 **계산 결과가 아니라 고정값**이었음 — 근거 클립 2개 조회수 합을 2~5로 나눈
것뿐이라 표본이 늘어도 표시가 그대로였음.

### 제시된 4계층 프레임워크 (사용자 승인 후 1·2번 구현)
1. **근거의 양·다양성**: 페르소나당 최소 근거 클립 수(2개→5개 이상, 채널 3곳 이상) 기준, 재관측
   (`content_metrics`) 조회수 증가 추이를 신뢰 근거로 활용, 신뢰도를 표본 수·채널 수·댓글 수·관측
   횟수의 함수로 계산해 다음 단계까지 부족분을 함께 표시.
2. **더 좋은 신호**: 채널 구독자 수 합을 타겟 규모의 **상한**으로 사용(조회수만으로 과대추정되는 문제
   완화), 좋아요·댓글 비율로 "반응 시청"과 "수동 시청" 구분, 댓글을 타겟에 대응시켜 "N개 중 M개"로
   수치화해 검증 가능하게 함.
3. **가설 교차 검증**: 카피 채점과 동일한 방식으로 **다른 벤더 모델이 근거 대비 지지도를 채점**하고
   근거 없는 주장을 플래그. 트렌드 보드(뉴스·Google Trends)와 연결해 외부 신호로 가점/감점(3번은
   설계만, 이번 구현엔 교차 심사만 포함되고 트렌드 보드 연동은 안 됨).
4. **실제 성과 피드백**(가장 확실하지만 시간이 걸림): 카피·릴스 게시 후 조회수·댓글을 페르소나에
   되돌려 기록 — 성과 이력이 쌓인 페르소나만 "높음"이 되는 구조. **이번 세션엔 미구현**(설계 스케치만).

### 구현 (같은 세션, 뒤이은 요청 "이 내용이 반영될 수 있게 해서, 페르소나 생성이 더 잘 될 수 있게
수정해줘")
- **신뢰도 계산화**: 고정 "낮음" 대신 근거 클립 수·채널 다양성·검증된 타겟 댓글·재관측 횟수·교차
  심사 지지도를 가중 합산해 0~100점 + 낮음/보통/높음 등급. 카드에 "보통까지: 근거 클립 2개 더, 다른
  채널 1곳 더"처럼 다음 단계 안내.
- **교차 심사 추가**: 생성 직후 다른 벤더 채점 모델(**Opus 5, 실패 시 Grok**)이 근거 대비 지지도를
  채점, 근거 없는 주장을 별도 표시. 심사 실패해도 생성은 유지되고 "교차 심사 미완료"로 남음(항상
  성공하는 폴백 설계, [[llm-judge-fallback-chain]]과 같은 계열).
- **댓글 근거 검증**: 모델이 타겟 반응 댓글을 원문 그대로 인용하게 하고, 실제 수집 데이터에 있는
  댓글만 저장 — 지어낸 댓글은 버려짐.
- **구독자 상한**: 근거 채널 구독자 합보다 큰 타겟 추정은 잘라내고, 좋아요+댓글 기반 "반응 시청" 수를
  별도 표시.
- **프롬프트 강화**: 페르소나마다 최소 3개 클립 인용(근거 부족 시 그 수까지), 서로 다른 채널 섞기,
  미확인 부분은 "가설:" 문장으로 분리, 재관측 클립의 조회수 증가분도 모델에 전달.
- **웹 반영**: Pulse 카드에 신뢰도 배지(색상 단계)·신호 요약·다음 단계 안내·교차 심사 코멘트·근거
  없는 주장·타겟 반응 댓글 인용. Copy 스트립은 신뢰도 점수 순 정렬 + 점수·심사 점수 표시 + 선택 시
  "신뢰도를 올리려면" 안내.
- 버그 하나 발견·수정: 테스트 어서션의 이중 이스케이프된 JSON 문제(구현 자체가 아니라 스펙 오류).
- 검증: lampas-api tsc 통과·jest 957개(20개 추가), pulse 웹 vitest 27개, copy 웹 vitest 32개, 모두
  tsc·build 통과.
- **배포는 이 세션에서 하지 않음** — 기존 페르소나는 "낮음·계산 전"으로 표시되고 재생성해야 반영,
  4단계(성과 피드백)는 없음, DB 변경이 없어 배포 시 API+pulse+copy 세 개만 필요하다고 안내한 채
  세션 종료.

## 최종 상태 (세션 종료 시점)
- 1번(아키텍처 개편)과 2번(계정간 보내기)은 각각 사용자 승인 후 배포·검증까지 완료.
- 3번(신뢰도 개선)은 구현·검증까지 끝났으나 **배포 여부는 이 소스에서 확인되지 않음**(다음 세션에서
  배포 확인 필요).
- 다른 세션의 "copy hints" 동시 작업이 이 저장소에 함께 존재 — 배포엔 같이 실려 나갔지만 커밋 시
  분리 필요하다는 권고가 세 번 반복됨(설계 단계·1차 배포 후·2차 배포 후).
