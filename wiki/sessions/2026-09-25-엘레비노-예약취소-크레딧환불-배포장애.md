# 2026-09-25 — 엘레비노 모임 예약 취소·크레딧 환불 기능 구축 + 프로덕션 배포 장애 복구

`Tool: claude`, 작업 디렉터리 `~/Works/cwc/elevino-system`. 한 세션 안에 "기능 구현 → 개발 배포 →
프로덕션 배포 → 프로덕션 다운 → 원인 규명·복구 → 형제 저장소발 기능 유실 발견·복구"까지 이어진
장시간 세션.

## 1. 기능 구현
[[progdesigner]] 요청: 어드민에서 모임 예약을 취소할 수 있게 하고, 결제 전이면 단순 취소, 결제
완료면 크레딧으로 환불하고 그 크레딧을 다시 계좌로 출금(환불)까지 어드민에서 처리.

- **전제 정정**: 어드민의 "모임 예약"은 `reservation`(공간 예약) 모듈이 아니라 `RESERVE_GATHERING`
  티켓 + 연결된 결제 영수증이었다. 취소/환불 로직은 티켓·영수증 기준으로 구현.
- **예약 취소** `POST /admin/tickets/:id/gathering/cancel` — 미결제면 영수증/티켓만 `CANCELLED`.
  결제완료(`PAID`)면 새 트랜잭션 타입 **`CREDIT_REFUND`**로 크레딧을 되돌리고 영수증 `REFUNDED`,
  티켓 `CANCELLED`(반환액은 `extras.refundedCredit`에 기록). 취소 사유·슬랙 알림·사용자 푸시 포함,
  취소된 티켓은 중복예약 체크에서 제외되어 재예약 가능.
- **크레딧 환불** `POST /admin/tickets/:id/gathering/refund-credit` — 반환된 크레딧을 관리자가
  입력한 계좌로 환불 처리(크레딧 차감 + 완료 상태 `CREDIT_EXCHANGE` 티켓·영수증 생성, 기존 "크레딧
  출금" 목록에도 노출). 초과 반환·잔액 부족·중복 환불 방지. 실제 계좌이체는 기존 출금 승인과
  동일하게 관리자가 수동 진행.
- 어드민 화면: 모임 예약 상세에 "예약 취소"/"크레딧 환불" 버튼 + 전용 화면 2개, 목록/상세에 결제
  수단·상태·취소사유·반환크레딧·계좌환불정보 컬럼 추가.
- 이 이식은 [[credit-ledger-balance-pattern]] 스킬이 분석한 elevino 크레딧 원장 구조를 그대로 활용한
  사례(단, 이번엔 [[cwc-system]]으로의 이식이 아니라 elevino-system 자체 내 신규 기능).
- DB 스키마 변경 없음(트랜잭션 타입 값 하나 추가, 기존 컬럼 길이 내). 검증은 API 타입 검사 통과 +
  어드민 신규 파일 오류 0건까지만, **실제 화면 동작(결제완료 예약 1건 취소→환불)은 미검증**.
- 주요 파일: `apps/api/src/modules/ticket/controllers/admin.ticket.cancel.controller.ts`,
  `apps/api/src/modules/gathering/services/gathering.service.ts`,
  `apps/api/src/modules/payment/services/payment.credit.service.ts`,
  `apps/admin/src/components/organisms/reserve-gathering/reserve-gathering-{cancel,refund}.tsx`,
  `apps/admin/src/data/schemas/reserve-gathering-schema.ts`.
- 커밋 `c46f8c19` "feat: 관리자 모임 예약 취소 및 크레딧 환불 기능 추가" (`dev`).

## 2. 개발 배포
`release/api/dev`에 `dev` 머지(`2df519b0`), `release/admin/dev`를 `dev`로 fast-forward. GitHub
Actions Deploy 워크플로가 `micro.dev.elevino.io`에 배포. 이 PC에서는 DNS/SSH가 안 잡혀 직접 검증
불가(`gh` CLI·토큰도 없음) — 결과 확인은 사용자에게 위임.

## 3. 프로덕션 배포 → 장애 → 복구
- 사용자가 "배포해줘"를 반복해 프로덕션까지 진행. `release/api/prod`(`d825a7c7`),
  `release/admin/prod`(`c46f8c19` fast-forward) 푸시. HTTP 상태코드 폴링(401/404 전환)으로 배포
  완료 여부를 원격에서 확인하는 방식 사용 — 어드민은 200 확인, **API는 프로덕션에서 다운**.
- **장애 원인**: `ServiceLoader.onModuleInit`이 모든 provider에 대해 무조건
  `name.endsWith('Service')`를 호출 — provider 이름이 문자열이 아니면 `TypeError`로 앱 부팅 자체가
  실패해 3101 포트를 못 열었다. 오래된 잠재 버그.
- **롤백이 안 먹힌 이유**: `release/api/prod`의 이전 커밋으로 되돌려도 같은 오류가 재현됐다 — 알고
  보니 9월 18일까지 돌던 "정상" 프로덕션은 `yarn version`으로 로컬 `package.json`만 올린 **개발자
  로컬 수동 빌드(0.9.5, origin에 없음)**였다. 즉 git 히스토리상의 "이전 정상 커밋"이 실제로 프로덕션에
  떠 있던 코드가 아니었다.
- **1차 수정**: provider 이름이 문자열일 때만 검사하고 예외 시 건너뛰도록 `ServiceLoader` 방어 코드
  추가(`2e05bcf1`) → `release/api/prod`(`556bf93e`) 배포로 복구. 다운타임 약 23분(10:08~10:31 UTC).
  복구 후 "CRASHED" 감시 오탐 1건(pm2가 `.env` 변경으로 먼저 재시작하며 회전 전 로그의 과거 오류를
  집계한 것) 발생, 실제 새 빌드는 정상 기동 확인.
- **2차 발견 (더 큰 문제)**: 사용자가 "코드 최신화하고 기능이 돌아간게 있으면 복구해줘"라고 지시.
  조사 결과 **프로덕션은 8월 3일부터 형제 저장소 `~/Works/cwc/cwc-system`의 `apps/elevino-*`에서
  수동 배포되고 있었다** — 이 모노레포(`elevino-system`)의 `dev`를 배포하면서 그쪽에만 있던 기능
  (cwc 브리지·와인 모듈, 소장 신청 중단/취소, 모바일 관리자 메뉴, 예약 티켓 모임ID 검색, 이미지
  CDN·KST 정리, Toss 라이브 키 등 env)이 프로덕션에서 통째로 사라졌던 것.
  - **복구 방법**: 두 저장소의 공통 조상(`afd2085c`)에서 동기화 브랜치를 만들어 cwc-system의 해당
    파일을 그대로 가져오고(`5b30bea5`), `dev`에 3-way 머지(`a3b0fdb2`). 충돌은 `ServiceLoader`
    한 파일뿐이었고 cwc-system 쪽(더 올바른) 구현을 채택. 예약 취소·크레딧 환불 기능은 그대로 유지.
  - 배포: `release/api/prod`(`9df0e0e6`, 서버 버전 0.9.5로 표시), `release/admin/prod`(`a3b0fdb2`).
    웹(`apps/web`)·링크(`apps/link`)도 코드는 반영했지만 이번엔 재배포하지 않음(원래 프로덕션에서
    돌아간 적 없는 변경이라).
  - 검증: API 11:51:38 UTC 기동, 복구된 cwc 라우트(`/admin/cwc/members`, `/users`, `/wines`) 401
    (존재·인증 요구)로 확인. 어드민 11:53:22 재시작, 홈/예약목록/취소·환불페이지/바우처요청 모두 200.

## 결정/사실
- 이 사건으로 **`~/Works/cwc/cwc-system`이 ERP 크롤링 분석 모노레포일 뿐 아니라, `apps/elevino-*`라는
  이름으로 elevino 서비스의 실제 프로덕션 배포 소스 역할도 겸하고 있었음**이 처음 확인됨 — 기존
  [[cwc-system]] 엔티티 페이지의 "4개 앱(cwc-api/cwc-web-admin/cwc-crawler-erp/cwc-agent-docs)"
  기술과 다른 사실이라 페이지에 별도 명시함.
- 앞으로 프로덕션은 **`release/api/prod`/`release/admin/prod` 브랜치 경유로만** 배포하는 것을 권장
  (로컬 수동 배포가 다시 섞이면 오늘처럼 롤백 불가능해짐). 모노레포(elevino-system)가 이제
  cwc-system보다 코드가 앞선 상태이므로, 앞으로는 한쪽에서만 작업·배포하는 것이 필요.
- 재사용 가능한 절차는 [[prod-rollback-source-of-truth-verify]] 스킬로 추출.
