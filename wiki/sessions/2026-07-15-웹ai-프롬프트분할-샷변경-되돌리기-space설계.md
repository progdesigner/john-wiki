## 1. 프로젝트 구조 분석 — 문서(CLAUDE.md)와 실제의 괴리

pnpm 워크스페이스 모노레포(pnpm 10.32.1, hoisted)에 **Lampas 6앱 + Iileex 3앱** 총 9개 앱. 핵심은
`lampas-api`(NestJS+Prisma, 19개 도메인 모듈, Prisma 모델 35개)와 `lampas-web-sdk`(React+Vite, Atomic
Design). CLAUDE.md 문서와 실제 파일 구조 차이 3가지 발견:
1. `lampas-api` 모듈 목록에 `admin`/`api-clients`/`audit-logs`/`email`/`products` 누락(실제 존재).
2. `lampas-web-sdk` organisms의 `references/` 디렉터리가 문서 구조도에 없음(Instagram 레퍼런스 작업 관련).
3. 루트에 `AGENTS.md`가 `CLAUDE.md`와 별도 존재.

## 2. `lampas-web-ai`가 주요 앱으로 승격

사용자가 "이제 중요해"라고 지정 → 하네스 자체 메모리에 저장(이 위키와 별개) + 구조 정밀 분석:

- 소스 16개 파일·약 4,900줄, 핵심 로직 절반 이상이 `src/chat/actorFlow.ts` 단일 파일(2,658줄)에 집중.
- **3개 유한 상태 머신**을 한 파일에서 `type`+`step` 문자열로 관리: 액터 만들기, Object 만들기, 촬영하기.
- 상태 관리는 reducer 없이 Context+useState, 대화는 사용자별 localStorage(`lampas_ai_chats:{userId}`, 최대
  50개, base64 이미지는 저장 전 제거)에 보관.
- 인증은 Google OAuth idToken → `POST /api/auth/google` → lampas-api 자체 JWT.
- lampas-web-sdk와 달리 Atomic Design/variant 체계를 쓰지 않는 별도 구조.
- **위험 신호**: actorFlow.ts가 단일 거대 파일이라 플로우 추가마다 충돌 위험 — 계속 커지면 플로우별 분리
  검토 필요(미해결 권고).

## 3. Object 생성 프롬프트 "항목별 수정" 기능 이식 (SDK → web-ai)

**요청**: web-ai의 Object 생성도 SDK처럼 프롬프트를 항목별로 쪼개서 도중에 수정할 수 있게.

SDK 분석 결과, Object 프롬프트는 이미 3계층으로 쪼개져 있었음: SDK 폼(카테고리·소재·색상·스타일·배경·설명
6필드) → 한글 요약(`buildObjectNarrativeSummary`) → API `buildObjectPrompt()`가 필드별 영어 문장으로 재조립
(`objects.service.ts:521-536`, 값 있는 필드만 한 줄씩). web-ai의 `ObjectFlowState.data`에는 이미 동일 6필드가
있었고, 촬영 플로우에서 쓰던 `prompt-editor` 메시지 컴포넌트(필드별 textarea + 적용 버튼, `MessageBubble.tsx`)
도 그대로 재사용 가능하다는 게 핵심 발견.

**구현** (`apps/lampas-web-ai/src/chat/actorFlow.ts` 한 파일만 수정, 새 타입·API 불필요):
- `showObjectPromptEditor()` — 6필드를 `prompt-editor`로 펼침.
- `applyObjectPromptEdit()` — 적용값 병합(빈 값은 필드 제거), 생성 결과 리셋 후 요약 재표시.
- `handleObjectOption()`에 `obj:edit`/`promptedit:` 분기 추가. Object 플로우는 타입별로 먼저 라우팅되므로
  촬영 플로우의 동일 이름 처리와 충돌 없음.
- `object-confirm`(요약 확인)과 `object-profile-review`(대표 이미지 검토, 생성 실패 시 포함) 양쪽에
  "✏️ 프롬프트 수정" 칩 노출. 요약 텍스트에 빠져 있던 "배경" 항목도 추가.

**배포**: `./scripts/deploy-web.sh lampas-web-ai` → https://ai.lampas.io. 도중 pnpm PATH 함정 →
[[deploy-sandbox-pnpm-shim]] 절차로 우회.
**커밋**: `05cda59`(feat) + `19b95e8`(chore: 이전에 실수로 커밋된 `.deploy-bin` shim 제거, 이번 세션이
만든 문제 아님).

## 5. 채팅 되돌리기(undo) 2종 구현

**요청**: "이전"이라 치면 직전 상태로 복귀, 또는 메시지별 수정 아이콘으로 그 시점부터 재시작.

- **"이전" 명령**: `이전`/`뒤로`/`되돌리기`/`undo` 인식 → 마지막 사용자 입력 직전 상태로 복귀(그 입력·이후
  대화 삭제, 당시 칩/프롬프트 편집기 복원). 반복 입력하면 계속 뒤로.
- **메시지별 재시작(✏️)**: 사용자 말풍선 옆 ✏️ 버튼 → 해당 메시지 보내기 직전 상태로 복귀 + 원문을
  입력창에 프리필. 칩으로 만든 메시지에서도 동작(다른 선택지 재선택 가능).
- **구현 방식**: 사용자 입력 발생마다 직전 플로우 상태(단계·수집 필드) 스냅샷을 그 메시지에 저장(`store.tsx`),
  되돌리기 시 스냅샷으로 세션 복원. 액터/Object/촬영 플로우 공통 동작.
- **제약**: 스냅샷 속 base64 이미지는 localStorage 저장 시 제거(기존 정책과 동일) → 새로고침 후 사진 단계로
  되돌리면 재업로드 필요. 배포 전 대화의 메시지엔 스냅샷 없어 ✏️ 미표시. busy 중엔 되돌리기 차단.
- 배포 + 커밋 `4e0fe77`.

## 6. Space(공간) 신규 엔티티 — 설계만 완료, 구현 미착수

**요청**: SDK·web-ai 양쪽에 Space(공간) 생성 기능. Object처럼 레퍼런스를 유지한 채 만들되, 샷 대신 **낮/밤
시간대·조명**을 프롬프트 항목으로 분리.

병렬 분석(SDK `objects` 프론트 구조 + API `objects.service.ts`)으로 확정한 전략:
- **백엔드**: 신규 모듈 없이 `StudioObject` 재사용 — Space는 `category: 'space'`인 오브젝트로 저장(스키마
  마이그레이션 불필요, `category`는 자유 문자열이고 findAll 필터·검색 이미 지원).
- **프롬프트 분할 5항목**: 공간 유형(spaceType) · **시간대(timeOfDay: 새벽/아침/낮/골든아워/노을/밤)** ·
  **조명(lighting: 자연광/네온/캔들/스튜디오)** · 분위기(mood) · 설명.
- **레퍼런스**: Object처럼 분석 후 생성 시 `referenceImageData`로 유지.
- **주의점 확인**: Gemini `analyzeObjectTraits` 프롬프트가 "single physical OBJECT(사람 아님)" 전제 + category
  enum에 space/interior 없어 그대로 재사용 불가 → 공간 전용 프롬프트/메서드 필요.
- SDK 쪽엔 `molecules/object/creation/` 복제 대상 파일 목록(훅 1개+상수+섹션 8개), 라우트 4줄, 내비게이션
  수정 지점까지 구체적으로 특정됨.

**중단 지점**: API 파일 3개를 Edit하려는 순간 하네스 권한 채널이 다시 "Stream closed"로 끊겨(이 세션에서
2번째 발생, [[lampas-harness]] 기존 함정과 일치) 구현에 착수하지 못한 채 세션 종료. 마지막 메시지는 "아무
메시지나 보내주시면 구현을 이어가겠습니다"로 끝남 — **API/SDK/web-ai 코드 변경은 이 세션에서 전혀 이뤄지지
않음**.

**저녁 세션과의 관계**: 같은 날 23:11~ 세션([[2026-07-15-스페이스-엔티티-sdk-api-webai-구현]])이 처음부터
다시 "Space가 코드베이스에 있는지" 조사해 "없음"을 재확인한 뒤 구현했다 — 이 세션의 설계(5필드: spaceType·
timeOfDay·lighting·mood·description, category='space' 재사용 전략)와 저녁 세션의 실제 구현(공간 카테고리
11종 + `Space` 신규 Prisma 모델)이 **세부 사항에서 다르다**: 이 세션은 기존 `StudioObject`를 `category`
값만으로 재사용하는 안이었으나, 저녁 세션은 별도 `Space` Prisma 모델(테이블 `spaces`)을 신설했다. 즉 낮
세션의 "최소 변경" 전략이 저녁 세션에서 채택되지 않고 더 무거운(그러나 더 명확한) "독립 모델" 전략으로
바뀐 것으로 보인다 — 두 세션 사이에 별도 논의가 있었는지는 이 소스만으로는 확인 불가.
