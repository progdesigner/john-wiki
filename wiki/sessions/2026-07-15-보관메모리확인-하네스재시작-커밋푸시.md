- 프런트: `.archbtn` 클릭 → `archiveSession(id)`(`apps/web/index.html:2092-2094`) → `POST

  미저장이거나 저장 후 변경(stale)됐을 때만 `memoryInput` 경로 설정(3767-3779) → 파일(`.md`/`.jsonl`/
  `.session.json`)을 `chats/archive/`로 이동(3781-3788) → `memoryInput` 있으면
  `enqueueJob("memory-ingest", {...})`(3790).
- `enqueueJob`(`src/queue.ts:54-61`)은 `queue/`에 잡 파일을 쓰기만 하고 즉시 반환 — HTTP 응답도
  `{ ok: true, remembered: true }`로 바로 나감(3796). **실제 wiki 통합(markdown 작성)은 별도 비동기
  작업**이라는 점을 재확인.

### 2. 하네스 재시작 — "재시작해줘" → 대상 확인 → 지연 스크립트
사용자가 "재시작해줘"라고만 요청하자 어시스턴트가 대상을 먼저 확인(웹서버 8787 / memory-ingest 데몬 /
rapid-mlx 8000 세 후보 중 하나 — 8787은 **이 대화 자체가 그 위에서 돈다**는 이유로 주의 필요).
"하네스를 재시작해줘"로 8787을 특정하자, `scripts/restart-lampas.sh`를 확인 후 실행:
- nohup으로 자신을 `--worker` 모드로 재호출 → 즉시 "예약됨" 반환(현재 응답이 먼저 사용자에게 전달됨) →
  워커가 5초 대기 후 `launchctl kickstart -k gui/$(id -u)/io.lampas.harness.daemon` → `/api/health`
  폴링으로 성공 확인, 실패 시 로그(`logs/server.log`)에 기록.
- 재시작 직후 같은 요청이 한 번 더 도착("하네스를 재시작해줘" 재입력, 새 세션으로 보임) — 이미 완료된
  상태(07:59:14 성공, launchd running pid 24309, `/api/health` `{"ok":true,...}`)임을 로그로 확인하고
  중복 재시작 없이 결과만 안내.

**⚠️ 기존 기록과의 불일치 발견**: `[[lampas-harness]]` 엔티티(2026-07-11 세션 반영분)는
`restart-lampas.sh`를 "**수동 즉시**: `pkill -f lampas` 후 daemon/server/scheduler 재시작"으로 기록했다.
그러나 이 세션과 같은 날 앞선 `[[2026-07-15-gpt-realtime-음성입력-길게누르기]]`(22:40~22:41)가 실제로
확인한 동작은 **지연(nohup+kickstart, pkill 없음)**이다. `scripts/restart-lampas.sh` 원본을 직접 읽어
대조한 결과 **현재 스크립트는 지연 방식이 맞다** — 2026-07-11 이후 스크립트가 즉시 pkill 방식에서 지연
nohup+launchd kickstart 방식으로 다시 쓰였을 가능성이 높다(안전성 개선). → `[[lampas-harness]]`·
`[[self-hosted-agent-server-ops]]`에 반영, 2026-07-11 기록은 낡은 것으로 표시.
