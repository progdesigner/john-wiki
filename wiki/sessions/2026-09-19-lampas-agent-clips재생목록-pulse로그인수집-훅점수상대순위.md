### 2. Pulse 스케줄 수집이 로그인 계정과 무관하게 저장되던 문제 (3라운드 수정)
사용자가 "스케줄 수집이 pulse.lampas.io에서 안 보인다"를 반복 제보했고, 어시스턴트가 세 번에 걸쳐
원인을 좁혀간 시퀀스:

**1차: 스케줄 런이 FAILED로 찍히는 원인**
- 스케줄 `MLB`(6시간) 런의 실제 오류는 `GET /v1/pulse/missions/6/selections → 401`. Pulse API가
  그날 "로그인 세션 단위(owner_email)" 필터로 바뀌면서 `/v1/pulse/missions/*` 읽기 엔드포인트 전부가
  사용자 JWT 전용이 됐고, 에이전트의 운영 스토어(`remote.ts`)는 ingest 토큰(`x-pulse-token`)만 가져서
  결과 카드 조회(`listSelections`)가 401 → 4xx는 결정적 실패로 분류돼 런 전체가 FAILED 처리됨. 저장
  자체(`/ingest/*`)는 이미 성공하고 있었다.
- 제시된 방법 3가지 중 **1번(ingest 토큰으로 결과 조회 허용 + 결과 조회 실패를 런 실패로 치지 않기)**을
  권장안으로 채택, 사용자가 승인.

**2차: "스케줄과 진행에 운영만 선택할 수 있게, 로컬은 제거"**
- 스케줄·진행(수집) 패널의 로컬/운영 토글을 제거하고 "저장 운영" 배지로 고정. 로컬 저장은 CLI
  `pulse run --env local`에만 남김.
- 동시에 lampas-api에 ingest 토큰 기반 결과 조회 엔드포인트 추가 + 에이전트가 그걸 쓰도록 변경,
  결과 조회 실패는 런을 실패시키지 않게 수정.
- 같은 배포에서 유튜브 자동 검색 후보 0개 문제도 발견·수정: 시의성 필터 조합("조회수순 + 기간 +
  4분 미만")이 유튜브에서 "검색결과 없음"을 반환하는 조합이었음을 헤드리스로 실측 확인 →
  정렬을 관련도로 바꾼 "기간 + 4분 미만" 조합으로 후보 확보(쇼츠 15→스크롤 후 30개).
- 커밋 5건(main): `0376c963`(agent: 런 원장·워커·접근제어+Clips 재생목록+Pulse 스케줄 복구) ·
  `85feb03a`(api: Pulse 로그인 세션 단위+페르소나 라이브러리 이관+ingest 결과조회) ·
  `e798e933`(web: pulse·copy·reels·clips·trends 반영) · `b41c75c9`(dalar-web-first 스크립트+lockfile) ·
  `9d79a140`(agent 배포 버전 bump).
- **미완 확인사항 2가지**: (a) lampas-api는 이 시점 아직 배포 안 됨 — 배포 전 운영 DB에
  `prisma/manual/2026-09-19-pulse-personas.sql` 적용 필수. (b) 저장소 정책상 `env/` 하위 env 파일이
  커밋 대상이라 `apps/lampas-agent/env/.env.local`의 `AGENT_ACCESS_TOKEN`이 이 커밋에 포함됨(비밀값
  커밋 사례 — `.lampas-attachments/`·`output/`은 이번에 `.gitignore` 추가로 제외).

**3차: "수집했는데 pulse.lampas.io에서 안 보인다 — 로그인 베이스로 수집을 안 해서 그런거 아냐?"**
- 확인 결과: 운영 DB에 미션 6~9는 모두 저장돼 있었고 소유자가 `bacchus.dev@gmail.com`(env의
  `PULSE_OWNER_EMAIL` 폴백값)으로 붙어 있었음 — **사용자 진단이 정확**했다. 수집·저장은 됐지만 소유자가
  로그인 계정이 아니라 에이전트 env에 고정된 이메일이라 pulse.lampas.io에 로그인한 계정과 다르면
  안 보이는 구조.
- 수정: 진행 탭 "지금 화면에서 수집"과 스케줄 등록이 **에이전트 우상단에 Google 로그인한 계정**을

  수집·등록 버튼이 잠기고 안내 표시. `PULSE_OWNER_EMAIL`은 CLI 폴백·구 스케줄 폴백으로만 남음.
- 사용자 조치 필요: 에이전트에서 pulse.lampas.io와 같은 Google 계정 로그인, 기존 `MLB` 스케줄
  삭제 후 재등록(계정 정보 없이 등록된 구 스케줄이라).

**4차: "또 로그인 계정이 아닌 bacchus.dev@gmail.com로 수집되어 보인다"**
- 근본 원인이 하나 더 있었음: 3차 배포 1분 뒤 실행된 런이 **배포 전 번들을 그대로 쓰던 열린 탭**에서
  요청돼 계정 정보 없이 전송됐고, 데몬이 이를 **조용히** env 폴백으로 받아 처리한 것. 수집 코드 자체
  버그가 아니라 "옛 번들 + 조용한 폴백"의 조합이 문제.
- 근본 수정(에이전트 1.0.11): 데몬이 **계정 없는 수집·스케줄 등록을 거부**(명확한 에러 메시지로 새로고침·

### 4. 훅 점수가 실행마다 흔들리고 단독 재채점 시 낮아지는 이유 → 상대 순위로 전환 (2단계 개선)
사용자의 목표는 "종합적으로 후킹한 영상 찾기"였고, 절대 점수 방식의 구조적 문제를 짚어낸 뒤 실제로
2단계에 걸쳐 구현까지 완료됨.

**진단 (원인 5가지)**
- temperature·seed 미지정 → Gemini 기본 샘플링으로 같은 입력도 ±10~15점 흔들림.
- 기준선 없는 0~100 점수 — "70점과 40점이 어떤 영상인지" 앵커 문장이 없어 모델이 매번 자기 눈금을 새로 만듦.
- JSON 필드 순서가 `hookScore`→`hookReason`이라 점수가 먼저 나오고 이유가 사후 합리화됨.
- 한 응답에 필드 12개(설명·태그·샷·분위기·이유·4축·스포츠 필드까지) — 훅 점수 하나에 쓰는 주의가 작음.
- **단독 재채점이 낮아지는 이유**: 배치(4개)로 보낼 때 모델이 배치 내 **상대 비교**로 대비 효과를 만들어
  눈에 띄는 클립엔 높은 점수를 줌 — 혼자 보내면 비교 대상이 없어 보수적인 중간·하위 점수로 회귀.
  재시도 경로(클립 단독 재호출)도 같은 현상.
- 결론: "후킹한 영상 찾기"는 절대 점수보다 **상대 순위**가 목적에 맞다. 더 근본적으로는 비교 채점
  (토너먼트·Bradley-Terry)이 단독 채점보다 안정적.

**후속 확인: 상대 비교가 더 빠른가?**
- 비교 채점은 **이미지 없이 텍스트만으로** 가능 — 라벨링이 이미 만든 설명·발화 요약·샷·분위기·전사를
  텍스트로 묶어 보내면 됨. 클립 100개 기준: 지금 방식(배치 4개 비전 채점) 25회·이미지 300장 vs
  리스트 비교(30~40개씩 텍스트 순위+상위군 재비교) 3~5회·이미지 0장·약 30~60초. 쌍대 비교 토너먼트
  (n log n ≈ 700회)는 비현실적이라 리스트 방식으로 대체.
- 트레이드오프: 텍스트만 보면 첫 프레임 시각적 훅이 약해짐 → 라벨링 때 "첫 1초 화면 묘사" 한 문장을
  받아두거나 비교 단계에 클립당 첫 프레임 1장만 보완 가능. 순위는 상대값이라 소스 간 직접 비교 불가 →
  뱅크 정렬은 소스별 백분위로 정규화해야 함.

**구현 (사용자 승인 후 2단계로 진행)**
- **1단계 (에이전트 1.0.12)**: 비전 라벨 프롬프트에서 훅 점수·훅 이유·4축 점수를 제거. 설명이 첫
  키프레임 장면으로 시작하도록 해 텍스트만으로도 첫 순간의 훅 판단이 가능하게 함. 라벨 비전 호출에
  temperature 0 추가.
- **2단계 (API 0.1.108)**: 새 엔드포인트 `POST /v1/clip-intelligence/rank-hooks` — 소스의 클립을
  설명·발화·전사 텍스트만으로 "훅이 강한 순서"로 리스트 비교(40개씩 조각 비교 후 각 조각 상위군을
  다시 비교해 합침), 소스 안 백분위(1위 100, 꼴찌 0)를 `Clip.hookScore`·`hookReason`에 되씀. 근거를
  먼저 쓰고 순서를 정하는 순서로(이유 우선), temperature 0. 에이전트가 업로드 직후 자동 호출, 실패해도
  잡은 완료되며 언제든 재호출해 순위만 재계산 가능.
- 효과: 클립 100개 기준 이미지 0장·호출 3~5회로 1분 안에 끝나고, 단독 채점이 없어져 "따로 하면
  낮아지는" 현상이 사라짐.

### 5. (부수적으로 함께 발견·수정) 위키 수집 실패
- 같은 배포 작업 중 "위키 수집 여부도 확인" 차원에서 발견: 운영 DB에 위키 소스 4건 저장됐지만 페이지가
  만들어진 건 1건뿐. 나머지 3건은 "응답 JSON 파싱 실패" 502로 종료된 것을 운영 로그에서 확인 — 응답
  상한 4000토큰에 선수·구단 페이지 본문이 잘린 게 원인.
- 수정: 응답 상한 16000으로 상향, 페이지당 1,500자·최대 6페이지로 간결하게 쓰도록 지시 변경, 파싱
  실패 시 JSON 모드로 한 번 더 재시도. 에이전트 쪽 위키 단계 자체는 문제 없었음. **다음 스포츠 소스
  클립화부터** 페이지가 쌓일 것으로 예상(이 세션 안에서 검증 완료는 아님).

## 최종 배포·검증 상태 (세션 종료 시점)
- **1단계·2단계 모두 배포·커밋 완료.** 드리프트는 운영 DB에 남은 구 컬럼 삭제 항목뿐이라 API 배포가
  안전하다고 판단해 에이전트→API 순서로 배포·검증.
- MLB 운영 수집 런 1건으로 검증: 첫 검색 후보 20개, 저장 20개, 조건 충족 8개로 정상 완료.
- 훅 순위 재계산은 이미 올라간 소스에 대해 **web-clips에 버튼이 아직 없어** 소스 id로 `rank-hooks`를
  직접 호출해야 하는 상태로 남음(사용자에게 버튼 추가 여부 제안, 이 세션에선 미결).
- 뱅크의 4축 미니 바(확산·정보·감정·완결)는 라벨링이 더 이상 채우지 않고 reels의 AI 선별(`analyze`)이
  채움 — 위 1단계 변경(4축 점수 제거)의 직접적 결과.
