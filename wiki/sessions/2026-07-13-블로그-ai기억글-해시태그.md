# 2026-07-13 — 기억 이관 트리거 + 네이버 블로그 AI기억글 해시태그 추천

한 트랜스크립트에 두 개의 독립 주제가 담긴 세션. 앞부분은 이미 별도로 정리된 기억 이관의
**하네스 측 시작 지점**이고, 뒷부분이 이 세션의 고유 내용(공개 블로그 글 + SEO 해시태그)이다.

## Part 1 (08:42~08:48) — "지금까지 보관한 것 모두 위키에 저장" 트리거

`[[progdesigner]]`가 "보관한 것까지 모두 wiki(장기 기억)에 저장"을 요청 → 어시스턴트가 프로젝트
auto-memory 13개를 `[[john-wiki]]`로 이관하는 작업을 시작한 대화. **결과물 자체는 이미
[[2026-07-13-람파스-누적운영기억-이관]] 세션에 정리돼 있고**, 여기서는 그 **하네스 측 실행 방식**만
추가로 드러난다:

- john-wiki가 작업 폴더 밖이라 어시스턴트가 파일/Bash로 직접 못 쓰고 **현재 위키 상태도 못 읽음**
  (샌드박스). 그래서 레포에 설계된 정석 경로 `memory-ingest` 잡을 사용.
- 절차: 13개 기억 전문을 `logs/memory-export-2026-07-13.md`(gitignore된 `logs/`)로 작성 → 실행 중
  데몬 큐에 `memory-ingest` 잡 등록 → 데몬이 위키 **pull → 사서 에이전트 병합 → index/log/AI_CONTEXT
  갱신 → commit → push**까지 자동 수행. **어시스턴트 턴이 끝나도 데몬이 완결**한다.
- 잡 상태는 `queue/*.processing` → 완료 시 `queue/done/` 또는 `queue/failed/`로 이동. 백그라운드
  샌드박스가 더 엄격해 홈·`node` 접근이 막히므로 **레포 내부 큐 파일 이동만 폴링**해 완료를 감지.
- "위키에 저장" = **셰어드 저장소에 git push** 포함임을 명시하고 진행.

→ 이 실행 방식은 [[wiki-memory-provider-integration]]·[[detach-long-job-nohup]] 맥락과 이어진다.

## Part 2 (14:21~14:24) — 네이버 블로그 글 SEO 해시태그 30개

`[[progdesigner]]`가 자신의 네이버 블로그 글에 붙일 **SEO용 태그 30개**를 요청.

1. 처음엔 URL(`blog.naver.com/study-ai-what/224345496699`)만 제시 → 어시스턴트가 본문을 못 읽음:
   **네이버가 외부 크롤(WebFetch) 차단** + 연결된 [[naver-blog-mcp]]에 **읽기 기능 없이 발행 기능만**
   존재. 내용을 모른 채 태그를 지어내면 저품질 위험이라 **제목·본문을 붙여달라 요청**(추측 대신 확인).
2. 사용자가 글 전문을 붙여넣음 → 어시스턴트가 본문 근거 기반 30개를 대표어/핵심주제어/롱테일로 배분.

### 핵심 발견 — 블로그 글의 주제가 곧 이 위키다

붙여넣은 글 제목: **"AI 장기기억 만드는 법 — ChatGPT·Claude가 나를 기억하게 하는 Git 위키"**.
즉 `[[progdesigner]]`는 자신의 네이버 블로그 **`study-ai-what`**에 `[[lampas]]`의 장기기억
아키텍처([[long-term-memory-architecture]])를 **공개 연재**하고 있다. "앞으로도 람파스가 스스로
기억을 정리·다듬는 과정을 이 블로그에 계속 기록하겠다"고 명시 → 반복될 작업 맥락.

글이 밝힌 아키텍처 서술(사용자 본인의 공개 설명, 2026-07-13):
- 벡터DB(RAG) 대신 **Git 마크다운 위키** 선택 이유 3가지: 커밋 이력·git pull/push 동기화·옵시디언 등
  사람이 직접 열람/수정.
- 파일 역할: `AI_CONTEXT.md`(매 대화 주입 40줄 요약)·`index.md`(목차/능동 조회 진입)·
  `wiki/{sessions,entities,topics,skills}`·`raw/conversations`(원본 근거).
- 자동화: '기억에 저장' → `memory-ingest` 큐 → pull·raw 보관·문서 갱신·AI_CONTEXT 재증류·commit&push.
  **매일 새벽 5:30 launchd 크론**이 미저장 대화 자동 ingest, **주 1회 `memory-lint`**로 모순·고아 정리.
- **회수(recall) 3층**: (1) AI_CONTEXT.md 상시 주입, (2) index.md 기반 능동 조회 — Claude는 파일 도구,
  **로컬 LLM(Rapid-MLX)은 `search_memory`/`read_memory`/`list_memory` 읽기 전용 MCP 3도구**로 위키를
  직접 검색, (3) **위키 corpus 전체를 로컬 모델에 넘겨 요약을 스트리밍**하는 별도 API.

> ⚠️ 위 (2)·(3)은 사용자의 **공개 블로그 서술**이다. 이 위키의 [[long-term-memory-architecture]]는
> 2026-07-11~12 관찰에서 **방법 C(능동 조회 tool)를 "미완"**으로 기록했다. 블로그가 로컬 LLM 경로에
> 한정해 이미 구현됐음을 뜻하는지, 설계/지향의 서술인지는 **미검증** — 실제 채팅에서 조회가 동작하는지
> 재확인 필요. (모순 명시: 소스=사용자 블로그 2026-07-13 vs 관찰=2026-07-11/12 채팅.)

### 네이버 태그 SEO 원칙 (어시스턴트 정리)

- 태그 **최대 30개, 각 태그 공백 없이** 입력.
- **제목·본문에 실제 등장하는 핵심어**만 태그로 — 무관한 인기태그 남발은 **저품질 판정 위험**.
- **대표키워드(넓은 검색어) + 세부·롱테일(구체 롱테일)** 혼합이 유리. 브랜드/시리즈 태그(`람파스`,
  `llmwiki`)는 검색량 적어도 **연재 축적용**으로 고정.
- 추천 30개는 대표어 10 + 핵심주제어 10 + 롱테일 10으로 배분. → 절차는 [[naver-blog-tag-seo]] 스킬로 추출.
