# 2026-07-17 — nginx 스캐너 차단·정체 조사 세션

`[[progdesigner]]`가 서버 nginx access 로그에 찍힌 대량의 `.env`/`.git`/`phpinfo`류 정찰성 404 요청을
붙여넣고 "AWS 로 막든 서버로 막든" 차단 방법을 물은 2왕복 quick 채팅. 어시스턴트가 (1) Nginx 레벨
차단·rate limit·real IP 복원·AWS WAF 조합의 방어 전략, (2) 두 번째 질문에 스캐너의 정체(자동
취약점 스캐너/봇넷 vs 내부 인스턴스 스캔 가능성)를 답했다. 어느 프로젝트의 서버인지는 소스에
명시되지 않음 — [[lampas-harness]](맥미니 launchd)도 위키에 기록된 다른 AWS 기반 저장소
([[cwc-system]]·[[elevino-system]] 등)도 아닌, 이 세션에서 처음 등장하는 미상의 AWS EC2+Nginx
서버로 취급한다.

## 흐름 (2왕복)

1. **user**: nginx access 로그 30여 줄 붙여넣기 — 요청 IP `172.31.10.37`(AWS VPC 사설 대역) 단일
   출처, 모두 `404`. `.env`, `.ssh/public.crt`, `phpinfo.php`, `aws-secret.yaml`, `.git` 관련 등
   민감 경로/파일을 무작위로 탐색하는 패턴. User-Agent는 2016년식 구형 Chrome 56.0(위조로 추정).
2. **assistant** (1턴): 전부 404이므로 노출 정황은 없다고 진단한 뒤 방어 강화책을 5단계로 제시:
   - Nginx에서 dotfile·설정/백업 확장자·`.git`/`.svn`/`node_modules`·phpinfo류 경로를 정규식으로
     즉시 차단(`404` 권장, `444`는 디버깅 어려움 때문에 보류)
   - `limit_req_zone`/`limit_conn_zone`으로 IP당 요청 속도 제한
   - **핵심 경고**: `172.31.10.37`은 ALB/리버스프록시의 사설 IP일 가능성이 높으므로 이 IP 자체를
     Nginx에서 차단하면 정상 사용자까지 막힐 수 있음 — IP 차단 대신 `set_real_ip_from`
     +`X-Forwarded-For`로 실제 클라이언트 IP를 복원해야 rate limit·차단이 의미 있게 동작
   - EC2 Security Group 인바운드를 ALB SG로만 제한(0.0.0.0/0 공개 금지)
   - ALB/CloudFront에 AWS WAF Managed Rules(Common/KnownBadInputs/IPReputation/SQLi, 유료
     BotControl 옵션) + Rate-based rule(예: 5분당 1,000요청) 연결
   - 과거 access log(및 압축 로그)에서 해당 민감 경로가 `200/206/301/302`로 응답한 적 있는지
     `grep`/`zgrep`으로 반드시 재확인 — 있었다면 파일 제거+비밀키 전량 교체+Git 노출 정리까지 필요
3. **user**: "뭐가 이걸 하고 있는 걸까?" (정체 질문)
4. **assistant** (2턴): 네 가지 가설 제시 — (1) Nikto/OWASP ZAP류 자동 스캐너 또는 개인 스크립트,
   (2) 사이버 범죄 자동화(한국 서버가 보안의식 낮다는 가정으로 자주 표적), (3) Shodan/ZoomEye류
   인터넷 전수 인덱싱 봇, (4) **가장 위험한 케이스** — `172.31.10.37`이 VPC 사설 IP이므로 실제로는
   자신의 AWS 인프라 *내부*(다른 EC2/Lambda/ECS 또는 침투당한 인스턴스)에서 나온 요청일 가능성.
   `aws ec2 describe-instances`로 사설 IP를 인스턴스에 역매핑해 먼저 확인할 것을 권고하고, 아니라면
   Security Group을 즉시 좁히고 AWS Support에 신고하라고 조언. 사용자에게 "VPC 구성/EC2 목록/실제
   출처 중 뭘 확인하고 싶은지" 되물으며 소스 종료 — **후속 확인 여부는 미확인**.

## 핵심 관찰

- **가장 중요한 통찰은 IP 오인 함정**: `172.31.10.37` 같은 `172.16.0.0/12` 사설 대역 IP를 "공격자
  IP"로 착각해 Nginx에서 직접 차단하면 ALB를 거치는 정상 트래픽 전체가 막힌다. 실제 방어는 ALB/WAF
  레벨(공인 발신 IP 기준) + Nginx real IP 복원 후 rate limit 조합이어야 한다는 점을 명확히 함.
- 로그가 전부 404라는 사실만으로 "침해 없음"이라 단정하지 않고, 과거 로그에서 `200`류 응답이
  있었는지 별도로 검증하라고 못박은 점 — 표면적 안전 신호와 실제 노출 여부를 분리해서 판단.
- 두 번째 답변에서 "내부 인스턴스에서 나온 요청일 수 있다"는 가장 심각한 시나리오를 먼저 짚고
  `aws ec2 describe-instances`로 검증 가능한 다음 행동을 제시 — 확인 후속은 이 소스에 없음.
- 어느 프로젝트/서버인지 미상 — 다음에 같은 서버 언급이 나오면 이 세션과 연결하고 정체를 확정할 것.
