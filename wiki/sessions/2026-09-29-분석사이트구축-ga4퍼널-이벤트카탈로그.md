# 2026-09-29 — 분석 사이트 구축: GA4 퍼널 점검 + 이벤트 카탈로그 구글시트

`Tool: codex`, 작업 폴더 `lampas-system`(2026-09-29T20:02:29Z 시작) — 같은 날 33분 뒤 시작된
[[2026-09-29-posthog-구축-연동]](20:35:45Z)보다 **먼저** 있었던 세션. 하루 동안 같은 결제 전환
분석 문제를 GA4 경로로 먼저 조사하고, 뒤이은 세션에서 결국 PostHog로 해결한 순서가 이 두
세션에 나뉘어 기록돼 있다.

## 1. 크로스도메인 결제 퍼널 — 일반 설계 상담
"구글 애널리틱스처럼 다른 도메인에 걸친 모든 접속자의 결제까지 여정을 추적하고 싶다"는 질문에
일반적 설계를 제시:
- 퍼널 예시: 랜딩 방문 → 서비스 진입 → 회원가입 → 첫 생성 → 결제 페이지 진입 → 결제 완료.
- **GA4(도메인 간 측정) + 서버 저장 전환 이벤트** 조합 추천. 로그인 전 익명 방문자 ID → 로그인 후
  공통 사용자 ID로 연결, 결제 완료는 **성공 페이지 방문이 아니라 백엔드 결제 승인 확인 시점**
  기준(주문 ID로 중복 집계 방지).
- **100% 추적은 불가능**하다는 한계 명시(쿠키 거부·광고차단·기기 전환) — GA4는 유입 분석, 서버
  데이터는 가입·생성·결제 전환의 정확한 집계에 역할 분담.
- 이메일·전화번호는 GA4로 보내지 않음.

## 2. `first.dalar.ai → admin.first.dalar.ai` 퍼널 — 실태 조사
사용자 질문: "[[dalar-web-first]]의 결제까지 가는 여정을 `admin.first.dalar.ai`에서 볼 수
있나, 안 되면 GA4에서라도 수집이 잘 되고 있나?" 운영 사이트·저장소 코드를 직접 확인한 결과:

| 확인 항목 | 상태 |
|---|---|
| `first.dalar.ai` 방문·행동 추적 | 운영 HTML·JS에 GA4 태그·First 이벤트 **없음** |
| `pay.lampas.io/first` 결제 추적 | `begin_checkout`/`purchase` 구현은 있으나 **Lampas 속성**으로 전송(Dalar 속성 아님) |
| `admin.first.dalar.ai` | 사용자·주문·제작 상태 조회만 — 방문자 기반 퍼널 조회 기능 **없음** |
| 로컬 개선 코드 | First·결제를 **Dalar 같은 GA4 속성**으로 연결하는 코드가 **로컬에만 준비돼 운영 미반영** |

결론: 현재 구조로는 "First 접속자 중 결제 전환율"을 정확히 분석하기 어렵다. 관리자 화면의
"결제 완료" 숫자도 **`first_orders.paidAt` 존재 여부** 기준이라, 결제 사이트의 실제 승인 건수와
의미가 다를 수 있음을 지적.

### 개선 권고 (4단계, 이 세션에서는 실행하지 않음)
1. 로컬에 준비된 계측 코드를 운영에 반영(배포는 이 세션에서 실행 안 함, 로컬 계측 테스트 7개·
   HTML 설치 일치 검사는 통과).
2. 도메인 이동 시 동일 방문자 연결 검증 — Dalar 속성 `G-7R1C9BXKTX` + `dalar.ai ↔ lampas.io`
   linker, 결제 링크의 `_gl` 전달 확인, First·결제 앱에 로그인 사용자 공통 `user_id` 추가.
3. 실제 결제와 GA4 기록 대조 — `first_landing_view → first_checkout_view → first_begin_checkout
   → first_purchase` 순서 확인 + 실제 승인 주문 ID·금액과 GA4 구매 기록 비교. 서버 승인 시점
   전송 추가 시 중복 방지 설계 동반 필요.
4. 관리자에 "전환 분석" 화면 추가 — 백엔드가 **GA4 Data API**로 퍼널 보고서를 조회해 방문자 수·
   단계별 전환율·이탈률·유입 채널/기기 비교를 표시, 실매출은 결제 DB 기준으로 병기. **단계별
   이벤트 건수를 단순히 나누는 방식은 피해야 한다**(사용자 여정 퍼널과 다름).

**저장소 문서 참조**: [First GA4 퍼널 탐색](https://analytics.google.com/analytics/web/#/analysis/a402451861p547256216/edit/1ewF4tNmQ3-zrUbc41j_hw), 상세는 `lampas-system` 저장소
`docs/analytics/ga4.md`. "운영 계측부터 반영해야 새 퍼널 데이터가 쌓인다 — 수집 안 한 과거
여정은 소급 복원 불가"라는 점을 명시.

> **후속 사실**: 33분 뒤 시작된 [[2026-09-29-posthog-구축-연동]]에서는 위 4단계 권고(GA4 Data
> API 기반 관리자 전환 분석 화면)를 따르지 않고, **PostHog를 신규 도입**해 First 퍼널 분석을
> 해결했다. GA4 계측 자체는 유지된 채 PostHog가 그 위에 얹힌 구조가 됐다 — 이 세션의 권고안
> 4번 항목은 실행되지 않은 것으로 보임.

## 3. 이벤트 카탈로그를 구글 스프레드시트로 정리
사용자가 "지금까지 작업된 [GA] 이벤트들이 어떤 게 있는지 구글 스프레드시트에 저장"을 요청,
먼저 `lampas-harness`가 쓰는 서비스 계정 이메일을 물어 시트에 편집자로 초대:

```
lampas-crawler@lampas.iam.gserviceaccount.com
```

이후 지정 시트([링크](https://docs.google.com/spreadsheets/d/1VpbhftSjfFyKsPH7PvHfaBXBsua6Qb0bNx87uSaZbx4/edit))에
`lampas-system` 저장소 전체의 GA 이벤트를 조사해 저장:

- **코드에서 106개 이벤트명 발견**, 앱별로 나누면 **382개 정의**(같은 이벤트명이 여러 앱에서
  각각 정의됨).
- 시트 구성(여러 탭): `GA 이벤트`(발생 조건·파라미터·코드 위치), 앱별 계측 상태, First 퍼널,
  동적 이벤트 검토, GA 자동 이벤트, 관리 안내.
- `GA 이벤트` 탭에 **수집 상태·담당자·검증일·메모**를 드롭다운/자유 입력으로 관리.
- **재동기화 커맨드 추가**: `pnpm analytics:catalog:sync` — 코드 재스캔 후 시트를 다시 써도
  사람이 입력한 담당자·검증일·메모 열은 보존되도록 설계. 코드 구현 여부와 운영 실제 수신 여부를
  별도 열로 구분해 표시.
- 결과를 다시 읽어 저장 내용을 검증 완료. 현재 목록은 **코드 기준 이벤트 정의**이며 실제 운영
  수신 여부는 이 세션에서 따로 확인하지 않고 열만 분리해둠.
