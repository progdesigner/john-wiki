## 1. Copy 스크롤 버그 수정 → [[lampas-web-copy]] v0.2.6

첨부 화면: 카피 화면의 페르소나/클립 목록 내용이 길어지면 화면 오른쪽으로 계속 밀려나가고 스크롤이
나타나지 않음. 원인은 목록 자체엔 가로 스크롤 설정이 있었지만 **바깥 `fieldset`이 카드 전체 너비만큼
늘어나 스크롤이 생기지 않는 구조**였음 — 스크롤 컨테이너의 너비가 콘텐츠에 종속돼 넘침을 못 잡는
전형적 레이아웃 버그. 바깥 영역 너비를 제한하고 긴 페르소나 설명도 영역 안에서 줄바꿈되도록 수정.
테스트 32개·프로덕션 빌드 통과 후 배포.

## 2. Fixs 작업 삭제 기능 → [[lampas-agent]] Fixs 탭, v1.0.22

`https://lampas-system.tail0e32ab.ts.net/fixs`에 쌓인 작업을 화면에서 삭제할 수 있게 해달라는 요청.
작업 상세에 **"작업 삭제"** 버튼 추가 — 대기·완료·실패 상태는 바로 삭제 가능, **실행 중인 작업은 취소가
끝난 뒤에만 삭제**하도록 순서를 강제. 삭제 API 인증, 실행 중 삭제 차단, 대기열 제거, 삭제한 작업이
자동 새로고침으로 되살아나지 않는지까지 검증. 테스트 398개·타입 검사 통과 후 배포, 버전 `1.0.22` 정상
응답 확인.

이 시점의 Fixs는 이후 저녁 세션([[2026-09-25-fixs-업그레이드-경로묶음-jev분류]], v1.0.25)이 추가한
경로 그룹핑(fingerprint)·Jev 오류 분류보다 **먼저** 존재했던 상태 — 버전 흐름은 아래 "버전 이력" 참고.

## 3. Tools(`tools.lampas.io`) 업로드 오류 수정 → v0.1.2

첨부 화면: 업로드는 성공했는데 화면이 실패로 표시. 원인은 업로드 응답에서 파일 주소를 읽는 코드가
서버가 실제로 주는 **`download_url`** 필드 형식을 인식하지 못해 성공을 실패로 오판하던 것. 해당 응답
형식을 지원하도록 수정 — **같은 업로드 코드를 오디오·비디오 입력도 공유**하므로 세 입력 모두에 적용됨.
테스트 39개·타입 검사 통과 후 배포(v0.1.2). "실제 유료 영상 생성까지는 검증하지 않았다"고 명시적으로
한계를 밝힘 — 바로 다음 요청에서 그 미검증 지점이 실제 문제로 드러남(아래 5절).

## 4. Tools 모델 표시 + 생성 거절 처리 + 전체 오류수집 확장 → v0.1.3 / Fixs 에이전트 v1.0.23

한 요청 안에 세 가지가 섞여 들어옴 — ① tools.lampas.io 각 기능에 실제 사용 모델을 모두 표시, ②
여전히 나는 생성 오류 재조사, ③ **모든 프로젝트**의 프론트 오류를 Fixs로 보낼 수 있게.

- **생성 거절 진단**: 운영 로그 확인 결과 업로드는 통과했고, **Kling 모델이 `Failure to pass the risk
  control system`으로 생성을 거절**한 것 — 공급자 측 콘텐츠 심사 거절이며 응답에 구체적 거절 사유는
  없음. 클라이언트 코드로 거절 자체를 해제할 수는 없다고 명시. 대신 ⓐ 거절 사유가 사라지는 토스트가
  아니라 **결과 영역에 계속 남도록** 표시, ⓑ 실패 응답을 계속 대기(로딩 고착)하던 처리를 수정.
- **모델 표시**: 13개 기능 전체의 목록·상세 화면에 실제 실행 모델을 노출, 여러 모델을 단계적으로 쓰는
  기능은 단계별로 보이게 함. 브라우저에서 13개 기능 모두 확인.
- **전체 오류수집 확장** — 기존 공통 Fixs 수집기는 **HTTP 500 이상만** 감지해 이번 400 오류를 놓쳤던
  것이 재조사 중 드러남. 400대 응답·네트워크 오류·콘솔 오류까지 수집하도록 코드 확장, "기능 변경과
  수집 코드 변경을 같은 배포에 섞지 않도록" 배포 스크립트에 수집 코드만 갱신하는 경로를 별도로 추가.
  **웹 프론트 36개**(코드 소스 연결 완료 + 33개 실제 재배포, 나머지 3개는 소스만 반영) + **토스
  미니앱 2개**(소스 반영만, 배포는 별도 남음)에 반영. Kling 거절 응답을 재현해 오류 안내가 화면에
  남고 Fixs 보고가 실제로 발생하는 것, Fixs 서버에 리포트가 저장되는 것까지 확인.
- 배포: Tools v0.1.3, Fixs 에이전트 v1.0.23.

## 5. 영상 생성 결과가 안 보임 — 2단계 오진 끝에 S3 직접재생으로 근본 수정

### 1차 진단·수정 (→ v0.1.4, 근본 원인 아니었음)
"생성된게 안 나와" 신고. 조사 결과 **영상 생성 자체는 성공**했으나, 화면이 존재하지 않는
`/v1/ai/media` 주소로 영상을 요청해 **404**가 발생 — "생성 실패"로 보였지만 실제로는 **재생 주소
버그**였다. 원본 영상 주소는 정상 응답함을 확인. 원본 주소로 재생하도록 수정하고, 이미 생성된
12.27초 영상을 **다시 생성할 필요 없이** 복원해서 보여주도록 처리. 실제 브라우저에서 그 영상 재생까지
확인 후 배포(v0.1.4). "이전 검증에서 실제 영상 재생까지 확인하지 못했다"고 3절의 한계를 스스로 재확인.

### 2차 신고 — 여전히 재발
사용자: "여전히 생성하면 영상이 안 나온다." v0.1.4가 **기존 저장된 영상의 재생**은 고쳤지만 **새로
생성하는 영상**의 재생 경로는 여전히 안 됐다는 뜻 — 증상이 같아 보여도 원인 범위가 달랐던 사례.

### 사용자 지시 — 프록시 대신 S3 직접 재생
사용자가 구체적으로 지시: **"s3 업로드 해서 보일 수 있게 해라 api 연결해서 보이게 하지 말고."** 즉
API 미디어 프록시 경유가 아니라 S3에 저장하고 CloudFront 주소로 직접 재생하라는 아키텍처 지정.

### 근본 원인 3건
1. 새로 생성한 영상은 **이미 S3에 저장돼 있었고 CloudFront 원본도 정상**이었는데, 재생 실패 로그는
   계속 **이전 화면 코드의 `/v1/ai/media` 요청**을 가리키고 있었음 — 즉 프론트 배포/캐시가 새 코드로
   안 갈아탄 상태로 재현되고 있었을 가능성.
2. 일부 **임시 영상 주소가 S3 저장 대상에서 누락**되는 경로가 있었음(전부는 아님).
3. S3 저장이 **실패**하면 임시 주소를 그대로 반환해 버리던 처리 — 저장 성공 여부와 무관하게 "일단
   응답은 보낸다"는 관성적 설계가 실패를 숨김.

### 수정
- S3 저장 대상 누락 케이스를 막고, **저장이 끝난 주소만** 반환하도록 변경(3의 관성적 폴백 제거).
- 기존에 이전 프록시 형식으로 남아있던 저장 기록을 파일(CloudFront) 주소로 복원.
- HTML 캐시가 이전 코드를 계속 서빙하지 않도록 배포 설정 수정.
- 결과: **S3 저장 → CloudFront 주소 직접 재생**, API 미디어 프록시는 더 이상 쓰지 않음. 운영 화면에서
  기존 12.27초 영상의 실제 재생을 다시 확인.
- 사용자에게 **강력 새로고침(⌘⇧R)**을 요청 — "다시 생성할 필요는 없다"고 안내하며 기존 영상의
  CloudFront 직링크를 제공.

**⚠️ 세션 로그가 여기서 끝나 새로 생성한 영상이 실제로 화면에 보이는지는 이 소스로 확인되지 않는다.**
같은 증상이 v0.1.4 배포 후에도 재발했던 전례(위 "2차 신고")가 있어, 이번 S3 직접재생 수정이
최종 해결인지 다음 세션에서 재확인 필요.
