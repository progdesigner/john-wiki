# 2026-09-26~27 — 브랜딩(위키 기반 Threads 글 생성) 기능 구축 + 로컬 LLM JSON 검증 버그 2라운드 수정

`Tool: codex` 터미널 세션(작업 폴더 처음엔 `lampas-system`, 사용자 지시로 **상위 폴더
`[[lampas-harness]]`로 변경**). [[2026-09-26-threads기능제거-llm위키탐색기-apps-wiki-이전]]에서
`[[lampas-agent]]` 쪽 Threads 글 자동생성 기능이 **전면 취소**된 바로 다음 날(또는 같은 날 늦게),
같은 아이디어가 **lampas-harness 자체의 "브랜딩" 기능으로 독립적으로 재등장**한 세션 — 소스에는
두 사건의 직접적 인과관계가 적혀 있지 않아 "같은 요구가 다른 곳에서 다시 나타났다" 정도로만 기록.

## 1. `branding.html` 최초 구현

- 요청: "하네스에 설정 아래 위키 버튼 아래에 **브랜딩**이라는 기능을 추가해서 내 위키 정보를 바탕으로
  기술적으로 AI와 관련해서 사람들에게 **Threads**로 공유할 수 있는 콘텐츠를 생성할 수 있는
  `branding.html`을 만들어주고 버튼을 연결해줘."
- 구현: `[[lampas-harness]]`의 **위키 조회 API**([[2026-09-26-threads기능제거-llm위키탐색기-apps-wiki-이전]]가
  연결한 `[[john-wiki]]` 데이터 소스)와 **로컬 AI 모델**([[rapid-mlx]])을 재사용. 흐름:
  1. 위키 문서 선택(근거 문서 확인 가능)
  2. 말투·글 형식 선택 — **단일 글** 또는 **3편 연속 글(스레드)**
  3. AI가 초안 생성 → 편집 가능
  4. 500자 표시(Threads 글자 수 기준으로 추정) → 복사 → Threads 작성창 연결
- 검증: 타입체크·빌드·관련 테스트 4개 통과. 브라우저에서 모의(mock) AI 응답으로 단일/연속 글 생성,
  500자 초과 처리, 모바일 레이아웃 확인.
- **설정(⚙) → 위키 버튼 바로 아래 "브랜딩" 버튼**으로 연결, 생성에는 로컬 AI 모델(rapid-mlx) 사용.
- 배포는 다른 대화의 작업 큐가 빌 때까지 지연됐다가(재시작 시 진행 중 턴이 끊기는 함정 —
  [[self-hosted-agent-server-ops]]), 사용자가 "재시작해"로 명시 요청해 반영.

## 2. 실제 로컬 모델로 돌리자 두 가지 버그 연쇄 발생

### 2-1. 추론 토큰이 본문 작성 전 출력 예산을 소진 (1차 수정)
- 증상: 첨부 이미지로 "AI 응답을 게시물 형식으로 해석 못함" 오류 재현.
- 원인: 로컬 모델이 **추론형 Qwen**(`[[local-llm-rapidmlx-install]]`의 `qwen3.5-35b`)이라, 사고
  과정이 실제 게시물 본문을 쓰기 전에 출력 토큰 한도를 먼저 소진할 수 있다는 것을 의심·확인 —
  Gemini에서 이미 관찰된 **사고 토큰이 maxTokens를 잠식하는 함정**과 같은 계열의 증상이 로컬 모델
  에서도 재현됨 → [[gemini-thinking-tokens-eat-maxtokens-budget]] (이 세션 사례로 공급자 범위 확장).
- 수정: **추론(reasoning) 출력을 끄고**, JSON 앞뒤에 설명 문구가 붙어도 읽어낼 수 있게 파서를
  관대하게 바꾸고, 형식 검증 실패 시 **한 번 자동 재시도**하는 방어선 추가.
- 검증: 같은 위키 문서·같은 요청으로 실제 로컬 모델을 호출해 **430자 초안**이 정상 생성됨을 확인.

### 2-2. 500자 넘으면 결과를 숨기던 문제 (UX 수정)
- 사용자 요청: "500자를 지키지 않아도 결과가 나오게 해줘" (첨부 이미지로 500자 초과 시 결과가
  안 보이던 증상 제보).
- 수정: 500자 초과도 **항상 결과를 표시**하도록 변경. 글자 수는 **참고용 표시로만** 남기고, 그
  길이와 무관하게 편집·복사·Threads 작성창 열기가 모두 가능하게 함.

### 2-3. 엄격한 JSON 스키마 검증 자체가 버그였다 (근본 원인 규명, 2차 수정)
- 사용자 재제보(다음 날, 2026-09-27): "여전히 작성을 못해주고 있다."
- 진단: 실제 브랜딩 API에 요청을 보내 실패 응답을 재현. **로그에서 원인 확정** — 모델은 **게시물
  본문을 정상적으로 생성**하고 있었는데, 서버가 `note` 필드 누락이나 `posts`가 배열이 아니라 문자열
  이라는 이유로 **결과 자체를 거부**하고 있었다. 즉 "로컬 서버가 제공하는 JSON 스키마 검증 기능"을
  2-1 수정 때 도입한 것이 **의도와 반대로 문제를 더 키운 것**(본문이 없는 게 아니라, 본문이 있는데
  부가 필드·타입 때문에 버려지고 있었음).
- 2차 수정: 게시물 본문을 **일반 텍스트로 받아 그대로 표시**(구조화 JSON 필드 강제 대신). 연속 글은
  구분선으로 나누고, **글 수나 500자 초과를 이유로 생성된 본문 자체를 버리지 않는다**는 원칙으로
  전환 — 스키마 적합성보다 "본문이 실제로 생성됐는가"를 우선하는 쪽으로 검증 기준을 완화.
- → 재사용 절차 스킬 추출: [[strict-json-schema-rejects-usable-llm-output]]

## 왜 중요한가 (사서 메모)

- **"Threads 기능"이 한 번 취소됐다가 다른 위치에서 다시 등장했다.** [[lampas-agent]]에서 취소된
  기능(위키 기반 Threads 글 생성)과 이 세션의 `branding.html`은 **목표가 거의 동일**하지만(위키 기반
  Threads 콘텐츠 생성), **구현 위치가 다르다**(lampas-agent → lampas-harness) — 같은 요구가 "취소"
  로 끝나지 않고 다른 자리에서 재구현된 사례. 두 사건의 직접적 승계 관계(사용자가 원래 요청을 여기로
  옮긴 것인지, 완전히 새로 낸 요청인지)는 소스만으로 **확정 불가**.
- **엄격한 검증이 가용성보다 우선시되면 안 된다는 교훈**이 이 세션의 핵심. 첫 수정에서 "JSON 스키마를
  강제하면 품질이 보장된다"는 가정으로 검증을 추가했는데, 실제로는 **모델이 맞게 생성한 본문을
  부차적 형식 불일치로 폐기**하는 역효과를 냈다. [[gemini-thinking-tokens-eat-maxtokens-budget]]과
  달리 이번엔 "토큰이 모자라서"가 아니라 "검증이 너무 엄격해서" 생긴 실패라는 점에서 구분되는 별개
  함정.
- 작업 폴더를 `lampas-system`에서 `[[lampas-harness]]`로 바꾼 전환이 이 세션 첫머리에 있다 — AGENTS.md
  로 주입된 `lampas-system`(=[[lampas-studio]]) 저장소 구조 설명은 이 세션의 실제 작업 대상이 아니라
  **직전 컨텍스트 잔재**였다는 점에 유의(세션 요약에 lampas-system 구조를 끌어오면 안 됨).
