# 2026-09-25 스포츠 위키 "경기(game)" 엔티티 설계·구현·배포

`Tool: claude`, 작업 폴더 `lampas-system`, 2026-09-25T22:11 시작 (다음날 새벽까지 이어짐).
소스: `raw/conversations/2026-09-25-위키개선-스포츠경기엔티티-설계.md`.

이 세션에서 처음으로 [[lampas-agent]](스포츠 클립 처리 맥미니 로컬 데몬)와 `lampas-api`의
"스포츠 위키" 모듈이 위키에 노출됨. **`[[lampas]]`(하네스 에이전트 이름)와 `lampas-agent`(제품 앱)는
전혀 다른 대상**이므로 혼동 주의 — 상세는 [[lampas-agent]] 상단 disambiguation 참고.

## 문제 제기
`[[progdesigner]]`: "agent 에서 클립을 만들고 나면 왜 wiki 데이터는 쌓이지 않지? 어떤 선수가 어떤
경기를 하고 어떤 팀이 어떤 승리를 만들어내는 지 쌓고 싶은데."

## 진단 (1차 조사)
운영 뱅크(`api.lampas.io`) 실측: 09-03~09-24 스포츠 클립 소스 15건 중 위키 소스로 들어간 것 6건,
그중 실제 페이지가 만들어진 것 3건. 경기 페이지는 **0건**(그런 타입 자체가 없음). 원인 세 가지:

1. **실패가 성공으로 보임** — `runWikiStage`(`runIngestPipeline.ts:422`)가 ingest 실패를
   `console.warn`으로 삼키고 `false`를 반환하는데, 바깥 `stage('wiki')`는 예외가 없어 UI엔 "완료"로
   표시. 재시도 진입점 없음. NBA 해설 영상은 클립 설명 나열이 17k~39k자라 12k에서 잘리고
   `gemini-3.5-flash`가 JSON 대신 프로즈나 잘린 응답을 냄.
2. **요청 자체가 안 간 소스** — `DomainCategoryPicker.tsx:62`가 `category?.key`를 넘기는데 카테고리
   목록 로드 전에 고르면 `undefined`가 되어 `runWikiStage` 첫 줄 `if (!categoryKey) return true`로
   조용히 스킵. 재업로드는 `wikiDone`이 이미 true라 다시 안 감.
3. **구조적으로 "경기"가 없음** — `sports-wiki-types.ts`의 `pageType`이 `player | team`뿐. 에이전트가
   보내는 소스 텍스트(`wikiIngestText.ts`)는 "선수: X / 클립 설명 / 점수" 나열이라 날짜·상대·스코어·
   승패는 영상 제목에서 우연히만 유추됨.

## 설계 결정 — "저장 위치"가 아니라 "역할 분리"
`[[progdesigner]]`가 "에이전트 전용 위키를 따로 만드는 게 나을까?"라고 재질문하자, 어시스턴트가
**반대**하고 세 번째 안을 제시·채택:

- 위키(저장·유지)는 지금처럼 `lampas-api`에 둔다 — 에이전트 로컬 SQLite에 두면 [[lampas-web-copy]]가
  카피 생성 프롬프트에 위키를 못 읽고, 에이전트가 꺼지면 데이터가 사라짐.
- **[[lampas-agent]]는 "위키를 만드는" 대신 "경기 사실을 구조화해서 보내는" 역할**로 좁힌다 — 라벨링
  배치에서 이미 비전 호출을 하므로 같은 호출에 경기 컨텍스트(날짜·양팀·이닝별/최종 스코어·승리팀·
  결정적 장면과 관련 선수)를 JSON으로 함께 뽑는다.
- **`lampas-api`가 경기 행을 결정적으로(LLM 없이) 저장**한다. 선수·구단 페이지의 "최근 경기" 절은
  코드가 병합하고, 서사 요약만 짧은 JSON 모드 호출로 다듬는다 — 모델이 절을 지워도 코드가 되살림.
  → 재사용 패턴: [[deterministic-extraction-vs-llm-rewrite]]
- Copy·Reels는 API로 클립 id → 경기·선수·구단 페이지 조회를 받아 카피 근거에 경기 사실 한 줄을 넣는다.
- 실패는 잡 카드에 경고로 노출 + 재시도 버튼, `categoryKey` 없는 스포츠 잡은 생성 단계에서 차단.

## 구현·배포 (같은 세션, 사용자 승인 후 진행)
- `lampas-api`: `sports-wiki`에 `game` 엔티티 추가. `POST /v1/sports-wiki/games`(LLM 없이 결정적
  저장), `GET /games`, 클립 단위 `GET /context?clipId=`. Prisma 모델+수동 DDL, 서비스·컨트롤러·DTO.
  API 테스트 24건.
- [[lampas-agent]]: 위키 단계 재구성 — 라벨링 뒤 스코어보드 키프레임과 라벨을 같은 배치로 보내 경기
  JSON 추출 → 업로드 뒤 소스 id와 함께 서버 반영, 실패 사유는 체크포인트에 남겨 잡 카드 경고+재시도
  버튼. 카테고리 키 없으면 id로 복구하거나 실패 기록, 스포츠인데 카테고리 미선택이면 큐 진입 차단.
  해설·분석 영상은 기존 prose ingest 유지. 에이전트 테스트 62건.
- [[lampas-web-copy]]: 클립이 속한 경기 맥락을 카피 프롬프트 끝에 추가 + 결과 상단 "이 클립의 경기"
  한 줄 표시. 테스트 38건.
- **운영 반영**: 운영 DB 경기 테이블 DDL 적용, `lampas-api` 0.1.145(재시작 0회), `lampas-agent` 1.0.27
  데몬 재기동, `lampas-web-copy` S3·CloudFront 배포, git 커밋 `9f8ba175` push.
- **같이 처리한 다른 세션 작업**: (1) 다른 세션이 만든 상태 페이지 모듈 DDL을 크래시 루프 방지 위해
  선반영(상태 프로브 스케줄러 가동 시작, 웹 자체는 CloudFront 없어 미배포). (2)
  `apps/lampas-agent/env/.env.local`은 라이브 파트너 API 키가 추가된 변경분이라 커밋에서 제외(원격
  업로드는 되돌릴 수 없다는 이유로 사용자 판단 유보) → [[secrets-plaintext-exposure-pattern]] 계열
  주의와 유사하나 이번엔 "커밋하지 않고 보류"로 사고를 막은 사례.

Threads 탭이 섞여 있어** 빌드된 화면에 Clips·Pulse·Threads·Fixs 4탭이 실림. 1분 뒤(07:41) 그 세션이
Threads를 소스에서 제거했지만 데몬은 이미 07:40 빌드를 서빙 중이라 브라우저엔 Threads가 남아 있었던
것 — 재시작 실패가 아니라 **두 세션이 몇 분 간격으로 같은 앱을 배포하며 서로의 중간 상태가 섞인 것**.
