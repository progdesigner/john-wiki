## 라운드 1 — 현재 구조 진단 + 1차 계획
현재 구조 확인 결과:
- 맥미니 `launchd` 데몬 + SQLite 작업 원장(스케줄·재시도·리스·재시작 복구)은 이미 있음 — 재사용 가능.
- **문제점 4가지**: ① 재생목록 조회가 **최대 200개**만 반환, ② Clips 영상 처리·체크포인트가
  **브라우저**(OPFS)에 있어 창을 닫으면 끊김, ③ 유튜브 다운로드 작업 상태가 **메모리**에만 있고
  임시 파일 수명 1시간, ④ 클립 뱅크 등록에 **영구적인 중복 방지 키가 없음**.
- 맥미니 시스템 잠자기가 **1분**으로 설정돼 있어 매시간 무인 실행을 위해선 잠자기 방지 설정도 필요.

1차 계획(6단계): 플레이리스트 구독 등록(URL·계정·저장대상·범위·확인간격 기본 1시간) → 목록감시/
처리큐 분리(매시간 전체 조회, 미수집만 큐잉, 긴 처리 중에도 감시는 계속, 겹치는 확인은 합침) →
영상ID 기준 영구 중복방지(저장대상+계정+YouTube ID, 발견/대기/진행/완료/실패 상태 구분, 뱅크 API
멱등키) → 서버 파이프라인 이전(다운로드→보관→장면분할/썸네일→전사/라벨링→뱅크등록, 동시 1개 시작) →
무인 운영/복구(리스 만료 복구, 백오프 재시도, 비공개/삭제 영상 처리, 디스크/확인시각/대기수 표시) →
검증(신규영상감지·중복생략·200개 초과·브라우저종료·데몬재시작·뱅크직후연결끊김·24h 연속운영).

새 앱이 아니라 **`lampas-agent/src/server` 아래에 구독·감시·처리 모듈 추가**하는 확장 방향 권고.
이 라운드는 **계획만 정리, 코드·설정 변경 없음**을 명시.

## 라운드 2 — 사용자 6개 조건 반영 (개별등록·분리·ID기준·4번 재검토 요청·무인운영 필수·검증 필수)
사용자 지시: "1.개별 영상 등록도 만들어라 2.응 분리해 3.id 기준, 파일업로드는 잠시 제거(중복 ID
재수집은 기존처럼 새 소스로) 4.서버 파이프라인이 정말 더 빠르고 효과적인지 다시 확인해 5.무인운영/복구
필수 6.검증 필수 — **4번만 다시 확인해 알려주고 나머지는 적용해서 계획 다시 달라**."

**4번 재확인 결과 — 네이티브 FFmpeg 처리가 더 낫다고 결론**: 맥미니가 **M4 Pro·64GB RAM**이고 네이티브
FFmpeg 설치돼 있음을 확인.
| 처리 | 현재(브라우저) | 변경(맥미니 네이티브) |
|---|---|---|
| 원본 전달 | 맥미니→S3→브라우저 수신 | 맥미니 파일 직접 처리 |
| 장면 감지 | 프레임마다 시킹+Canvas 비교 | FFmpeg 순차 디코딩·프레임 분석 |
| 썸네일 | 반복 시킹 | 필요 프레임 묶어 추출 |
| 오디오 추출 | FFmpeg WASM 직렬 | 네이티브 FFmpeg |
| 전사·라벨 | 외부 API | 그대로(서버 이전만으론 안 빨라짐, 외부 API·업로드 속도에 종속) |

핵심은 "브라우저 원본 재수신 제거 + 반복 시킹/WASM 처리 축소". **정확한 속도 개선폭은 미측정** —
단계별 시간·메모리·분할 품질을 비교하고 장면 감지 기준은 먼저 유지해 품질 저하를 막겠다고 명시.

수정 계획 6단계 상세화:
1. 개별 URL 즉시 큐 + 플레이리스트 URL은 구독(1시간 폴링, 기존영상 포함여부 설정). 파일 업로드
   UI는 화면·신규 등록 경로에서 **잠시 제거**(기존 파일 기반 소스·클립은 보존).
2. 감시기(새 영상ID만 기록·작업등록)와 처리워커(다운로드~뱅크등록) 분리. 200개 제한 보완.
3. **자동 중복방지 vs 명시적 재수집 구분표**: 구독에서 이미 처리한 ID → 자동 생략 / 같은 계정·
   저장대상 여러 구독에 동일 ID → 수집작업 하나로 연결 / 사용자가 개별등록·재수집 선택 →
   **새 소스·새 클립 생성** / 실패·재시작 재시도 → 기존 작업 이어서 실행. 즉 **영상 ID=자동수집
   이력 판단용, 작업 ID=재시도 중복방지용**으로 역할 분리, 영상 ID 자체엔 소스 생성 금지 제약을
   걸지 않음.
4. 맥미니 서버 파이프라인 통합(개별등록/구독감시→영속 작업큐→다운로드→장면분석/썸네일/오디오→
   전사/라벨링→보관/뱅크등록). 브라우저는 등록·진행확인·취소·재시도만. 기존 "원본 1개+구간
   메타데이터" 가상 클립 방식 유지. 동시 1개로 시작.
5. SQLite에 구독·작업·단계별 체크포인트, 재시작 시 미완료 단계부터 재개. 백오프 재시도, 인증
   만료/크레딧부족/접근불가 사유 표시. 장기실행 서버 인증, 디스크 관리, 잠자기 방지, 재부팅 후
   실행조건까지 포함.
6. 배포 조건: 기능·복구·성능 검증(신규감지·중복생략·수동재수집·200개초과·브라우저종료·처리중
   프로세스종료·저장직후 응답유실) + 기존·신규 처리 품질·속도 비교 + **24시간 이상 연속 운영** 검증.

구현 순서: **작업·구독 모델 → 감시/처리 분리 → 네이티브 파이프라인 → 등록 화면 → 복구·인증 →
성능·연속운영 검증**.

사용자: "이렇게 구축해서 다시 lampas-system 하네스를 재구축해줘." (≈19:25 KST로 추정 —

어시스턴트: 합의한 구조로 구축 착수를 선언 — 먼저 현재 변경사항·하네스 연결지점 확인 후 서버
작업큐·플레이리스트 감시·네이티브 처리·관리화면을 연결, 맥미니 배포·복구 검증까지 진행하겠다고 응답.
이어서 중복 처리를 **두 층**으로 구현하겠다고 재확인: 구독은 영상 ID로 자동 중복 방지, 수동
재수집은 새 작업 ID 발급해 별도 소스·클립 생성. 서버 파이프라인은 **기존 장면분할·전사·라벨 해석
로직을 공유**해 결과 형식을 유지하고, 파일 처리만 네이티브 FFmpeg로 교체하겠다고 설명 — 이 설명이
교차 확인 세션이 발견한 실제 구현 1단계(`apps/lampas-agent/src/shared/ingest/` 신규, 브라우저
`web/lib` 순수 로직 서버 공유화)와 정확히 일치한다.
