# lampas-agent (스포츠 클립 에이전트)

`apps/lampas-agent` — `[[lampas-studio]]` 저장소(`lampas-system`) 내 앱. **스포츠 경기 영상을 클립으로
잘라 라벨링·업로드하는 맥미니 로컬 데몬**. 2026-09-25 세션에서 위키에 처음 노출됨.

> ⚠️ **이름 충돌 주의**: 이 "에이전트"는 `[[lampas]]`(하네스에서 코딩·업무를 돕는 Claude 기반 어시스턴트,
> `[[lampas-harness]]`에서 구동)와 **완전히 다른 대상**이다. `lampas-agent`는 `[[lampas-studio]]` 제품군의
> 한 구성 앱(코드명이 우연히 "agent"일 뿐 별도 자동화 프로세스이며, 대화형 AI 어시스턴트가 아니다) —
> 소스 대화에서 "에이전트"라는 말이 두 대상을 가리키며 섞여 쓰이므로 향후 ingest 시 문맥으로 구분할 것.

  [[lampas-agent]]가 Clips·Pulse 탭과 함께 이미 등장한다 → 아래 "Clips — 유튜브 재생목록 다중선택"·

## 최초 노출 시점 재정정 — 2026-09-18 (2026-09-26 뒤늦게 ingest)
위 "관찰된 구조" 절이 기록한 최초 노출 시점(09-20→09-19로 한 차례 정정됨)이 다시 하루 당겨진다.
2026-09-18 세션([[2026-09-18-lampas-agent-omnara분석-durable-run구현]])에서 원격 12개 커밋을
fast-forward로 받는 과정에 **`lampas-agent-clips` + `lampas-agent-pulse`(별도 두 앱) →
`apps/lampas-agent`(단일 앱) 병합**이 확인됐다 — 즉 `apps/lampas-agent`는 이 세션 시점 **직전까지
두 개로 분리된 앱**이었다가 막 하나로 합쳐진 상태였다. launchd 라벨도 이때 `io.lampas.agent.daemon`으로
바뀌었다. 같은 세션에서 daemon이 **v1.0.1**로 재배포됐다는 기록이 있어, 아래 "버전 이력"의 최초 확인
버전 1.0.16보다 앞선 최초 버전 지점을 채운다.

이 세션은 [[omnara]](외부 durable-agent 런타임)와의 비교 분석을 근거로 SQLite 잡 원장·워커 루프·
`/pulse/ws` 접근 토큰 게이트·AI 결정 단계(`pulse/ai/gateway.ts`의 `AiBudget`)를 구현·배포했다 —
`AiBudget`은 이틀 뒤 [[lampas-system-ai-call-architecture-audit]](09-20)가 "저장소 전체에서 유일하게
잘 짜인 AI 클라이언트"로 지목한 바로 그 모듈이라 생존이 교차 확인된다. 반면 SQLite 잡 원장·워커
루프·접근 토큰 게이트는 이후 09-19·09-20 세션 요약에 언급이 없어 **존속 여부가 미확인** 상태다 —

## 접속 주소 origin story — Tailscale Funnel 마라톤 (2026-09-13~15)
위 절이 다루는 시기 바로 다음날, `lampas-agent-clips`(당시 독립 앱, 로컬 포트 7452)를 여러 Tailscale
주소로 옮겨 다니며 최종 주소를 확정한 사흘짜리 세션이 있었다 — 지금까지 위키 여러 곳에 "접속 주소
`https://lampas-system.tail0e32ab.ts.net`"으로만 인용되던 것의 **유래**가 이 세션이다.

- 시작 주소 `progdesigner-mac-mini.tail43b73a.ts.net:8443`이 실은 **노드 자체가 테일넷에서 삭제된
  상태**(`404 node not found`)라 로컬 설정과 무관하게 접속 불가였음 — "연결됐습니다"라고 먼저
  보고했다가 로컬 확인만으로 판단한 오답임을 뒤늦게 정정한 사례.

## 훅 점수 — 절대 점수에서 상대 순위로 전환 (2026-09-19)
"종합적으로 후킹한 영상을 찾는다"는 목표에서 비전 라벨링이 매 실행마다 다른 훅 점수(0~100)를 내고
단독 재채점 시 낮게 나오는 문제를 진단·해결. 원인은 temperature 미지정, 점수 기준선(anchor) 부재,
점수를 이유보다 먼저 쓰는 JSON 순서, 배치 내 상대 비교로 인한 대비 효과(단독 채점 시 비교 대상이
없어 저평가) 등 다섯 가지였다. **아래 "4축 점수"는 바로 하루 전날
[[2026-09-18-lampas-clip-intelligence-brand-kit-대량구현]] 세션이 AI Clip Intelligence 기능의
일환으로 비전 라벨링에 갓 추가한 것 — 즉 이 절이 기록하는 조치는 그 신규 기능을 하루 만에 되돌린
것이다. 목적이 절대값이 아니라 순위이므로, 1단계(에이전트 1.0.12)에서 비전
라벨 프롬프트의 훅·4축 점수를 제거하고 temperature 0으로 고정, 2단계(API 0.1.108)에서 새 엔드포인트
`POST /v1/clip-intelligence/rank-hooks`가 설명·발화·전사 **텍스트만으로**(이미지 0장) 클립을 40개씩
조각 비교→상위군 재비교해 소스 내 백분위를 `Clip.hookScore`에 되쓰도록 구현·배포. 클립 100개 기준
호출 3~5회·1분 안에 완료. 뱅크의 4축 미니 바는 이후 라벨링이 아니라 reels의 AI 선별(`analyze`)이
채움. 이 "상대 순위 vs 절대 점수" 진단·전환 절차는 일반화해 스킬로 추출 →
[[llm-relative-ranking-vs-absolute-scoring]]. 이미 올라간 소스의 순위 재계산은 세션 종료 시점까지
web-clips에 버튼이 없어 소스 id로 직접 호출해야 하는 상태로 남음. 상세 →
[[2026-09-19-lampas-agent-clips재생목록-pulse로그인수집-훅점수상대순위]].

## Fixs 탭 — 최초 신설 (2026-09-21)

## 유튜브 플레이리스트 구독 자동 수집 — 배포·검증 완료 + 가입 무료 크레딧 제거 (2026-10-03, `Tool: claude`, Codex 핸드오프 이어받기)
아래 "재구축 착수" 절이 기록한 Codex의 미완료 작업을, 같은 날 [[cli-tool-handoff-via-transcript-file]]

- **감시/처리 분리**(Codex 계획의 2단계가 그대로 실현됨): 구독은 1시간마다 전체 목록(개수 제한 없음)을

## 유튜브 플레이리스트 구독 자동 수집 — 재구축 착수 (2026-10-03, `Tool: codex` 작업 중, 바로 위 세션이 이어받아 완료)
"플레이리스트에 새 영상이 추가되면 1시간마다 확인해 중복 없이 수집"하는 기능을 위해 Codex 세션이
19:12:24 KST부터 lampas-agent를 재구축 중이다. **이 절은 원래 간접 교차 확인(아래 "조사 시점" 단락)
만으로 작성됐으나, 2026-10-03 뒤늦게 그 Codex 세션의 원본 로그를 직접 ingest**해 4라운드 전체
대화로 보강됐다 → [[2026-10-03-lampas-agent-플레이리스트구독계획-codex원본]].

**현재 구조 진단(원본 세션 1차 확인)**: 맥미니 `launchd` 데몬+SQLite 작업 원장(스케줄·재시도·리스·
재시작 복구)은 이미 있어 재사용 가능. 문제 4가지 — ① 재생목록 조회 최대 **200개** 제한, ② Clips
영상 처리·체크포인트가 **브라우저**(OPFS)에 있어 창을 닫으면 끊김, ③ 유튜브 다운로드 작업 상태가
**메모리**에만 있고 임시 파일 수명 1시간, ④ 클립 뱅크 등록에 **영구 중복 방지 키 없음**. 맥미니
시스템 잠자기가 **1분**으로 설정돼 있어 매시간 무인 실행 위해 잠자기 방지도 필요.

합의된 6단계 계획(사용자 피드백 6개 — 개별등록도 추가/감시·처리 분리/ID 기준+파일업로드 제거/
서버파이프라인 재검토/무인운영 필수/검증 필수 — 반영 후 확정본):
1. 개별 URL은 즉시 큐, 플레이리스트 URL은 "구독"으로 저장해 1시간 폴링(파일 업로드는 일시 제거,
   기존 파일 기반 소스·클립은 보존).
2. 감시기(신규 영상 ID만 기록)와 처리 워커(다운로드·분할·전사·라벨링·뱅크 등록) 분리, 기존
   유튜브 목록 조회 **200개 제한**도 함께 보완. 긴 처리 중에도 매시간 감시는 계속.
3. **역할 분리**: 영상 ID는 자동 수집 이력 판단(구독 내 이미 처리된 ID는 자동 재수집 스킵, 같은
   계정·저장대상 여러 구독의 동일 ID는 작업 하나로 연결), 작업 ID는 재시도 중복방지. 사용자가
   개별 등록하거나 명시적으로 재수집을 선택하면 **항상 새 소스·새 클립 생성**(의도된 예외, 영상
   ID 자체에 소스 생성 금지 제약을 걸지 않음).
4. **4번(서버 파이프라인이 실제로 더 나은가) 재확인 결과**: 네이티브 FFmpeg 채택 확정. 맥미니가
   **M4 Pro·64GB RAM**+네이티브 FFmpeg 설치 확인. 원본 전달(맥미니→S3→브라우저 수신 폐지, 맥미니
   파일 직접 처리)·장면 감지(프레임별 시킹+Canvas 비교→FFmpeg 순차 디코딩)·썸네일(반복 시킹→배치
   추출)·오디오 추출(WASM 직렬→네이티브)은 개선되지만, **전사·라벨링은 외부 API 종속이라 서버
   이전만으로는 안 빨라짐**(정확한 개선폭 미측정 — 단계별 시간·메모리·품질 비교 후 확정 예정, 장면
   감지 기준은 먼저 유지해 품질 저하 방지).
5. SQLite에 구독·작업·단계별 체크포인트 저장, 재시작 시 미완료 단계부터 재개(백오프 재시도·
   잠자기 방지·디스크 관리·장기실행 서버 인증 포함 — 현재 Clips API가 사용자 로그인만 허용해
   **수집 계정에 귀속된 제한된 서버 인증 경로** 신설 필요).
6. 검증 범위: 신규영상 감지·중복 생략·수동 재수집·200개 초과 목록·브라우저 종료·처리 중 프로세스
   종료 복구·뱅크 저장 직후 연결 끊김·**24시간 이상 연속 운영**.

구현 순서: 작업·구독 모델 → 감시/처리 분리 → 네이티브 파이프라인 → 등록 화면 → 복구·인증 →
성능·연속 운영 검증. 구현 착수 지시 직후 어시스턴트는 중복 처리를 "구독=영상ID 자동방지, 수동재수집=
새 작업ID" 두 층으로, 서버 파이프라인은 "기존 장면분할·전사·라벨 로직 공유 + 파일처리만 네이티브
FFmpeg 교체"로 재확인했다 — 이 설명이 아래 "조사 시점" 교차 확인이 발견한 실제 1단계 구현
(`src/shared/ingest/` 신규)과 정확히 일치한다.

**조사 시점(같은 날 19:32 KST, 별도 Claude 세션의 교차 확인) 진행 상태 — 1단계만 착수, 미커밋**:
