## 데이터
- 소스 1: 사용자 첨부 엑셀 → 블루리본 맛집 579곳(리본 등급별 분포 포함, 좌표 없음).
- 소스 2: 사용자 공유 구글 시트 → 블루리본 통합 657곳 + 다이닝코드 90점 이상 86곳, 중복 5건
  병합 → 최종 **738곳**. 출처(블루리본/다이닝코드)·동네(석촌호수·광화문·압구정·도산공원·군자동)
  필터 지원, 다이닝코드 항목엔 점수·영업시간·메뉴 추가 표시.
- 원본 사이트(`bluer.co.kr`)는 403으로 직접 스크래핑 불가 — 사람이 내려준 엑셀/시트가 유일한
  데이터 경로.
- 좌표는 [[nominatim-batch-geocode-progressive-rollout]] 절차로 주소→좌표 변환. 738곳 중
  **502곳만 지도 표시**(주소·건물번호 정확히 일치하는 것만 핀 처리), 236곳은 위치 미확인으로
  목록 + 카카오맵 검색 링크 유지.

## 지도 — **최종 OpenStreetMap 단일 경로** (2026-09-24/25 기준, 2026-09-26 카카오맵으로 대체됨 — 위 "모순 해소" 절 참고)
이 앱은 세션 진행 중 지도 프로바이더를 3번 바꿨다. **최종 결정은 OpenStreetMap(키 불필요)**이며,
카카오·네이버 지도는 모두 폐기됐다:
1. 카카오 지도 컨셉으로 UI 골격 먼저 구현(데이터 0건 상태).
2. 지도 위 핀 요구 → 카카오/네이버는 사이트 삽입에 키가 필요해 **OpenStreetMap + Nominatim**
   지오코딩으로 전환, 396핀까지 배포.
3. 사용자가 네이버 클라우드 Client ID를 제공해 네이버 지도로 재전환 시도 → `spot.lampas.io`에서
   **401 인증 실패**(Dynamic Map 미활성/Web 서비스 URL 미등록 추정), 인증 실패 시 OSM으로 자동
   폴백하는 코드만 배포된 상태로 유지.
4. 최종적으로 사용자가 "네이버 지도는 제거하고 오픈 맵으로" 지시 → 네이버 SDK·인증 오류 UI
   전부 제거, **OpenStreetMap 단일 경로로 확정**.

> **이전 기록과의 모순 해소**: 이 페이지가 처음 생성됐을 때(2026-09-26, 원격 병합 커밋
> `e07db82f` 기준) `.env.local`/`env/.env.production`에 **Naver 지도 클라이언트 ID**만 보여
> "네이버 지도 기반으로 추정"이라 기록했었다. 실제로는 그 env가 위 3번(네이버 재전환 시도) 중간
> 시점의 스냅샷이었을 뿐이고, 이 세션의 최종 상태는 4번(OSM 확정)이다. env 파일의 네이버 키가
> 이후 실제로 정리(제거)됐는지는 이 세션 소스만으로 확인 불가 — 다음 코드 조사에서 재확인 필요.

## 기능 (2026-09-24/25 기준, 신고·필터는 2026-09-26 재구축으로 대체됨 — 아래 "재구축" 절 참고)
- 검색, 지역/리본 필터, 출처(블루리본/다이닝코드) 필터, 동네 모음.
- 즐겨찾기(브라우저 저장), 카카오맵 길찾기 링크(지도 프로바이더와 무관하게 길찾기만 카카오
  경유 유지).
- **폐업/정보 신고**: 사유·설명 입력 → 접수 번호 표시 → 신고자 개인 지도/목록에서 즉시 숨김·
  복원 가능. 신고 내용은 신설 인프라 없이 **기존 Lampas 관리자 문의함**에 저장. 전체 목록 제외는
  운영자가 문의함을 검토한 뒤 수동 반영하며, 제외된 장소는 구글 시트 재동기화·개인 숨김 복원과
  무관하게 계속 제외 상태 유지.

## 2026-09-26 재구축 — "주소만으로 맛집 데이터 생성" 서비스로 전환 (최신 상태)

- **블루리본·다이닝코드 표기 전면 제거.** 위 "데이터" 절의 738곳 엑셀/시트 소스 전시 방식은
  폐기됐다. 신규 lampas-api `spot` 모듈(테이블 `spot_places`)이 주소(+이름) → 카카오 REST(좌표·
  행정구역·장소 전화/카테고리/URL) → 블로그·웹 검색 발췌를 [[jev-typed-classification|Jev]](System
  One)로 "이 식당 글"만 typed 필터링 → 이미지 검색 후보를 비전 LLM이 음식/내부/외관/메뉴로 판정해
  최대 6장 선택 → LLM이 사실·발췌만 근거로 소개(요약·본문·태그·대표메뉴·팁)를 **완전히 새로 생성**
  하는 파이프라인으로 교체됐다. 외부 원문은 비공개 `notes`에만 남고 공개 필드는 전부 새 글.
- **구 데이터 856곳**(위 738곳과는 별도 집계로 언급 — 두 수치의 정확한 관계는 소스로 불확실)을
  운영 워커가 이 새 파이프라인으로 자동 보강 중(동시 처리 3).
- **"흔적 제거" 추가 지시**("크롤링한 게 티나지 않게 하는 게 핵심") — ★ 등급(블루리본 리본 수
  유래) 전부 제거, 공개 API의 `legacyId`(블루리본·다이닝코드 원본 id)를 해시 `ref`로 교체. 아래
  "기능" 절의 지역/리본/출처 필터는 더 이상 공개 화면에 없다 — 정렬은 소개·사진 준비 여부 기준으로
  대체.
- **신고→복원 플로우가 뒤집힘**: 아래 "기능" 절의 "신고자 개인 지도/목록에서 즉시 숨김·복원 가능"은
  이 세션에서 폐기됐다. 신고 즉시 서버가 `visible=false` 처리하고, **복원은 관리자만**(spot 웹 신설
  관리자 모드 또는 `admin.lampas.io/spot`)이 할 수 있다.
- **길찾기·장소 링크**: 네이버/카카오 선택 팝업으로 통일(위 "카카오맵 길찾기 링크 고정" 서술도
  갱신), 주소 복사 버튼 추가.
- **네이버 검색 API 보강 추가**(지역·블로그·이미지, 키 설정 시 자동 활성화) — 이 세션 시점엔
  `NAVER_CLIENT_ID`/`SECRET` 미설정으로 비활성.
- **Jev 채팅 검색 신설**: `POST /v1/spot/search`, 자연어 질문("송파구에서 기념일에 가면 좋은 곳")을
  규칙으로 지역·상황 파싱 후 후보 60곳을 Jev가 적합도 4단계로 판정·순위화.
- 상세·버그 2건(Gemini thinking 토큰 JSON 절단, `.env.local` 운영 번들 유입)·UX 반복은 세션 페이지
  참고 → [[2026-09-26-spot-주소기반재구축-카카오맵전환-네이버보강-채팅검색]].

## ⚠️ 모순 — "수집 데이터 표기 전면 제거" 이후에도 수집 파이프라인은 계속 운영됨 (2026-10-03 ingest)
위 "2026-09-26 재구축" 절은 08:31:28Z 세션을 근거로 "블루리본·다이닝코드 표기 전면 제거"·"주소만
넣으면 AI가 새로 쓰는 서비스로 재편"을 최신 상태로 적어 두었다. 그런데 **같은 날 02:38Z부터
시작해 10-02까지 이어진 별도 세션**([[2026-09-26-블루리본-식신-타베로그-맛집수집-spot확장]])은
그 재편 이후에도 블루리본→식신→타베로그로 소스를 바꿔가며 "이름+주소+평점 수집 → 중복 제거 →
Google 시트 append → Spot에 신규분만 추가"를 계속 반복했다:
- 블루리본: 시트 657→743, Spot 738→824→**856**(15초 간격 스크래핑으로 429/흰화면 회피).
- 식신(평점 4.0↑, 송파·종로): Spot **995**까지 증가. 중복 판정 기준이 "같은 주소면 제외"에서
  "주소+지도 장소 ID까지 봐서 동일 매장만 제외"로 교정됨(과잉 제외됐던 10곳 복원).
- 남양주시 +14, 도쿄/타베로그(평점 3.5↑) +6 → Spot **1,021**, 긴자 숙소 인근 바 +4.
- **해외 주소 지원 신설**: 해외 장소는 Google 지도로 길찾기·장소 정보 연결(국내는 네이버·카카오
  유지), 소개는 한국어로 작성하되 영문 주소도 등록 가능.

재편 세션이 말한 "구 데이터 856곳을 자동 보강 중"의 그 856이 이 세션의 블루리본 최종 수치와
일치한다 — **추정상 두 파이프라인은 공존**: 이 세션이 원시 후보(이름+주소)를 계속 공급하고,
재편 세션이 만든 Jev+비전 LLM+글쓰기 LLM 파이프라인이 각 신규 행의 공개용 소개를 자동 생성하는
후속 단계로 보인다. 다만 이는 소스 교차 추정이며, **공개 화면에 블루리본/식신/타베로그 출처 표기가
실제로 전혀 없는지**는 코드로 재확인되지 않았다 — 다음 코드 조사 시 확인 필요.
