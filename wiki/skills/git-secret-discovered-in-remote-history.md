# 원격 히스토리에서 비밀 발견 시 대응 절차

## 언제 쓰는가
"커밋하고 푸시해줘" 같은 평범한 요청을 처리하던 중 `git push`가 거부돼 `git fetch`로 원격 상태를
확인하다가, **자신이 만들지 않은 원격 커밋에 `.env`나 키 파일이 평문으로 들어 있는 것**을 우연히
발견했을 때. [[secrets-plaintext-exposure-pattern]]의 여러 사례 중 [[lampas-harness]]
([[2026-09-26-브라우저탭-좌표클릭-원격직접입력-위키백필-env노출-빌드동기화]])가 이 절차의 첫 실행
사례.

## 절차 (단계별)
1. **push 거부는 항상 fetch 후 diff를 보고 나서 병합한다** — 원격에 새 커밋이 있다고 무조건
   `git pull`/`merge`부터 하지 말고, 무엇이 들어왔는지 먼저 확인한다. 평상시엔 사소해 보이는 이
   습관이 비밀 노출을 우연히 발견하는 유일한 계기가 된다.
2. **발견 즉시 로컬 `.env`(또는 해당 비밀 파일)를 백업한다.** 이후 추적 해제·병합 과정에서 작업
   디렉터리의 파일이 삭제되거나 덮어써질 수 있다.
3. **그 커밋을 되돌리거나 강제로 지우려 하지 말고, 위에 자기 작업을 얹어 그대로 푸시한다.** 히스토리
   재작성은 다른 클론에 영향을 주는 파괴적 작업이라 사용자 승인 없이 임의로 결정할 일이 아니다.
4. **비밀 파일을 `.gitignore`에 추가하고 `git rm --cached`로 추적만 해제하는 커밋을 별도로 만든다.**
   이 커밋은 향후 재발만 막을 뿐, 이미 히스토리에 남은 값은 지우지 못한다 — 이 한계를 사용자에게
   명확히 설명한다.
5. 로컬 `.env`를 백업본으로 **그대로 복원**해 실행 중인 서비스 설정이 바뀌지 않게 한다.
6. **재발급(rotate) vs 히스토리 재작성+강제 푸시, 두 선택지를 사용자에게 제시하고 결정을 맡긴다.**
   어느 쪽도 어시스턴트가 임의로 골라 실행하지 않는다 — 재발급은 노출된 서비스 개수만큼 수동 작업이
   필요하고, 히스토리 재작성은 다른 클론의 강제 재동기화를 요구하는 파괴적 작업이기 때문.
7. 저장소가 "비공개로 보인다"(로그인 없이 404)는 사실이 안전을 보장하지 않는다는 점을 함께 알린다 —
   저장소 접근 권한이 있는 누구든 히스토리에서 비밀을 볼 수 있다.

## 주의사항 / 함정
- 비밀이 원격 커밋에서 발견됐다고 해서 **자기 작업 푸시를 멈추지 않는다** — 별개 문제다. 다만 반드시
  같은 응답 안에서 발견 사실을 사용자에게 보고한다(조용히 넘어가지 않는다).
- 이 위키(john-wiki)처럼 **ingest 과정에서 원본 소스를 그대로 복사하는 경우, 원본 트랜스크립트에
  실제 키 값이 출력돼 있는지 먼저 grep으로 확인**한다 — 있으면 위키 사본에는 레닥트 후 저장
  (원본 raw 파일 자체는 수정하지 않는 CLAUDE.md 규칙과 별개).
- 사용자가 "그냥 커밋해줘" 류의 직접 지시로 비밀 노출을 반복 승인하는 저장소도 있다
  ([[secrets-plaintext-exposure-pattern]] 사례 5, `toktalk`의 "env는 항상 커밋" 정책) — 이런 경우는
  이 절차가 적용되지 않는 **사용자 확정 정책**이므로 임의로 `.gitignore`에 추가하는 "정리"를 하지
  말 것. 이번처럼 **사용자가 비밀 노출 사실 자체를 몰랐던 경우**와 구분해서 판단한다.
