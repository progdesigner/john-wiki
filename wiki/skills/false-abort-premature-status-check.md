# 비동기 생성 "정상인데 실패로 오표시" 진단

## 언제 쓰는가
서버에서 오래 걸리는 비동기 작업(영상 생성 등)을 요청한 뒤, 실제로는 서버가 계속 작업 중이고 결국
정상 완료되는데도 클라이언트가 "중단된 생성"/"실패" 상태를 잠깐 띄웠다가 사라지는 증상이 **반복**될
때. "실행 자체엔 이슈 없음"이 사용자 제보의 핵심 단서 — 즉 백엔드 로직이 아니라 **클라이언트의 상태
판정·폴링 로직**을 의심해야 한다.

## 절차 (단계별)
1. 오표시가 뜨는 시점을 두 구간으로 나눠 조사한다: (a) 요청 직후 ~ 서버 작업 ID를 받기 전, (b) 작업
   ID를 받은 이후.
2. **(a) 구간**: 로딩 상태를 표현하는 노드/객체가 아직 작업 ID가 없다는 이유만으로 "중단된 생성"으로
   분류되는 조건문이 있는지 확인한다. 정상적인 초기 로딩 상태와 실제로 중단된 상태를 같은 조건으로
   판별하고 있으면 이게 원인이다.
3. **(b) 구간**: 작업 ID 획득 후 **두 종류의 폴링이 동시에 붙는지** 확인한다 — 화면에 남아있는
   컴포넌트의 "실행 중 폴링"과, 새로고침·재진입 시 상태를 복구하는 "복구용 폴링"이 별도 타이머/구독으로
   중복 등록되면, 둘 중 하나가 네트워크 hiccup으로 **한 번만** 실패해도 그 폴링 인스턴스가 즉시 실패
   알림을 띄운다. 서버는 계속 생성 중이므로 나중에 다른 경로(다른 폴링 또는 새로고침)로 완료 표시가
   따라와 "실패 떴다가 나중에 완료되는" 것처럼 보인다.
4. 수정 방향: (a)는 판정 조건에 "작업 ID 없음 = 아직 요청 전송 직후"인 경우를 별도로 분기해 중단 판정
   에서 제외한다. (b)는 폴링을 단일 소스로 합치거나(실행 중 폴링이 있으면 복구용 폴링을 등록하지 않음),
   일시적 조회 실패를 즉시 실패로 승격시키지 않고 재시도 후에만 실패 처리한다.
5. 다중 이미지/모델 입력처럼 같은 요청에 여러 기능이 동시에 바뀌는 세션이면, 이 진단은 다른 기능
   변경과 **독립적으로 회귀 테스트**한다 — 원인이 두 겹이라 한쪽만 고치면 증상이 줄어들 뿐 완전히
   사라지지 않아 "고쳤는데 왜 아직도 가끔 뜨지"로 오인되기 쉽다.

## 주의사항 / 함정
- "실행엔 이슈 없음(서버는 계속 생성되어 나중에 완료됨)"이라는 사용자 표현은 백엔드가 아니라
  클라이언트 상태판정/폴링을 가리키는 강한 신호다 — 서버 로그부터 파기 전에 프론트 폴링 코드를 먼저
  본다.
- 원인이 하나가 아니라 **둘이 겹쳐 있을 수 있다**(이 사례가 그랬음) — 하나 고치고 증상이 줄었다고
  종료하지 말고 두 구간 모두 확인한다.
