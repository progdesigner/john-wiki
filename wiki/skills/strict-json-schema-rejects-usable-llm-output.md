# 엄격한 JSON 스키마 검증이 오히려 쓸 수 있는 LLM 결과를 버리는 함정

## 언제 쓰는가
LLM에게 구조화 출력(JSON)을 요청하는 기능에서 "모델이 응답을 안 준다"는 제보가 반복될 때. 특히
**직전에 "형식 검증을 강화"하는 수정을 했는데도(또는 그 수정 직후부터) 증상이 계속되거나 악화**
됐다면 이 함정을 의심한다 — 원인이 "모델 출력 품질"이 아니라 "서버가 거부하는 기준" 쪽에 있을 수 있다.

## 원인
구조화 출력을 신뢰성 있게 받으려고 JSON 스키마 검증(필수 필드 존재, 타입 일치 등)을 추가하는 것은
합리적인 1차 대응처럼 보이지만, 모델이 **본문 자체는 맞게 생성**했으면서 부차적인 형식만 다르게
낼 수 있다(예: 선택적 설명 필드 `note`를 안 씀, `posts`를 배열 대신 하나의 문자열로 반환). 이런
경우 엄격한 검증은 "쓸 수 있는 본문이 있는데도" 전체 응답을 거부해버려, 증상이 "모델이 응답을 못
만든다"처럼 보이게 만든다 — 실제로는 **검증 기준이 너무 엄격해서 멀쩍이 버려지는 것**이다.

## 진단
1. 실패 처리 전에 **서버가 받은 원문 응답을 그대로 로그로 확인**한다 — 실패 메시지(`note 누락`,
   `posts가 문자열`)만 보고 "모델이 못 만들었다"고 결론 내리지 않는다.
2. 원문에 실제로 쓸 수 있는 본문(게시물 텍스트 등 핵심 콘텐츠)이 들어 있는지 눈으로 확인한다. 들어
   있다면 문제는 모델이 아니라 **검증 로직**이다.
3. 검증을 추가/강화한 시점과 증상 재발/악화 시점이 겹치는지 확인 — 겹치면 그 검증 자체가 회귀의
   원인일 확률이 높다.

## 수정
1. **핵심 콘텐츠와 부가 필드를 구분**한다 — 사용자에게 실제로 필요한 것(게시물 본문)과 선택적
   메타데이터(설명 노트 등)를 분리하고, 부가 필드 누락만으로 전체 응답을 버리지 않는다.
2. **타입이 유연해도 되는 필드는 관대하게 파싱**한다 — 배열을 기대했는데 문자열이 오면, 가능하면
   문자열을 단일 요소 배열로 취급하는 등 변환을 시도한 뒤에만 실패로 처리한다.
3. **2차 제약(글자 수, 항목 수 등)으로 1차 생성물을 폐기하지 않는다** — 예: 500자 제한을 넘었다는
   이유로 생성된 본문을 숨기지 말고, 제한은 참고 표시로만 남기고 결과는 항상 보여준다. "검증 실패"와
   "품질 경고"를 같은 심각도로 다루지 않는다.
4. 그래도 구조가 필요하면 **일반 텍스트로 받아 사후 분리**(예: 구분선으로 연속 글 나누기)하는 쪽이
   엄격한 JSON 강제보다 실패에 강하다 — 파싱 실패 시에도 원문 텍스트를 그대로 보여줄 수 있는
   폴백을 유지한다.

## 주의사항 / 함정
- "검증을 강화하면 품질이 보장된다"는 직관이 여기서는 반대로 작동한다 — 검증 대상이 **모델 출력
  전체를 all-or-nothing으로 막는 게이트**가 되면, 사소한 형식 불일치 하나가 멀쩍이 쓸 수 있는 결과
  전체를 가린다.
- 디버깅 시 에러 메시지(`note 누락`, `타입 불일치`)에 낚여 "프롬프트를 더 명확히 하면 해결된다"고
  판단하지 말 것 — 근본 수정은 프롬프트가 아니라 **검증 로직의 관대함** 쪽에 있는 경우가 많다
  (관련: [[gemini-thinking-tokens-eat-maxtokens-budget]]도 같은 "증상은 파싱 실패인데 원인은 다른
  곳" 패턴이지만, 그쪽은 토큰 예산 문제이고 이쪽은 검증 엄격도 문제로 서로 구분되는 별개 원인).
