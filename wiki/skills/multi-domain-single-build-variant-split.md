# 단일 빌드의 호스트명 기반 다중 도메인 분리

## 언제 쓰는가
한 SPA가 여러 하위 기능(예: Actor/Object/Place/Transform 관리)을 다 가지고 있어 "다 연결된 사이트
같다"는 피드백을 받았을 때, 또는 기능별로 독립 제품처럼 보이게 서브도메인을 나누고 싶을 때 —
단 백엔드 API는 공유하고 **새 저장소나 새 CloudFront 배포를 만들지 않고** 기존 빌드 산출물 하나로
여러 브랜드 사이트를 서빙하고 싶은 경우.

## 절차 (단계별)
1. **도메인·경로 소유 규칙을 순수 함수로 뽑아낸다**(예: `appDomains.js`). "이 경로는 어느 도메인이
   소유하는가", "현재 호스트는 어느 variant인가", "이 variant의 내비 항목은 무엇인가"를 전부 이
   모듈이 결정하게 하고 vitest로 테스트를 붙인다 — 컴포넌트 안에 하드코딩하지 않는다.
2. **App 루트가 `html[data-site]`(또는 동일 효과의 전역 속성)를 현재 variant로 찍게 한다.** 테마
   색·로고·타이틀을 이 속성에 거는 CSS 변수로 구현하면 기존 컴포넌트 트리를 전혀 고치지 않고
   사이트별 브랜딩(액센트 색·파비콘·탭 타이틀)을 입힐 수 있다.
3. **다른 도메인 소유 경로로 들어왔을 때의 catch-all 리다이렉트**(`CrossAppRedirectPage` 류)를
   라우터 최하단에 둔다 — 레거시 딥링크나 다른 사이트의 내부 링크가 그대로 유입돼도 깨지지 않고
   올바른 도메인으로 넘어가게 한다. 레거시 경로 별칭(예: 리네이밍 전 경로)도 이 정규화 단계에서
   함께 처리한다.
4. **로컬 개발은 쿼리 파라미터(`?variant=x`)+sessionStorage로 전환**하면 별도 로컬 도메인 설정 없이
   variant를 바꿔가며 테스트할 수 있다.
5. **인프라는 기존 CloudFront 배포에 호스트 별칭만 추가한다** — 와일드카드 인증서가 이미 있다면
   신규 배포·신규 인증서 없이 `Aliases`에 새 호스트명을 추가하고 Route53에 CNAME만 만들면 된다.
   배포 스크립트는 그대로 재사용(빌드 하나 → 모든 도메인에 반영).
6. **상태 페이지·헬스체크 레지스트리에 새 도메인을 등록**한다 — 안 하면 다른 영역의 배포 게이트
   (운영 드리프트 검사 등)를 깨뜨릴 수 있다.
7. 각 단계마다 vitest·빌드·크로스도메인 동기화 드리프트 검사를 통과시키고, 가능하면 헤드리스
   브라우저로 각 variant의 제목·액센트·내비·파비콘을 실제로 열어 확인한다.

## 주의사항 / 함정
- **경로 소유권 분기와 레거시 경로가 충돌할 수 있다** — 새로 만든 도메인이 어떤 접두 경로(예:
  `/studio/...`)를 "다른 도메인 소유"로 판단하도록 규칙을 짜면, 그 접두사로 시작하는 레거시 딥링크
  (리네이밍 전 경로 등)가 전혀 다른 화면으로 잘못 라우팅될 수 있다 — 분리 작업 직후 레거시 경로
  전수 조사가 필요하다.
- **API 재배포 여부를 분리 단계별로 판단**한다 — 프론트 분리는 API 변경이 없으면 API를 건드리지
  않는 것이 다른 동시 작업(워킹트리에 있는 미완성 변경)과의 충돌을 피하는 길이다.
- 사이트별 "독립 제품처럼 보이기"는 내비에서 형제 링크를 빼는 것만으론 부족할 수 있다 — 워드마크·
  액센트 색·파비콘·탭 타이틀·독립 홈 화면까지 다섯 요소가 함께 바뀌어야 "연결된 사이트" 느낌이
  사라진다(사용자가 두 차례에 걸쳐 피드백한 패턴).
- 같은 저장소를 동시에 작업하는 다른 세션이 있다면 커밋 범위를 경로 단위가 아니라 파일 단위로
  좁혀야 한다 — → [[selective-hunk-commit-shared-file]].
