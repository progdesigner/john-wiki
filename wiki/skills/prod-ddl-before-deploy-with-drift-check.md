# 운영 DDL 선적용 + 스키마 드리프트 검사

## 언제 쓰는가
새 Prisma 모델(또는 그에 준하는 새 테이블)을 쓰는 기능을 수동 DDL 방식(마이그레이션 프레임워크가 아닌
직접 작성한 `.sql` 파일)으로 운영에 반영해야 할 때. 특히 작업본에 이번 기능과 무관해 보이는 다른
미커밋 변경이 함께 있는 상태에서 배포를 진행할 때 이 절차가 중요해진다.

## 절차 (단계별)
1. **API 배포보다 먼저 운영 DB에 DDL을 적용한다.** 순서를 어기면(테이블 없이 API부터 배포) 배포된
   코드가 존재하지 않는 테이블을 참조해 크래시 루프에 빠진다.
2. **DDL 적용 전, 작업본 전체를 드리프트 검사한다** — 이번에 배포되는 API 코드가 참조하는 테이블 중
   운영 DB에 없는 게 이번 기능 것 하나뿐인지 확인한다. "이번 변경과 무관한 미커밋 작업이니 무시해도
   된다"고 단정하지 않는다 — 무관한 기능이라도 같은 API 빌드에 코드가 이미 포함돼 있다면 그 기능이
   쓰는 테이블도 없으면 똑같이 크래시 루프를 만든다. 발견되면 이미 있던 DDL 파일로 함께 생성한다.
3. **전체 테스트 스위트에서 무관한 스펙이 실패하면 먼저 단독 재실행으로 재현을 확인한다.** 다른 빌드/
   테스트와 동시 실행되며 생긴 일시적 실패라면 재현되지 않는다 — 이 경우 배포 게이트를 그 재실행
   결과로 통과시켜도 된다. 재현되면 진짜 회귀이므로 배포를 막아야 한다. 어느 쪽이든 사용자에게
   명시적으로 보고한다(조용히 넘기지 않는다).
4. 신규 서브도메인을 쓰는 웹 앱이 함께 배포된다면 CloudFront·DNS 최초 연결이 필요하다 →
   [[new-subdomain-cloudfront-wildcard-deploy]]. API DDL → API 배포 → 웹 도메인 최초 연결 → 웹 배포
   순서를 지킨다.
5. **커밋 범위는 실제로 운영에 반영된 스키마까지만 포함한다.** 드리프트 검사로 발견해 함께 DDL을 적용한
   다른 기능의 Prisma 모델·DDL 파일은 저장소 스키마를 운영과 맞추기 위해 커밋하되, 그 기능의 나머지
   코드 변경(아직 배포되지 않은 부분)은 미커밋 상태로 그대로 남긴다 — "DB에 테이블이 생겼다"는 이유로
   관련 없는 코드까지 커밋 범위를 넓히지 않는다.
6. 새 서비스/컴포넌트를 레지스트리(예: 상태 페이지 컴포넌트 목록)에 등록해야 하는 시스템이면, 등록
   지점을 배포 보고에 명시하고 빠뜨림을 잡아주는 별도 spec(예: `deploy.json` 대조 테스트)이 있는지
   확인한다.

## 주의사항 / 함정
- DDL을 안 적용하고 API를 먼저 배포하면 크래시 루프 — 되돌리려면 서비스 다운 상태에서 급하게 DDL을
  적용해야 하므로, 항상 DDL을 먼저 적용하는 순서를 지킨다.
- 드리프트 검사를 "이번 기능 스키마만" 좁게 하면, 같은 빌드에 섞여 들어간 다른 미커밋 기능의 테이블
  누락을 놓친다 — 검사 범위는 "이번에 배포되는 API 코드 전체가 참조하는 테이블"이어야 한다.
- 동시 실행 중 생긴 일시적 테스트 실패를 "무관하다"며 재현 확인 없이 배포 게이트를 우회하면 진짜
  회귀를 놓칠 위험이 있다 — 반드시 단독 재실행으로 재현 여부를 먼저 확인한다.
- 새 테이블이 생겼다고 무관한 미커밋 코드 전체를 얼떨결에 함께 커밋하면 리뷰 범위가 불필요하게
  커진다 — 스키마(모델+DDL)와 나머지 코드를 분리해서 커밋 여부를 판단한다.
