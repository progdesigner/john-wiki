# 실수 방지 인라인 확인 (destructive-action-inline-confirm)

## 언제 쓰는가
클릭 한 번으로 즉시 실행되는 버튼이 (a) 되돌리기 어렵거나(진행 중 작업 중지) (b) 오조작이 잦은
위치에 있을 때(hover만으로 노출되는 버튼, 리스트 항목 위의 작은 아이콘). `window.confirm()` 모달을
띄우는 대신, UI 안에서 상태 전환으로 확인을 처리하고 싶을 때. [[lampas-harness]]에서 두 가지 사례로
확립: 진행 중 턴 중지 버튼, 대화 목록 보관.

## 절차 (단계별) — 두 가지 변형

### 변형 A: 같은 버튼 2회 클릭 (타임아웃 방식)
자주 누르는 위치(활동바, 툴바)에 적합 — 버튼 자리를 유지한 채 상태만 바꾼다.
1. 첫 클릭 시 버튼을 "확인 대기" 상태로 전환 — 라벨을 "정말 OO?"로 바꾸고 시각적으로 강조(색상
   변경·깜빡임).
2. 타이머(예 3초) 시작. 같은 버튼을 타이머 안에 다시 클릭하면 실제 동작 실행.
3. 타이머 만료 시 자동으로 원래 상태로 복귀 — 별도 취소 조작 불필요.
4. 다른 버튼(예: 배경 작업 중지, 대기 취소)은 건드리지 않고, 되돌리기 어려운 그 버튼에만 적용한다 —
   모든 액션에 일괄 적용하면 UX 마찰만 커진다.

### 변형 B: 롱프레스 + 확인창 (리스트 항목용)
리스트 항목처럼 hover 버튼이 오조작을 유발하는 곳에 적합 — hover 버튼을 완전히 제거한다.
1. hover 시 노출되던 버튼을 제거한다.
2. pointerdown부터 타이머(예 0.6초) 시작, 누르는 동안 항목을 시각적으로 예고 강조(색상 하이라이트).
3. 타이머 만료 시 확인창(`"OO 하시겠습니까?"`)을 띄운다.
4. **이동 취소**: 누르는 중 일정 픽셀(예 8px) 이상 움직이면 스크롤/드래그로 간주해 취소한다 —
   그래야 리스트 스크롤 제스처와 충돌하지 않는다.
5. **클릭 억제**: 롱프레스가 확인창까지 이어졌다면, 손을 뗄 때 뒤따라 발생하는 클릭(예: 항목 선택/전환)
   이벤트를 억제한다 — 안 하면 확인 후 의도치 않은 클릭이 함께 실행된다.
6. 뒤에 걸리는 실제 동작(API 호출 등)은 기존 함수를 그대로 재사용 — 확인 트리거만 바꾸고 실행 로직은
   손대지 않는다.

## 공통 원칙
- 확인 UI는 **버튼/항목 자체의 상태 변화**로 표현한다 — 별도 모달 오버레이보다 맥락이 유지되고
  구현이 가볍다 (단, 변형 B의 최종 단계는 확인창 사용 — 실수로라도 삭제성 동작은 명시적 확인 문구가
  나을 때가 있다).
- 확인 대기 상태는 **자동으로 원복**되어야 한다 — 사용자가 다른 곳을 클릭하거나 잊어버려도 위험한
  상태로 남지 않게.
- 기존 실행 로직(API 호출, 상태 변경 함수)은 그대로 두고 **트리거 지점만 교체**한다. 리팩터 범위를
  최소화해 회귀 위험을 줄인다.

## 주의사항 / 함정
- 타이머 방식(A)에서 강조 애니메이션(깜빡임)이 없으면 사용자가 "확인 대기 중"이라는 걸 못 알아채고
  그냥 다시 첫 클릭으로 오인할 수 있다 — 라벨 변경만으로는 부족, 시각적 강조를 같이 준다.
- 롱프레스(B)는 모바일 터치와 데스크톱 마우스 양쪽에서 pointerdown/pointerup 기반으로 구현해야
  한다 — mousedown만 쓰면 터치 환경에서 안 먹는다.
- 두 변형 모두 "이 버튼만 위험하다"는 범위를 명확히 하고, 인접한 안전한 버튼(취소·닫기 등)까지
  확인 절차를 넣지 않는다 — 과도한 확인은 그 자체로 UX 저하.
