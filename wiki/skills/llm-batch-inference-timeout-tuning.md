# LLM 배치 추론 타임아웃 튜닝 + 요청 경로에서 모델 대기 제거

## 언제 쓰는가
운영 배포 후 로그에서 "모델 유추/분류가 전부 실패"처럼 **배치 단위로 100% 실패**하는 증상이 보일
때. 로컬 검증에서는 (API 키가 없어) 규칙 기반 폴백만 돌았고, 운영에서 처음으로 실제 모델 배치
호출이 켜지면서 드러나는 경우가 흔하다. 원인은 대개 모델 자체 오류가 아니라 **배치가 너무 커서
"배치당 응답 시간 × 배치 크기"가 클라이언트/게이트웨이 타임아웃을 넘기거나, 큰 배치의 JSON 응답이
토큰 상한에 걸려 잘리는 것**이다.

## 절차 (단계별)
1. **실패 로그에서 원인을 분리한다** — 타임아웃 에러인지, JSON 파싱 실패(응답 잘림)인지 구분한다.
   같은 배치 크기 문제가 두 증상 모두를 만들 수 있다.
2. **배치 크기를 줄인다** — 처음 크기의 절반 정도로 시작(예: 40개 → 20개). 배치 하나당 예상 소요
   시간(모델 응답 지연 × 배치 크기)을 먼저 추정하고, 목표 타임아웃의 절반 이하로 맞춘다.
3. **타임아웃을 명시적으로 늘린다** — 기본 타임아웃이 짧게 잡혀 있었다면(예: 30초) 실측 소요
   시간에 여유를 더해 늘린다(예: 90초). 배치 크기 축소와 타임아웃 확대를 함께 해야 안전 마진이
   생긴다.
4. **응답 형식을 압축한다** — 키 이름을 줄이거나 불필요한 필드를 제거해 응답 토큰 수를 줄이면 같은
   배치 크기에서도 잘릴 확률이 낮아지고 속도도 빨라진다.
5. **잘린 응답 복구 로직을 넣는다** — JSON 파싱이 실패해도 배치 전체를 버리지 말고, 파싱 가능한
   앞부분만 잘라 살리거나 실패한 항목만 재시도하도록 한다.
6. **사이클당 처리량에 상한을 둔다** — 무제한으로 큰 배치를 계속 만들지 않도록 사이클(주기 실행)당
   처리 건수 상한을 두어 한 번의 튜닝 실수가 전체 지연으로 번지는 것을 막는다.
7. **요청 경로에서 모델 응답을 기다리지 않도록 분리한다** — 사용자 대면 API(예: 실시간 검색)가 이
   모델 호출을 동기로 기다리면 배치가 느려질 때마다 응답 지연이 함께 늘어난다. 캐시가 없으면 규칙
   기반 폴백으로 즉시 응답하고, 모델 호출은 **백그라운드로 캐시를 데우는** 별도 경로로 뺀다 — 첫
   요청은 폴백, 재요청부터 모델 결과가 붙는 구조(→ [[accept-then-poll-for-slow-ai-jobs]]와 같은
   "동기 대기 제거" 계열이지만, 여긴 폴링이 아니라 캐시 워밍이라는 점이 다르다).
8. **검증**: 운영에서 같은 검색어를 여러 번 반복 조회해, 첫 조회는 규칙 결과·이후 조회에서 모델
   결과 건수가 실제로 늘어나는지 확인한다(캐시가 데워지는지 실증).

## 주의사항 / 함정
- 로컬 검증만으론 이 문제가 안 보인다 — API 키가 없으면 규칙 기반 폴백만 타므로 배치 호출 경로
  자체가 로컬에서 실행되지 않는다. **운영에 API 키가 있을 때 첫 배포에서만 드러나는 실패**라는 점을
  염두에 둔다.
- 배치 크기만 줄이고 타임아웃은 그대로 두면, 응답이 여전히 빠듯하게 걸려 간헐적으로만 실패해
  진단이 더 어려워진다 — 배치 크기·타임아웃·응답 압축 세 가지를 함께 조정한다.
- 유추 규칙(폴백용) 사전이 수집기·API 등 여러 서비스에 중복 존재하면, 이 튜닝과 별개로 규칙을
  고칠 때 모든 위치를 같이 고쳐야 한다 — 결합 지점을 문서에 명시해둔다.
