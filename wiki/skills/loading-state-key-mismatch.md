# 로딩 상태 키 불일치

## 언제 쓰는가
"AI로 수정/다시 쓰기 같은 액션을 눌러도 **아무 반응이 없어 작동 안 하는 것 같다**"는 신고인데,
네트워크·서버 로그로 보면 **요청은 정상 전송·처리**되고 있는 경우. 즉 로직은 도는데 **로딩 스피너/비활성화 UI가 안 뜨는** 상황.

## 절차 (단계별)
1. 먼저 **요청이 실제로 나가는지** 확인(네트워크·서버 로그·응답 토스트). 나간다면 로직 버그가 아니라 **피드백(UI) 버그**로 좁힌다.
2. 로딩 상태 저장소를 찾는다 — 보통 `busy`/`loading` 맵이나 Set에 **키 문자열**로 담는다.
3. **생성 측**(요청 시작 시 키를 넣는 코드)과 **조회 측**(버튼이 스피너를 그릴지 비교하는 코드)의 **키 문자열이 정확히 같은지** 대조한다.
   - 흔한 원인: 한쪽만 붙는 접미사/접두사(예: count 접미사 `-1`, id 조합 순서, 낙관적 임시 id vs 실제 id, 대소문자, 공백).
   - 예(이 세션): 생성은 `beat-ai-replace-{beatId}-1`, 조회는 `beat-ai-replace-{beatId}` → 영원히 불일치.
4. **키를 한쪽으로 통일**한다. 단위가 이미 유일하면 불필요한 구분자를 빼고(예: beatId만으로 유일 → count 제거), 여러 인스턴스를 구분해야 하는 경로는 그 규칙을 **양쪽 모두**에 적용.
5. 실제로 스피너가 돌고 완료 시 사라지는지(패널 닫힘·성공 토스트 등) 확인.

## 주의사항 / 함정
- 같은 함수가 **여러 진입점**(beat 단위 vs 전체 추가 등)에 쓰이면, 한 경로만 유일 키가 필요하고 다른 경로는 count로 구분해야 할 수 있다. 조건 분기로 키 생성 규칙을 나눈다(무조건 접미사 제거는 다른 버튼을 깬다).
- "작동 안 함" 신고를 **로직 버그로 오진**하지 말 것 — 요청이 나가는지부터 확인하면 반은 끝난다.
- 조회 측이 `busy[key]`가 아니라 `busy[key] && ...` 같은 파생 조건이면 그 파생식도 함께 본다.
