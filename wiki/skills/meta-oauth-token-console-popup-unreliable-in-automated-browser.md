# Meta 개발자 콘솔 "토큰 생성" 팝업은 자동화 브라우저에서 신뢰할 수 없다

## 언제 쓰는가
Meta 개발자 콘솔(Instagram 비즈니스 로그인 등)에서 "토큰 생성" 버튼으로 장기 액세스 토큰을 발급받아야
하는데, 사람이 직접 조작하는 일반 브라우저가 아니라 **AI 에이전트가 조작하는 자동화 브라우저**(예:
[[lampas-browser]]의 하네스 "브라우징" 패널)를 통해 진행해야 할 때.

## 먼저 알 것 — 이 경로는 구조적으로 막힌다 (시간 낭비 방지)
정상 브라우저에서는 "토큰 생성" 버튼이 **팝업 창**을 열고, 로그인·권한 허용이 끝나면 팝업이 **스스로
닫히면서** 메인 창이 완료를 감지해 토큰을 모달로 띄운다. 자동화 브라우저 환경에서는 이 메커니즘이
아래 세 지점에서 깨진다([[2026-09-26-ai-dalar-인스타그램-토큰발급-메타앱생성]] 세션에서 실측):

1. **팝업이 별도 탭으로 열려 닫히지 않는다** — 메인 화면이 "완료"를 감지할 방법이 없어 토큰 모달이
   영원히 뜨지 않는다. AI가 콜백 완료를 확인하고 그 탭을 수동으로 닫아도 메인 화면은 감지하지 못했다
   (재시도해도 동일).
2. **비밀번호 입력 필드는 AI 도구가 아예 조작하지 못한다** — 보안상 의도적으로 제외돼 있음. Facebook/
   Instagram 로그인, 시크릿 재확인 비밀번호 등은 항상 **사람이 브라우징 패널에서 직접 입력**해야 한다.
3. **좁은 입력란에 표시되는 시크릿/토큰 값은 도구로 못 읽는다** — `selection` 읽기, "복사" 버튼→
   클립보드(`pbpaste`) 읽기 둘 다 실패할 수 있다(복사 버튼이 실제로 시스템 클립보드에 텍스트를 넣지
   않는 경우 관찰됨 — 클립보드에 12바이트 바이너리만 남음).

## 절차 (단계별) — 팝업 UI를 우회하는 확실한 방법
콘솔 UI의 "토큰 생성" 버튼에 의존하지 말고, **앱 시크릿만 확보해 OAuth 코드 교환을 직접 curl로 처리**한다.

1. Meta 앱에서 이용 사례(Instagram)·필요 권한(`instagram_business_content_publish` 등)·리디렉션 URL을
   등록해 둔다(이 부분은 콘솔 UI로 정상 진행 가능, 팝업 없음).
2. 대상 계정을 Instagram 테스터로 초대 → 대상 계정에서 초대 수락 → 필요 시 개인 계정을 비즈니스 계정으로
   전환(Facebook 페이지 연결은 Instagram 로그인 방식에선 불필요, 건너뛰기).
3. **앱 시크릿 값**은 사용자에게 직접 채팅/클립보드로 전달받는다 — 위 3번 한계 때문에 자동화 도구로는
   못 읽으므로, "표시" 클릭(비밀번호 재확인 필요, 사람이 처리) → 값을 드래그 선택해 복사 → 채팅에
   붙여넣기를 사람에게 요청한다.
4. 시크릿을 받으면 등록된 리디렉션 URL로 인증 URL을 열어 `code`를 받는다(대상 계정 로그인·권한 허용이
   이미 끝나 있으면 추가 로그인 없이 통과될 수 있음).
5. `POST api.instagram.com/oauth/access_token`으로 단기 토큰 교환.
6. `GET graph.instagram.com/access_token?grant_type=ig_exchange_token`으로 60일 장기 토큰 교환.
7. `GET graph.instagram.com/me`로 토큰이 올바른 계정에 발급됐는지 검증 후 앱 시크릿과 함께 정리.

## 주의사항 / 함정
- **팝업 재시도는 답이 아니다** — "이번엔 콜백 끝나자마자 탭을 닫아보겠다"는 재시도가 두 번 실패했다.
  구조적 문제이므로 첫 실패 시점에 바로 curl 경로로 전환하는 것이 시간을 아낀다.
- **비밀번호·좁은 시크릿 필드는 처음부터 사람에게 넘겨라** — 도구로 읽으려 여러 방법(selection, 복사
  아이콘+클립보드)을 시도하는 것보다, 값을 사람이 직접 채팅에 붙여넣게 요청하는 편이 훨씬 빠르다.
- 이 함정은 Meta/Instagram 콘솔에 국한되지 않고, **"팝업이 닫혀야 완료를 감지하는" 모든 OAuth 콘솔 UI**에
  자동화 브라우저를 쓸 때 재현될 수 있다 — 새 서비스에서도 같은 패턴이면 처음부터 curl 기반 코드 교환을
  1순위로 고려할 것.
