# 프록시 본문 크기 제한(413)이 "Network Error"로만 보이는 문제

## 언제 쓰는가
브라우저에서 파일(특히 영상·이미지 렌더 결과)을 API 서버로 업로드할 때 브라우저 개발자도구에
상태코드 없이 그냥 **"Network Error"** 또는 CORS 오류로만 뜨고, 작은 파일은 정상 동작하는 경우.
API 서버 자체 로그에는 요청이 도달하지 않은 것처럼 보이거나 아예 흔적이 없다.

## 절차 (단계별)
1. **파일 크기로 재현 여부를 가른다** — 실패하는 파일과 비슷한 크기(예: 130MB)로 업로드를 재현하고,
   훨씬 작은 파일(예: 6MB)로 같은 요청이 정상(또는 다른 에러로) 응답하는지 대조한다. 크기 임계값
   근처에서 갈리면 API 로직이 아니라 **경로상의 본문 크기 제한**을 의심한다.
2. **API 앞의 리버스 프록시 설정을 확인한다**(nginx `client_max_body_size`, ALB 페이로드 한도 등).
   기본값(예: nginx 1MB, 흔히 올려둔 100MB)에 걸리면 **413 Payload Too Large**를 반환한다.
3. **413 응답에 CORS 허용 헤더가 없는지 확인한다** — 정상 응답 경로에만 CORS 헤더를 붙이는 서버
   설정이 흔한데, 프록시가 자체적으로 반환하는 413에는 그 헤더가 안 붙는다. 브라우저는 CORS 헤더
   없는 응답을 스크립트에서 읽을 수 없어 상태코드 대신 **"Network Error"**로만 노출한다 — 이게
   증상과 원인 사이의 진짜 연결고리다.
4. **근본 수정**: API 서버를 경유하지 않고 **브라우저에서 오브젝트 스토리지(S3 등)로 직접 업로드**
   하도록 바꾼다. API는 presigned URL 발급 + 업로드 완료 확인(계정 소유 경로 검증)만 담당,
   실제 파일 바이트는 프록시·ALB를 거치지 않아 어떤 본문 크기 제한도 적용되지 않는다.
5. **완료 확인 엔드포인트는 업로드 경로 키를 계정 범위로 검증**한다(예: 로그인 계정의 프리픽스만
   허용) — presigned PUT 자체는 누구나 그 URL만 알면 쓸 수 있으므로, 완료 처리 API에서 남의 경로에
   행이 생기지 않도록 막아야 한다.
6. **업로드 진행률 UI**를 추가한다 — presigned PUT은 API 경유가 아니므로 기존 진행률 표시 로직이
   있었다면 새 경로에 다시 연결해야 한다.
7. **폴백을 남긴다**: presign 엔드포인트가 없는 구버전 클라이언트/서버를 만날 수 있으면 기존 API
   경유(multipart) 업로드를 폴백으로 유지한다.
8. **CORS 설정을 재확인한다** — 이 문제를 조사하며 스토리지 버킷 CORS의 PUT 허용 오리진 목록에
   해당 도메인이 원래 빠져 있었을 수 있다(다른 "조용히 실패하던" 업로드 기능, 예: 원본 자동 백업이
   같은 원인으로 동시에 고쳐지는 경우가 있다 — 하나만 고치고 끝내지 말고 같은 버킷을 쓰는 다른
   업로드 경로도 함께 점검한다).

## 주의사항 / 함정
- "Network Error"라는 브라우저 메시지만 보고 CORS 설정 문제로 단정하지 않는다 — CORS는 413의
  **증상을 가리는 매개체**일 뿐, 진짜 원인은 프록시 본문 크기 제한이다. 상태코드를 못 보면 파일
  크기를 바꿔가며 재현해 임계값을 직접 찾아야 한다.
- 프록시 설정을 단순히 올리는 것(예: 100MB→500MB)도 임시 해결은 되지만, 렌더 결과물 크기가 계속
  커지는 제품(영상 편집 등)이면 결국 다시 막힌다 — 대용량 페이로드는 프록시를 완전히 우회하는
  구조가 근본 해결이다. 같은 결론이 [[tailscale-funnel-large-payload-bypass]](다른 원인: 공개
  터널 대역폭 제한)에서도 나왔다 — "큰 페이로드는 중간 경로를 거치지 말고 오브젝트 스토리지로
  직접 보낸다"는 패턴이 반복되는 구조적 함정이다.
