# 느린 AI 작업의 동기 대기 → 즉시 접수 + 별도 폴링

## 언제 쓰는가
자동 실행/자동화 엔드포인트가 AI 호출(Jev·LLM 등) 완료까지 **동기적으로 응답을 대기**하다가,
플랫폼·프록시·게이트웨이가 강제하는 요청 타임아웃(예: 30초)에 걸려 실패로 보일 때. 실제로는 AI
작업 자체엔 문제가 없고, "응답을 기다리는 방식"이 문제다.

## 절차 (단계별)
1. **타임아웃 발생 지점을 확인한다** — 클라이언트/게이트웨이의 고정 타임아웃 값과, 실제 AI 작업의
   평균/최대 소요 시간을 비교해 구조적으로 초과할 수밖에 없는지 확인한다.
2. **엔드포인트를 접수형으로 바꾼다** — 요청을 받으면 작업을 백그라운드로 넘기고 **즉시** "접수됨"
   응답을 반환한다(운영 확인 기준 수십 ms대).
3. **진행 상태 조회를 분리한다** — 별도 엔드포인트/폴링으로 작업 상태(대기/진행/완료/실패)를
   조회하게 한다.
4. **중복 실행을 막는다** — 반복 폴링이 AI 작업을 다시 트리거하지 않도록, 이미 접수된 작업은
   상태만 반환하고 재실행하지 않는다(멱등성 확보, → [[idempotent-message-retry]]와 같은 계열의
   원칙).
5. **일시적 지연과 실제 실패를 구분한다** — 폴링 중 한 번의 네트워크 hiccup을 즉시 "실패"로
   승격시키지 말고, 재시도 후에도 반복되면 실패로 처리한다(→ [[false-abort-premature-status-check]]
   와 같은 원칙).
6. **검증**: 접수 응답 지연을 실측(예: 29ms)하고, 느린 AI 응답에서도 접수는 즉시 반환되는지·반복
   조회가 중복 실행을 일으키지 않는지 자동 테스트로 확인한다.

## 주의사항 / 함정
- 이 구조는 오류 발생 시 사용자가 진단 정보를 다른 시스템(예: 개발 도구/이슈 트래커)으로 넘기는
  기능과 잘 어울린다 — 접수/폴링으로 오류가 명확히 분리되면, 오류 옆에 "실행·노드·오류 정보를 담은
  진단 요청문"을 자동 생성해주는 기능을 붙이기 쉬워진다.
- 접수-폴링 전환 자체는 가짜 실패를 없애지만, 진행 상태 판정 로직에 별도 버그(작업 ID 발급 전
  오판정 등)가 있으면 증상이 남을 수 있다 — [[false-abort-premature-status-check]]도 함께 점검한다.
