# 기능 명세의 적용 대상 모호성: 텍스트 vs 파라미터

## 언제 쓰는가
사용자가 새 슬라이더/토글 같은 조절 요소를 "대사를 도와줄 수 있게" 식의 동사로만 설명하고, 그
조절 값이 **(a) 텍스트 콘텐츠 자체를 변경**하는 것인지 **(b) 콘텐츠는 그대로 두고 하위 처리
파라미터(음성 합성의 강도·속도, 이미지 생성의 시드 등)만 바꾸는 것**인지 명시하지 않을 때. 둘 다
"대사를 도와준다"는 표현과 기술적으로 양립 가능해, 구현자가 더 익숙하거나 먼저 떠오르는 해석(LLM
재작성)으로 치우치기 쉽다.

## 절차 (단계별)
1. 조절 요소가 **콘텐츠를 바꾸는지, 그 콘텐츠를 소비하는 하위 파이프라인(TTS, 렌더러 등)의 파라미터를
   바꾸는지**를 구현 전에 한 문장으로 되묻거나, 사용자가 이미 준 맥락(예: "음성이 생성될 때")을
   먼저 찾는다. 이 세션에선 "대사를 도와줄 수 있게"만 보고 ①로 단정했으나, 바로 다음 문장이
   "한번 음성이 생성되면 재생만"이라 음성 관련 맥락이 이미 바로 옆에 있었다 — 인접 문장을 묶어
   읽었어야 했다.
2. 두 해석이 구현 난이도·되돌리기 비용에서 차이가 크면(여기선 "대사 다듬기 버튼 추가/제거" vs
   "TTS 요청 파라미터 연결+흥분도별 음성 재생성") 먼저 작게 확인 질문을 하는 쪽이 전체 왕복을
   줄인다. 이 세션은 되묻지 않고 바로 (a) 해석으로 구현·테스트·**2회 배포**까지 마친 뒤에야
   정정받았다.
3. 정정을 받으면 **콘텐츠는 보존하고 파라미터 경로만 다시 연결**한다 — 이미 만든 UI(슬라이더)는
   재사용 가능한 경우가 많고, 바뀌는 건 그 값이 흘러가는 하위 호출(TTS API의 강도/속도 인자)뿐이다.
4. 파라미터가 바뀌면 **캐시 단위도 그 파라미터를 포함해야 한다** — 이 경우 같은 대사라도 흥분도가
   다르면 별도 음성 파일로 저장해야 했다(대사 텍스트만으로 캐시 키를 잡으면 흥분도 변경이 반영 안
   되는 2차 버그로 이어졌을 것).

## 주의사항 / 함정
- "다듬는다/도와준다" 류의 동사는 거의 항상 LLM 재작성을 연상시키지만, 실제로는 수치형 조절
  UI(슬라이더·드래그)일수록 **하위 파라미터 제어**일 가능성이 더 높다 — 좌우 드래그로 "다듬는" 텍스트
  편집 UX는 드물고, 좌우 드래그로 강도·속도를 조절하는 UX는 흔하다. UI 형태(슬라이더)가 이미 단서였다.
- 오해로 구현해도 테스트·빌드·브라우저 확인·배포가 전부 "통과"할 수 있다 — 그 통과는 **구현이
  내적으로 일관됨**을 증명할 뿐, **요구사항과 일치함**을 증명하지 않는다. 정정 전 2회 배포 모두
  "테스트 N개 통과"로 보고됐다.
- 사용자가 짧게 던진 두 요청(①선택지 답변+이동, ②흥분도)을 한 턴에 같이 처리할 때, 뒤 요청은
  앞 요청보다 설명이 짧아지는 경향이 있다(이 세션에서도 흥분도 설명이 1줄뿐) — 짧은 설명일수록
  맥락(바로 다음 문장의 "음성이 생성될 때")을 더 적극적으로 끌어와 해석해야 한다.
