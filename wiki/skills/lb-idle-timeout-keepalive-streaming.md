# 로드밸런서 유휴(idle) 타임아웃 — 진단과 킵얼라이브 스트리밍 수정

## 언제 쓰는가
API가 AWS ALB/ELB, nginx 같은 프록시 뒤에 있고, 클라이언트가 **결과가 전부 완성된 뒤에야 한 번에
응답받는 동기 엔드포인트**(비전 라벨링 배치, LLM 카피 생성·채점 등)를 호출할 때 정확히 60초(또는
프록시 설정값) 근처에서 504가 재현성 있게 난다면 이 절차를 쓴다. "느려서 타임아웃"이 아니라
"응답을 한 번에 늦게 보내서 유휴 연결로 오인됨"이 진짜 원인인 경우가 많다.

## 절차 (단계별)
1. **오진 함정을 피한다** — 처음엔 "AI 프로바이더 자체 엣지 게이트웨이 타임아웃"처럼 그럴듯한 다른
   원인을 의심하기 쉽다(이전에 비슷한 증상을 다른 원인으로 겪은 전례가 있으면 더 그렇다). 수정을
   배포한 뒤에도 **원본 페이로드로 운영 엔드포인트를 직접 재현**해서 실제로 해결됐는지 반드시
   재검증한다 — 안 됐다면 오진이었다는 뜻이니 계속 원인을 좁혀야 한다.
2. **정확한 시간을 실측한다** — `curl`이나 스크립트로 실제 운영 엔드포인트에 무거운 요청을 보내
   504가 나는 정확한 소요 시간을 잰다(예: 60.05초). 이 숫자가 애플리케이션 자체 타임아웃 설정과
   다르면(애플리케이션은 90초·150초로 늘려놨는데도 60초에 죽는다면) **애플리케이션 바깥의 인프라
   레이어**를 의심한다.
3. **인프라 레이어를 특정한다** — `dig`로 도메인이 가리키는 주소를 확인하고, 그 주소가 EC2 인스턴스
   퍼블릭 IP와 다르면 로드밸런서를 거친다는 뜻이다. `aws elbv2 describe-load-balancers`로 어떤 ALB가
   그 도메인을 프론트하는지 확인 — AWS ALB의 기본 유휴 타임아웃은 **60초**다.
4. **권한을 먼저 확인한다** — ALB 속성(idle timeout)을 늘릴 수 있는 IAM 권한
   (`elasticloadbalancing:DescribeLoadBalancerAttributes` 등)이 있는지 확인한다. 없으면 인프라
   설정을 바꾸는 근본 해결은 불가능하므로 애플리케이션 레이어에서 우회해야 한다(아래 5).
5. **애플리케이션 레이어 우회 — 킵얼라이브 스트리밍**: 무거운 작업이 진행되는 동안 클라이언트에
   **일정 주기(예: 15초)로 작은 바이트를 흘려보내** 로드밸런서가 항상 "활성 트래픽"으로 인식하게
   만든다. HTTP 상태 코드는 스트림의 첫 바이트에서 이미 커밋되므로, 이 방식을 쓰는 엔드포인트는
   **항상 200을 반환**하고 실제 성공/실패는 `{ok: true, data}` / `{ok: false, error}` 같은 응답
   봉투(envelope)로 표현해야 한다 — 호출부(프론트엔드 등)가 이 봉투를 풀어 기존 성공/에러 처리
   경로로 되돌리는 어댑터가 필요하다.
6. **배치/동시성도 함께 줄인다** — 킵얼라이브만으로 부족하면(가정용/제한된 업로드 대역폭에서 여러
   요청이 동시에 대역폭을 나눠 쓰면 개별 요청이 오히려 길어져 여전히 타임아웃권에 들어갈 수 있음)
   배치 크기를 줄이고(예: 8→4) 동시 실행 수도 줄인다(예: concurrency 6→1, 순차 실행). 두 조치를
   함께 하면 여유(margin)가 배로 커진다.
7. **실측으로 마진을 확인한다** — 축소된 배치/동시성으로 같은 운영 엔드포인트를 다시 재보고, 원래
   60초 임계 대비 몇 배 여유가 생겼는지(예: 11.9초 = 5배) 기록해둔다.

## 주의사항 / 함정
- **URL 상태 동기화와 충돌할 수 있다** — 응답이 기존엔 즉시(또는 504로 빨리) 오던 것이 킵얼라이브
  덕에 정상적으로 60~130초+ 걸리게 되면, 그 사이에 다른 코드 경로(예: `?run=<id>` URL을 세팅해
  히스토리 복원 이펙트를 트리거하는 코드)가 **아직 완료 안 된 상태를 조회해 UI를 잘못된 상태로
  덮어쓰는 경쟁(race) 버그**가 새로 드러날 수 있다. 이전엔 창이 좁아 안 보였을 뿐, 킵얼라이브가
  버그를 만든 게 아니라 **드러나게 한 것**이다. 자기가 유발한 상태 변경과 진짜 외부 네비게이션을
  구분하는 플래그를 둬서 고친다.
- **오래 걸리는 요청은 항상 200을 반환하게 되므로**, 이 엔드포인트를 호출하는 모든 클라이언트가
  `{ok:false}` 봉투를 에러로 처리하도록 함께 바꿔야 한다 — HTTP 상태 코드만 보고 에러를 판단하던
  기존 클라이언트 코드가 있다면 그 부분을 놓치기 쉽다.
- 배치 크기·동시성 축소는 처리량을 희생하는 트레이드오프다 — 전체 작업 시간이 길어지는 대신
  개별 요청의 타임아웃 위험이 줄어든다는 점을 사용자에게 명시한다.
