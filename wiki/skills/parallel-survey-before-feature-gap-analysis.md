# 기능 구현 전 병렬 서베이로 갭 분석

## 언제 쓰는가
사용자가 (다른 제3자가 작성했을 수도 있는) 장문의 제품 요구사항 문서를 붙여넣고 "여기 없는 기능을
만들어달라"처럼 넓고 모호한 범위로 요청할 때. 이런 요청을 코드부터 작성해 처리하면 이미 존재하는
기능을 다시 만들거나, 기존 컨벤션(모델명, 프롬프트 파서, DDL 방식 등)과 어긋나는 새 패턴을 도입할
위험이 크다.

## 절차 (단계별)
1. 요구사항 문서를 기능 단위로 쪼갠다(표·목록·아키텍처 다이어그램이 있으면 그대로 활용).
2. 이 기능들이 걸쳐 있을 코드 영역(모듈/앱)을 3~5개로 나누고, **각 영역마다 하나씩** 서베이 에이전트를
   병렬로 띄운다. 각 에이전트에게는 "이 영역의 파일 구조·핵심 타입·엔드포인트를 나열하고, 요구사항의
   구체적 질문(예: '단어 단위 타임스탬프가 저장되는가?', '화자 구분이 있는가?')에 코드 근거(파일:줄)와
   함께 답하라"고 명시적으로 지시한다 — 막연히 "조사해줘"보다 예/아니오로 답할 수 있는 질문 목록을
   주면 결과를 갭 분석표로 바로 옮길 수 있다.
3. 모든 서베이가 끝나면 결과를 하나의 갭 분석표(요구 기능 × 현재 상태: 있음/없음/부분)로 합친다.
4. 이미 있는 기능은 절대 다시 만들지 않고 그대로 재사용하며, 없는 기능만 구현 대상으로 좁힌다. 기존
   컨벤션(공용 JSON 파서, 수동 DDL 규칙, 인증 데코레이터 등)은 서베이가 찾아낸 것을 그대로 따른다.
5. 구현 범위가 확정되면 설계 문서를 먼저 작성(이 저장소 컨벤션이면 `docs/superpowers/specs/`)한 뒤
   구현에 들어간다.

## 주의사항 / 함정
- 서베이 결과로 만든 신규 기능이라도 **하루이틀 안에 뒤집힐 수 있다** — 이 절차는 "지금 무엇이 있는지"
  갭을 좁혀줄 뿐, 새로 만든 것이 실사용 피드백에서 다시 검증돼야 한다는 점은 그대로다(예:
  `[[lampas-clip-intelligence]]`에서 에이전트 라벨링에 넣은 4축 점수가 다음 날 채점 불안정 문제로
  롤백된 사례).
- 서베이 질문이 막연하면("이 모듈 조사해줘") 결과도 막연해져 갭 분석표를 만들기 어렵다 — 반드시
  예/아니오로 답할 수 있는 구체적 질문을 사전에 준비한다.
- 서베이 도중 작업 트리에 다른 세션의 미커밋 변경이 섞여 있을 수 있다 — 서베이 결과에 "이 파일은
  최근 변경됐을 수 있음"이라는 잡음이 낄 수 있으므로, 구현 착수 전 `git status`로 현재 작업 트리
  상태를 별도로 확인해둔다.
