# LLM 채팅 첫 응답 지연 진단 (llm-chat-latency-direct-connection)

## 언제 쓰는가
한 제품에 텍스트/음성처럼 **같은 LLM을 쓰는 대화 모드가 여러 개** 있는데, 그중 하나(흔히 텍스트)만
유독 첫 글자가 나오기까지 오래 걸린다는 제보를 받았을 때. `[[toktalk]]`에서 텍스트 46.6초 vs
음성 즉각 반응 사례로 확립.

## 절차 (단계별)
1. **범위부터 좁힌다.** "왜 느리지"에 바로 코드를 뒤지지 말고, 사용자에게 정확히 어떤 앱/경로를
   말하는지 확인한다(이 사례에서 "Talk 전체"였다가 "talk-api·talk-web-app만"으로 좁혀짐 — 레거시
   경로까지 건드리면 범위가 커지고 실제 화면은 이미 다른 서버(Samantha)를 쓰고 있을 수 있다).
2. **빠른 경로와 느린 경로를 나란히 놓고 차이만 골라낸다.** 보통 세 가지 축으로 갈린다:
   - 매 요청마다 반복되는 부가 요청(세션 갱신 등) — 캐시하거나 제거 가능한지 확인.
   - 모델의 추론량(reasoning effort) 설정 — 대화용 기본 모델엔 추론을 끄거나 낮은 티어로 낮춘다.
   - 프로바이더 직접 연결 vs 게이트웨이(자체 API 게이트웨이·Atlas Cloud류) 경유 — 게이트웨이 홉
     자체가 지연의 큰 부분일 수 있다.
3. **각 축을 개별로 측정한다.** 같은 짧은 대화를 고정해 놓고 한 축씩 바꿔가며 "첫 글자까지 시간"을
   기록 — 한 번에 다 바꾸면 어느 변경이 효과였는지 알 수 없다. (실측 예: 46.6초 → 부가요청 제거만
   12.0초 → 직접연결 추가 4.3초 → 추론 끈 저지연 모델 0.6초.)
4. **기본값만 바꾸고 사용자 선택은 보존한다.** "빠른 기본 모델"로 전환하되, 사용자가 이미 특정
   모델을 직접 골라둔 경우엔 그 선택을 덮어쓰지 않는다 — 속도 최적화가 명시적 선호를 무시하면 안 됨.
5. **운영 배포 후 실측치로 보고한다.** 로컬 측정과 운영 측정이 다를 수 있으므로(캐시·리전·부하
   차이) 운영 서버에서 최소 1회 재측정해 사용자에게 알린다.

## 주의사항 / 함정
- "느리다"는 제보의 기준점이 음성 대화처럼 **다른 모드와의 상대 비교**일 때, 그 다른 모드가 이미
  쓰고 있는 연결 방식(직접 연결 등)을 그대로 베끼는 게 가장 빠른 답일 수 있다 — 새로운 최적화를
  발명하기 전에 "이미 빠른 경로가 왜 빠른지"부터 본다.
- 대상 앱 뒤에 이름이 다른 별도 서버(레거시 vs 현재 운영)가 숨어 있을 수 있다 — 코드를 고치기 전에
  실제 화면이 어느 서버를 타는지부터 확인, 아니면 죽은 코드를 고치고도 체감 변화가 없다.
- 추론량을 낮추는 최적화는 답변 품질 저하와 트레이드오프다 — 대화형·저지연이 우선인 기본 경로에만
  적용하고, 정확도가 중요한 다른 기능(분석·생성)까지 일괄 적용하지 않는다.
