# 자체 설정 vs 외부 제공자 제약 구분 진단

## 언제 쓰는가

외부 API(결제형 SaaS, AI 프로바이더 등)를 얹은 서비스에서 사용자가 "유료 결제했는데 왜 제한이 걸리나요?",
"왜 요청한 값보다 짧게/적게 적용되나요?" 같은 질문을 할 때. 원인이 ① 우리가 자체적으로 걸어둔 서버 설정,
② 외부 제공자가 우리 요청과 무관하게 강제하는 제약, 둘 중 어느 쪽인지 섞어서 추측하면 안 되는 상황.
`[[tavus]]` 연동 세션(`[[2026-09-26-virtual-toktalk-tavus-아바타-구축]]`)에서 하루 통화 한도·통화 최대
시간·미리보기 워터마크 3건을 연달아 겪으며 정립됨 — 셋 중 앞의 둘은 자체 설정, 뒤의 하나는 실제 제공자
제약으로 원인이 갈렸다.

## 절차 (단계별)

1. **자체 서버 env/설정값을 먼저 확인한다.** 증상과 관련된 이름의 env 변수(횟수 제한·시간 제한·플래그)가
   있는지 grep한다. 있으면 그 값을 그대로 사용자에게 보여주고, "이건 우리가 배포 시 정한 값"이라고
   명시한다 — 외부 제공자 요금제 탓으로 돌리지 않는다.
2. **자체 설정을 바꾸면 해결되는지 먼저 시도한다.** API 키 재발급 같은 무거운 조치를 제안하기 전에,
   env 값 변경 + 재배포로 해결되는지 확인한다. (이 세션에서 "API 키를 다시 만들어야 하나?" 질문에
   "아니요, env만 바꾸면 됩니다"로 답한 것이 정확한 사례.)
3. **자체 설정을 그대로 요청했는데도 다른 값이 실제 적용됐다면, 외부 제공자가 조용히 낮췄을 가능성을
   의심한다.** 예: 서버가 1,800초를 요청했지만 실제 통화가 정확히 900초에서 끊김 — 외부 제공자의 종료
   사유 필드(`max_call_duration` 등)를 반드시 조회해 확인한다. 요청값과 실제값이 정확히 나누어떨어지는
   숫자(15분 배수 등)로 잘리면 요금제 상한일 가능성이 높다.
4. **결제/크레딧 관련 거절(402 등)은 외부 제공자 응답 코드로 직접 확인한다.** 자체 로직이 막은 게
   아니라는 걸 증명하려면 우리 서버 로그가 아니라 외부 API가 반환한 상태 코드·에러 메시지를 인용해야
   한다.
5. **화면에 남는 표시(워터마크 등)는 영상/데이터 자체에 포함된 것인지, 우리 UI가 그린 것인지 구분한다.**
   전자라면 "사이트 설정으로 끌 수 없다"고 명확히 답하고, 제공자 공식 문서에서 해소 조건(예: 학습 완료
   후 몇 시간)을 찾아 안내한다.
6. **결론에는 항상 "이건 우리 설정 / 이건 외부 제공자 제약"을 분리해서 명시한다.** 사용자가 유료 결제
   여부를 걱정하고 있다면 특히, 결제와 무관한 자체 설정 때문이라는 걸 먼저 밝혀야 한다.

## 주의사항 / 함정

- "제공자가 결제했는데 안 된다"는 사용자 보고를 그대로 믿고 바로 제공자 탓으로 결론짓지 않는다 — 자체
  env 제한이 훨씬 흔한 원인이다.
- 반대로, 자체 설정을 요청대로 다 바꿨는데도 증상이 안 바뀌면 제공자 쪽 상한을 의심해야 한다 — 여기서
  "우리 서버 설정은 30분인데 왜 15분이지?"처럼 자체 설정 확인만 반복하다 멈추면 오답으로 굳어진다.
  실제 통화 종료 기록(제공자가 반환하는 종료 사유)까지 봐야 진짜 원인이 드러난다.
- 두 원인이 한 세션에 섞여 나타날 수 있다 — 하나를 찾았다고 나머지 증상도 같은 원인이라 단정하지 않는다.
