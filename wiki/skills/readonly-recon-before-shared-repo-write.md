# 공유 저장소 쓰기 전 읽기전용 조사 2단계 절차

## 언제 쓰는가
"저장소를 최신화하고 기존 변경을 검토해서 커밋·푸시해줘"처럼 조사와 쓰기(fetch/pull/커밋/푸시/코드
수정/배포)가 한 요청에 묶여 있을 때, 그 저장소가 **여러 에이전트·세션이 동시에 cwd로 쓸 수 있는
모노레포**(예: `lampas-system`)라면, 쓰기 작업 전에 항상 읽기전용 조사를 먼저 완결하고 사람에게
분류·위험을 보고한 뒤에만 쓰기로 넘어간다. [[2026-09-26-studio5도메인분리-models카탈로그-packaging플랫폼-유튜브]]
세션에서 경로 단위 커밋이 다른 세션의 미완성 변경을 함께 쓸어가 운영 장애까지 번진 사례
([[selective-hunk-commit-shared-file]])가 이 절차의 근거다.

## 절차 (단계별)

### 1단계 — 읽기전용 조사 (쓰기 작업 절대 안 함)
1. 기기 식별: hostname, `hw.model`(또는 동급), `pwd`.
2. git 상태: 저장소 루트·브랜치·리모트 URL·HEAD 커밋·upstream ahead/behind(fetch 없이, 로컬이
   아는 범위에서), 전체 `status`·`diff --stat`.
3. 기존 미커밋 변경을 **기능/영역 단위로 분류**한다(디렉터리·파일명 패턴으로 그룹핑) — 각 그룹의
   목적·서로의 관련성(합쳐야 하는지 분리해야 하는지)을 판단해둔다.
4. **동시 작업 확인**: 같은 저장소 경로를 cwd로 쓰는 다른 프로세스(Codex·Claude 등 에이전트 세션,
   detached worktree 포함)를 나열한다. 실제 편집 중인지·변경 소유자가 누구인지는 프로세스 목록만으로
   확정되지 않는다는 점을 그대로 보고한다 — 추측으로 단정하지 않는다.
5. 저장소 루트의 `AGENTS.md`/`CLAUDE.md`와 적용되는 `.agents/skills/SKILL.md`를 읽는다.
6. 비밀값(`.env` 내용 등)은 **절대 출력하지 않는다** — 존재 여부·경로만 언급.
7. `git diff --check`로 충돌 마커 여부만 가볍게 확인(테스트·빌드 실행은 이 단계에서 필요 없음).
8. **fetch/pull/커밋/푸시/코드수정/배포/인증설정 변경은 이 단계에서 절대 하지 않는다.**
9. 위 내용을 간결한 표/목록으로 보고: 기기·경로·git 상태·변경 분류·동시 작업 위험·안전한 다음 단계.

### 2단계 — 사용자의 명시적 재승인 후에만 쓰기
10. 사용자가 1단계 보고를 보고 **다시 한번 명시적으로** "커밋·푸시해줘" 등으로 지시한 뒤에야 쓰기로
    전환한다 — 1단계 요청문에 "커밋·푸시"가 같이 언급돼 있었어도, "읽기전용만 먼저"라는 제약이
    있었다면 재승인 없이 넘어가지 않는다.
11. 쓰기 직전 원격을 다시 확인(ahead/behind가 1단계 이후 바뀌지 않았는지)한다.
12. 1단계에서 분류한 기능 그룹별로 테스트를 돌리고, **그룹마다 별도 커밋**으로 분리한다 — 서로
    무관한 기능을 한 커밋에 묶지 않는다 ([[multi-repo-bulk-commit-push]]의 저장소 간 분리 원칙을
    저장소 1개 안의 기능 간 분리로 적용한 변형).
13. 기존에 있던 미푸시 커밋이 있다면 이번 커밋들과 함께 push한다.
14. 결과를 커밋 해시·테스트 통과 수·작업 트리 상태(clean)·로컬=원격 HEAD 일치로 보고한다.

## 주의사항 / 함정
- 1단계 요청문에 최종 목표(커밋·푸시·배포)가 적혀 있다고 해서 1단계 보고만으로 바로 쓰기로 넘어가지
  않는다 — "우선 읽기전용만"이라는 명시적 범위 제한은 별도의 사용자 확인 턴을 요구하는 게이트다.
- 동시 작업 에이전트가 발견되면, 소유자를 못 밝혀도 **커밋 범위를 경로 단위가 아니라 자기 작업이 만든
  파일 단위로 좁혀 스테이징**하는 것으로 위험을 낮춘다 — [[selective-hunk-commit-shared-file]].
- "읽기전용 조사"라는 같은 요청이 한 세션에서 멈추거나 응답이 늦어도, 다른 세션/터미널로 같은 요청을
  다시 시작하면 된다 — 중단된 세션의 조사 결과가 없다고 해서 그 요청 자체가 실패로 확정되는 것은
  아니다(다른 rollout이 몇 분 뒤 끝까지 완료한 사례 → 출처 세션).

## 변형: 활성 동시 세션 확인 시 조사에서 즉시 멈추기 (2026-10-03)
4번 단계("동시 작업 확인")에서 다른 에이전트 프로세스가 **지금도 실행 중임이 구체적으로 확인되면**
(예: 세션 로그의 시작 시각·pid, "아직 응답 없음" 등으로 살아있는 작업임을 알 수 있을 때), 1단계
보고 뒤 사용자의 재승인을 기다리는 것조차 건너뛰고 **조사 결과 보고에서 완전히 멈춘다** — 코드
수정·파일 생성 어느 것도 하지 않는다. [[2026-10-03-lampas-agent-플레이리스트구독재구축-codex작업파악]]
세션(Codex가 `lampas-agent` 플레이리스트 구독 기능을 재구축 중인 것을 Claude 세션이 교차 확인)이
이 변형의 사례다 — 단순히 "동시 작업 위험을 보고하고 재승인 기다리기"가 아니라, 활성 세션이 같은
작업 영역(같은 앱·같은 목표)을 편집 중이면 **이어받거나 산출물(계획 md 등)을 남기려는 시도 자체를
보류**하고, 먼저 그 세션을 멈추거나 역할을 나누도록 사용자에게 요청한다. 판단 기준: 동시 세션이
"다른 영역을 조용히 건드리고 있을 수도 있다"(기존 1~9단계 수준, 추측으로 단정 안 함) vs "바로 지금
내가 보려는 바로 그 코드를 활성으로 편집 중"(이 변형) — 후자는 보고만으로 끝내지 않고 작업 자체를
시작하지 않는다.
