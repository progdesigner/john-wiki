# LLM 판정기 폴백 체인 설계

## 언제 쓰는가
사용자 입력을 LLM으로 짧게 분류해 이후 동작(모델 라우팅, 우선순위, 태깅 등)을 결정해야 하는데,
그 판정 자체가 **단일 장애점**이 되면 안 될 때 — 특히 판정에 쓸 API 키/크레딧/네트워크가 불안정할
수 있는 환경(개인/소규모 운영 하네스 등).

## 절차 (단계별)
1. **판정을 가장 싼 작업으로 취급**: 분류가 한두 단어짜리 라벨링이면, 판정용 모델은 지능보다
   속도·비용을 최우선으로 고른다(예: Claude Haiku급). 실제 실행 모델과 혼동하지 말 것 — 판정 모델과
   실행 모델은 별개 선택.
2. **신뢰도 순으로 3단 폴백 체인**을 설계한다: (1) 원하는 API 판정 → (2) 로컬 LLM 판정(비용 0, 자체
   호스팅 서버 필요) → (3) 순수 휴리스틱(키워드/길이/첨부 유무 등, LLM 불필요). 각 단계는 실패
   시(타임아웃·인증오류·서버 다운) 자동으로 다음 단계로 넘어가야 하며, **최종 단계(휴리스틱)는 항상
   성공**해야 한다 — 턴 자체를 막으면 안 됨.
3. **모호하면 안전한 쪽으로 틀리게 설계**: 판정 프롬프트·휴리스틱 모두 애매한 경우 더 강한(비싼)
   모델 쪽으로 편향시킨다. "약한 모델이 어려운 일을 받는" 실패가 "센 모델이 쉬운 일을 받는" 실패보다
   비용은 크지만 결과 품질 리스크는 작기 때문.
4. **최상위/위험 티어는 안전망(휴리스틱)에서 도달 불가하게 막는다**: 가장 비싸거나 강력한 옵션은
   실제 LLM 판정(1·2단계)을 통해서만 선택되게 하고, 휴리스틱 폴백 결과에는 포함하지 않는다 — 근거
   없는 최상위 티어 남용을 방지하는 의도적 비대칭.
5. **실사용 예시로 검증**: 실제 카테고리를 대표하는 예시 5~10개(인사, 단순 조회, 문서 작성,
   구현/디버깅, 보안/아키텍처 등급 등)로 로컬/휴리스틱 판정을 실측한다. 오분류가 나오면 판정
   프롬프트에 **few-shot 예시를 추가**해 교정 — 규칙 설명보다 예시가 분류기 정확도에 더 잘 먹힘.
6. **장애 원인을 확정하고 기록**: "API 판정이 실패한다"는 관찰에서 멈추지 말고, 인증 실패인지
   크레딧 소진인지 네트워크 문제인지 실제 응답 코드/메시지로 근본 원인을 확정해 기억에 남긴다(예:
   크레딧 잔액 0 확인) — 나중에 같은 증상이 재발했을 때 재조사 없이 바로 원인을 좁힐 수 있다.

## 주의사항 / 함정
- 폴백 단계 수를 늘릴수록 "지금 실제로 어느 단계가 판정했는지"가 사용자에게 불투명해지기 쉽다 —
  결과를 표시할 때 실제 배정 결과(예: `auto·claude-sonnet-5`)만 보여줘도, 어느 단계가 판정했는지는
  로그로 남겨 사후 확인 가능하게 할 것.
- 로컬 LLM 단계에 타임아웃을 반드시 건다(예: 5초) — 로컬 서버가 응답 지연 중이면 3단계 폴백 전체가
  체감상 멈춘 것처럼 보인다.
- 크레딧/인증이 복구되면 **코드 수정 없이 자동으로 상위 단계로 승격**되도록 체인을 설계해두면,
  운영 중 재배포 없이 품질이 회복된다.
