# 관리자 가드 선례 재사용 (admin guard precedent reuse)

## 언제 쓰는가
공용 관리자 콘솔(web-admin)에 **이미 존재하는 도메인 관리자 API**를 새로 연결해야 할 때 —
"이 데이터를 admin 화면에서 보고 싶다"는 요청이 왔는데, 그 도메인의 관리자 엔드포인트는 이미
구현돼 있지만 **web-admin이 쓰는 로그인 인증과 다른 방식**으로 막혀 있는 경우. 여러 도메인 모듈이
독립적으로 개발되다 보면 각자 다른 시점에 다른 방식(도메인 전용 env 토큰 vs 로그인 JWT)으로
관리자 보호를 구현해두는 것이 흔하다.

## 절차 (단계별)
1. **막혀 있는 가드의 정체를 먼저 특정한다.** 대상 도메인의 관리자 컨트롤러가 어떤 가드를 쓰는지
   확인하고, 그 가드가 web-admin의 로그인 인증(대개 `AdminGuard` 류, 관리자 로그인 JWT 검증)과
   같은지 다른지 판단한다. 다르다면 어떤 조건으로 통과하는지(예: 도메인 전용 `*_ADMIN_TOKEN` env
   Bearer 대조)까지 정확히 읽어야 한다 — "보호돼 있다"는 사실만으론 재사용 가능 여부를 알 수 없다.
2. **같은 콘솔에 이미 통합된 자매 도메인 중 선례를 찾는다.** 신규 도메인이 아니라 이미 web-admin
   화면이 있는 다른 도메인의 관리자 컨트롤러를 찾아, 그게 `AdminGuard`(공용 로그인 인증) 패턴을
   쓰고 있는지 확인한다. 있다면 그 컨트롤러 파일명·구조를 그대로 템플릿으로 삼는다.
3. **선택지를 사용자에게 암묵적으로 정하지 말고 구조로 판단한다.** 두 갈래가 있다 — (a) 기존
   도메인 컨트롤러의 가드를 `AdminGuard`로 교체하거나 별도 `admin/<domain>/*` 컨트롤러를 신설,
   (b) web-admin이 도메인 전용 토큰을 추가로 관리. 자매 도메인에 이미 (a) 선례가 있다면 (a)를
   따르는 것이 일관성 있다 — (b)는 콘솔이 도메인마다 다른 인증 방식을 기억해야 하는 부채가 쌓인다.
4. **레거시 가드 컨트롤러의 존치 여부를 명시적으로 결정한다.** 기존 토큰 가드 경로를 그대로 두고
   신규 `AdminGuard` 경로를 병행 추가할지, 완전히 교체할지 결정하고 기록한다 — 애매하게 두면 같은
   기능에 인증 경로가 두 개 남아 나중에 헷갈린다.
5. **프론트 페이지는 콘솔의 기존 목록/상세 템플릿 컴포넌트를 그대로 복제**한다(`useState`+
   `useCallback reload`+로딩/에러 처리 패턴 등) — 인증만 통일하면 나머지 UI 뼈대는 이미 콘솔
   안에 검증된 패턴이 있다.

## 주의사항 / 함정
- **"보호돼 있으니 안전하다"고 넘기지 않기** — 도메인 전용 토큰 가드가 로그인 인증과 무관하게
  단순 env 값 대조라면, web-admin 로그인 사용자가 그 토큰을 모르는 이상 화면에서 절대 못 쓴다.
  가드 구현을 직접 열어 무엇을 검증하는지 읽어야 한다.
- **선례가 하나라도 있으면 새 규칙을 발명하지 않기** — 콘솔 안에 이미 `AdminGuard` 통합 사례가
  있는데 신규 도메인에서 또 다른 방식(예: 별도 토큰)을 만들면, 콘솔이 인증 방식을 도메인마다
  다르게 기억해야 해 유지보수 부채가 된다.
- 같은 세션에서 기능 제거(오래된 소비자 로직 삭제)와 신규 통합(관리자 화면 추가)이 섞여 있으면
  둘을 분리해 순서대로 처리하는 게 안전하다 — 제거는 [[full-stack-feature-removal-audit]] 절차,
  통합은 이 스킬.
