# 죽은 외부 CDN 도메인 이전

## 언제 쓰는가
회사 로고·첨부파일 등 정적 자산 URL이 더 이상 존재하지 않는(DNS 자체가 안 풀리는) 옛 외부 도메인
(예: 인수합병·리브랜딩 전 옛 서비스명 도메인)을 가리키고 있어서 전면적으로 깨져 보이는 경우. 단순
재배포가 아니라 (1) 원본 파일 자체를 새 버킷으로 옮기고 (2) 그 파일들을 참조하는 모든 DB 레코드의
URL을 갈아치워야 하는 시나리오.

## 절차 (단계별)
1. **원인부터 확정**: placeholder/기본 이미지가 정상 서빙되는지 먼저 확인해 "파일이 없다"가 아니라
   "가리키는 주소가 죽었다"임을 구분한다. 실제 죽은 도메인에 대한 DNS 조회(존재하지 않는 응답)로
   확정한다.
2. **S3 서버사이드 복사**: 옛 버킷의 관련 prefix 전체를 새 버킷으로 복사한다. 복사 후 반드시 **키
   목록을 대조**해 누락이 없는지 확인한다(폴더 마커류는 예외 처리해도 됨).
3. **CloudFront 신규 생성**: 새 서브도메인 별칭으로 배포를 만든다. 인증서는 새로 발급하지 말고 같은
   루트 도메인에 이미 있는 와일드카드 인증서를 재사용한다([[new-subdomain-cloudfront-wildcard-deploy]]
   와 공통). OAC로 버킷 접근을 제한하고, 버킷 정책에 새 배포 ARN을 추가한다.
4. **DB 경로 일괄 치환 전 백업 필수**: 바꾸기 전 원본 값을 통째로 백업(ndjson 등)해 둔다. 옛 도메인이
   두 가지 형태(짧은 CNAME 형태 / S3 리전 URL 형태)로 섞여 저장돼 있을 수 있으니 **둘 다** 찾아
   바꾼다. 이미 다른 이유로 깨져 있던 값(예: `/undefined/` 경로)은 이번 마이그레이션 대상이 아니므로
   건드리지 않는다 — "전부 새 도메인으로" 라는 목표가 "이미 깨진 것도 고친다"를 의미하진 않는다.
5. **코드에서 도메인 판별 로직도 같이 갈아치운다**: 옛 도메인을 화이트리스트/판별하던 모든 지점(웹·
   API·시드 데이터)을 찾아 새 도메인 기준으로 바꾼다. 하나만 놓치면 그 경로만 다시 깨진다.
6. **깨짐에 대한 방어책을 배포에 포함**: 이미지 로드 실패 시 자동으로 placeholder로 대체하는 `onError`
   처리를 추가해, DNS 전파 대기 중에도 사용자에게 아이콘이 완전히 깨진 것처럼 보이지 않게 한다.
7. **DNS가 IaC 관리 밖(3rd-party 등록업체)에 있으면 사용자 개입이 필수임을 먼저 통지**: 루트 도메인
   DNS가 Route53이 아니라 Squarespace 같은 등록업체 콘솔에 있으면 CNAME 추가를 대행할 수 없다.
   레코드 값(CloudFront 도메인)을 정확히 안내하고 등록을 기다린다.
8. **전파 확인은 공개 리졸버로**: 사용자가 "등록했다"고 하면, 여러 공개 DNS(Google 8.8.8.8, Cloudflare
   1.1.1.1)로 직접 조회해 실제 전파 여부를 확인한다. 일부 통신사·로컬 리졸버 캐시는 더 오래갈 수
   있음을 미리 안내해 둔다.

## 주의사항 / 함정
- API 서버 코드까지 반드시 그 순간에 재배포할 필요는 없다 — 운영 API가 이미 신규 도메인을 허용하고
  있다면(예: CORS/화이트리스트가 이미 관대함) 코드는 커밋만 해 두고 다음 정기 배포에 묶어도 무방.
- DNS가 3rd-party에 있다는 사실을 마이그레이션 계획 초반에 확인하지 않으면, 인프라 작업을 다 끝내고
  나서야 "마지막 한 줄"이 사용자 의존적이라는 걸 알게 돼 완료 타이밍이 어긋난다 — 가능하면 도메인의
  네임서버/DNS 관리처를 제일 먼저 확인한다.
- 옛 도메인 문자열이 여러 형태(직접 CNAME, S3 리전 경유 URL)로 저장돼 있을 수 있다는 걸 놓치면 치환이
  절반만 된다.
