# URL 형태 id를 REST 경로 파라미터로 쓸 때의 함정

## 언제 쓰는가
클라이언트 로그상으로는 "저장/삭제 요청을 보냈다"고 나오는데 서버 DB에는 반영이 안 되고, 새로고침하면
방금 추가한 항목이 사라지는 증상. 특히 항목의 id가 사람이 만든 단순 숫자/UUID가 아니라 **URL을 포함한
합성 문자열**(`u:https://cdn.example.com/a/b.png` 같은)일 때 의심한다.

## 절차 (단계별)
1. 문제가 되는 저장/삭제 요청의 **실제 운영 응답 코드**를 로그에서 확인한다 — 200처럼 보이는 낙관적
   UI 업데이트에 속지 말고, 서버가 실제로 몇 번을 돌려줬는지(404 등) 본다.
2. 그 요청이 `PUT /resource/:id`, `DELETE /resource/:id`처럼 **id를 경로 파라미터로 쓰는 라우트**인지
   확인한다. id 값 안에 `/`나 `:`, `%2F`로 인코딩된 문자가 있는지 본다.
3. 클라이언트와 서버 사이에 **리버스 프록시/로드밸런서가 있다면** 그 프록시가 경로를 정규화하는지
   확인한다(`%2F` 디코딩 후 `//`를 `/`로 합치는 동작은 nginx 등에서 흔하다) — 이 정규화가 일어나면
   클라이언트가 보낸 경로와 서버 라우트 패턴이 더 이상 일치하지 않아 조용히 404가 난다.
4. 근본 수정은 **id를 경로가 아니라 요청 본문으로 옮기는 것**이다 — 예: 기존
   `PUT /resource/:id`/`DELETE /resource/:id` 대신 `POST /resource/upsert`·`POST /resource/remove`를
   id를 포함한 바디로 받게 신설한다. 기존 경로 파라미터 라우트는 하위 호환을 위해 남겨도 된다(다른
   소비처가 있을 수 있으므로 깨끗이 지우기보다 유지).
5. 클라이언트 래퍼를 새 라우트로 교체하고, 배포 후 **운영에서 새 라우트가 올바른 상태 코드(인증
   필요 401 등 — 404가 아님)를 돌려주는지** 직접 확인한다. 404가 계속 나오면 아직 재시작/배포가
   반영되지 않았을 수 있으니 재배포 타이밍도 함께 의심한다.

## 주의사항 / 함정
- 메모리/로컬 상태에는 정상적으로 반영되므로 사용 중엔 문제를 못 느끼다가 **새로고침 후에만** 사라지는
  게 전형적인 신호다 — "가끔 저장이 안 된다"는 모호한 제보보다 "새로고침하면 사라진다"는 제보가 이
  패턴을 더 명확히 가리킨다.
- 같은 id 체계를 쓰는 다른 엔드포인트(생성뿐 아니라 삭제·수정)도 동일 문제를 갖고 있을 가능성이
  높다 — 하나만 고치지 말고 같은 라우트 패턴을 쓰는 다른 엔드포인트도 함께 점검한다.
- 같은 백엔드를 공유하지 않는 자매 서비스(예: 같은 기능이 다른 API 서버엔 아예 구현 안 돼 있는 경우)는
  이 수정의 영향을 받지 않는다 — 수정 범위를 보고할 때 어느 서비스까지 반영됐는지 명확히 밝힌다.
