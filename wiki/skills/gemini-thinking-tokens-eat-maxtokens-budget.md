# Gemini 사고 토큰이 maxTokens를 잠식해 JSON이 잘리는 함정

## 언제 쓰는가
Gemini(특히 `gemini-3.5-flash` 등 thinking 지원 모델)를 호출해 JSON 구조화 응답을 받는 기능에서
**JSON 파싱 실패/검증 거부가 간헐적으로, 특히 응답이 길어질수록 더 자주** 일어날 때. 프롬프트나
스키마를 고쳐도 재발하면 이 함정을 의심한다.

## 원인
Gemini의 "사고(thinking)" 과정이 내부적으로 토큰을 소비하는데, 이 토큰이 **별도 예산이 아니라
요청에 지정한 `maxTokens`(출력 토큰 상한) 안에서 함께 차감**된다. 모델이 사고에 토큰을 많이 쓰면
실제 JSON 본문을 쓸 토큰이 부족해져 응답이 중간에서 잘리고, 잘린 지점이 괄호나 문자열 중간이면
JSON 파서가 그대로 실패한다. 증상은 "모델이 가끔 이상한 JSON을 낸다"로 보이지만 실제로는 **토큰
예산 설계 문제**다.

## 진단
1. 실패한 응답의 **원문(raw text)을 그대로 받아** 확인한다 — 파싱 에러 메시지만 보고 넘기지 말고,
   잘린 지점이 JSON 구조 중간(예: 마지막 필드 값이 미완성)인지 직접 눈으로 본다.
2. 잘린 지점이 일관되게 `maxTokens` 근처라면(예: 매번 정확히 그 토큰 수 부근에서 끊김) 사고
   토큰이 예산을 갉아먹는 것으로 거의 확정된다.
3. 응답이 길어질수록(요청 항목 수↑, 프롬프트 복잡도↑) 실패율이 올라가는지도 함께 확인 — 사고
   시간이 길어질수록 사고 토큰도 늘어나는 상관관계가 있으면 추가 근거가 된다.

## 수정
1. **`maxTokens`를 넉넉히 올린다** — 사고 토큰 소비분까지 포함해 실제 JSON 본문이 다 들어갈
   여유를 준다. 정확한 사고 토큰량은 모델·입력마다 달라 예측이 어려우므로, 실패가 사라질 때까지
   보수적으로 큰 값을 쓴다(작게 올렸다가 또 실패하면 다시 올리는 식으로 반복하지 말고 처음부터
   여유 있게).
2. **재시도 로직을 같이 넣는다** — 한도를 올려도 드문 케이스에서 여전히 잘릴 수 있으므로, JSON
   파싱 실패 시 1~2회 재시도하는 방어선을 유지한다.
3. API가 thinking 토큰 예산을 별도로 분리 설정할 수 있는 옵션을 제공한다면(모델/SDK 버전에 따라
   다름) 그쪽으로 사고 토큰 상한을 직접 캡하는 방법도 고려할 수 있으나, 가장 간단하고 검증된
   수정은 `maxTokens` 상향이다.

## 주의사항 / 함정
- 이 문제는 "프롬프트를 더 명확히 하면 고쳐진다"는 직관과 달리 **토큰 예산 구조**의 문제라,
  프롬프트 튜닝만으로는 근본적으로 해결되지 않는다.
- 같은 모델이라도 입력이 복잡해지거나(이미지 포함, 긴 컨텍스트) 사고 시간이 늘어나는 경우가
  많으므로, 항목 수·입력 크기가 늘어나는 기능에서는 이 함정이 다시 나타날 수 있다 — 관련
  패턴: [[llm-per-item-generation-budget]](항목이 늘어날수록 출력 예산이 쪼그라드는 별개 원인).
