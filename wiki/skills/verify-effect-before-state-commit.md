# 부수효과 확인 후 상태 커밋 (verify-effect-before-state-commit)

## 언제 쓰는가
"A를 하면 B도 같이 일어나야 하는데 가끔(또는 항상) B가 안 일어난 채로 남는다"는 버그. 전형적으로
A는 **신호만 보내고 완료를 기다리지 않는 요청**(프로세스 kill, 외부 API 비동기 콜, 큐 적재)이고, B는
그 결과에 의존하는 **상태 전환의 커밋**(보관 표시, 완료 플래그, 삭제 확정)이다. `[[lampas-harness]]`의
터미널 세션 보관 버그([[2026-09-20-하네스터미널-jev검색연동-질문선택ui-보관세션종료-파일첨부]])가
전형적 사례: "보관"이 PTY 프로세스에 종료 신호만 보내고 곧바로 보관 상태를 기록해, 종료가 실제로
끝나기 전(또는 실패해도) 보관됐다고 표시됐다.

## 절차 (단계별)
1. **부수효과 호출이 "완료"가 아니라 "요청 접수"만 보장하는지 확인한다.** `process.kill()`, `fetch()`를
   응답 대기 없이 던지는 fire-and-forget 호출, 메시지 큐 발행 등은 전부 이 범주다.
2. **그 부수효과의 실제 완료를 관찰할 수 있는 지점을 찾는다.** 프로세스라면 `exit`/`onExit` 콜백이나
   상태 파일(`status: "exited"`), 외부 API라면 웹훅·폴링 응답, 큐라면 워커의 ack.
3. **상태 커밋(보관·완료 표시)을 그 완료 관찰 지점 이후로 옮긴다.** 요청을 보낸 직후가 아니라, 완료가
   확인된 콜백/폴링 안에서 상태를 기록하도록 순서를 뒤집는다.
4. **완료 확인에 실패하거나 타임아웃되면 상태를 커밋하지 않고 에러를 노출한다.** 조용히 "일단 커밋하고
   나중에 맞겠지"로 넘어가지 않는다 — 실패를 사용자가 보고 재시도할 수 있어야 한다.
5. **이미 잘못 커밋된 상태를 소급 스캔해 정리한다.** 버그가 있던 기간 동안 "완료"로 잘못 기록된 항목이
   남아있을 수 있으므로, 실제 시스템 상태(예: 여전히 실행 중인 프로세스)를 조회해 불일치 항목을 찾아
   수동 정리한다.

## 주의사항 / 함정
- **1차 수정이 "요청은 보냈으니 됐다"는 착각으로 그칠 수 있다** — 실제로 이 사례에서도 첫 수정(2026-09-20)은
  종료 요청을 보낸 뒤 곧바로 보관을 진행해, 며칠 뒤(2026-09-24) 같은 증상이 재발했다. "종료 함수를
  호출했다"와 "종료가 끝났다"를 구분하는 게 핵심이지, 종료 함수 호출 여부만 확인하고 끝내면 안 된다.
- 완료 관찰이 **비동기 콜백 안에서 별도로 상태를 저장**하는 구조라면(예: PTY `onExit`이 스냅샷을 쓰는
  경우), 그 콜백이 실행되기 전에 프로세스 자체가 죽는 레이스도 별도로 존재할 수 있다 — 이건 이 스킬로
  못 막고 [[self-hosted-agent-server-ops]] 함정 2의 SIGINT/`process.exit()` 순서 문제로 넘어간다.
- 완료 확인에 타임아웃을 두지 않으면, 부수효과가 영영 완료되지 않는 경우(좀비 프로세스 등) 상태 커밋도
  영원히 막혀버린다 — 실패 처리 경로(4단계)에 타임아웃도 포함해야 한다.
