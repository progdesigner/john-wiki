# 관리자 대행 결제·생성 — "대납"과 "대리결제" 두 패턴

## 언제 쓰는가
"관리자가 대신 ~해줄 수 있게 해줘" 같은 요청은 표면적으로 하나처럼 들리지만, 실제로는 비용
부담 주체가 다른 **완전히 반대되는 두 구현**이 있다. 어느 쪽인지 구현 전에 반드시 확인한다 —
[[2026-10-03-admin대납영상생성-first대리결제-구현]] 세션에서 같은 날 두 기능이 따로
요청됐을 때 이 구분이 드러났다.

## 두 패턴
1. **대납(subsidize)** — 플랫폼(회사)이 비용을 부담, 사용자/주문자 크레딧은 전혀 건드리지
   않음. 전제조건 없음(크레딧 잔액 무관하게 항상 가능). 회계적으로 "없었던 일"에 가까우므로
   **크레딧 원장·사용량 집계에 남기지 않는 것이 보통 의도**다 — job/리소스 metadata에만
   기록하고 일반 목록 UI에는 노출하지 않는 편이 안전(파트너 수익 집계 등 다른 지표를 오염시키지
   않기 위함). 실사례: [[lampas-web-admin]] `/jobs` "대납 생성"(`POST
   /v1/admin/ai/generate-video`) — source `ADMIN`으로만 구분, 원장 미기록.
2. **대리결제(proxy-pay)** — 주문자/사용자 **본인 크레딧에서 실제로 차감**, 일반 셀프 결제와
   동일한 규칙(가격·검증 로직 전부 재사용)을 그대로 타되 버튼만 관리자 화면에 놓는 것. **전제
   조건: 잔액이 금액 이상일 때만 허용**(클라이언트 버튼 비활성화 + 서버 동일 조건 재검증 이중
   가드). 원장에는 정상 기록하되 `createdBy: admin:<채널>` 같은 태그로 "관리자가 대신 눌렀다"는
   사실을 남긴다. 실사례: [[dalar-web-first]] admin 주문 상세 "대리 결제" — 결제 대기 주문만,
   이미 결제된 주문엔 버튼 비노출.

## 절차 (단계별)
1. 요청 문장에 "크레딧이 있는 경우에만"/"충분할 때만" 같은 **조건부 표현**이 있으면 대리결제
   패턴 신호다 — 조건이 없으면 대납 패턴 신호.
2. 비용 주체를 사용자에게 명시적으로 확인하거나(모호하면 반드시 되묻는다), 확인이 어려우면
   구현 완료 보고에서 **어떻게 해석했는지 명문화**한다("사용자 크레딧을 건드리지 않고 플랫폼이
   부담하는 방식으로 해석했다" 식) — 뒤늦게 반대 의미였음이 드러나도 되돌리기 쉽도록.
3. 대납이면: 금액 계산 로직만 재사용(단가 × 길이 등)하고 차감 로직은 호출하지 않는다. 결과는
   metadata/비공개 필드에 남겨 일반 집계와 분리한다.
4. 대리결제면: 기존 셀프 결제 엔드포인트/서비스 메서드를 그대로 호출(중복 구현 금지), 호출자
   구분용 태그만 추가한다. 버튼 활성화 조건과 서버 검증 조건이 **반드시 같은 소스**(같은 비교
   로직)를 참조하게 해 드리프트를 막는다.
5. 두 패턴 모두 실제 결제/생성 호출은 비용이 실제로 발생하므로, 구현 세션에서 **직접 눌러
   검증하지 않는 것이 합리적 기본값** — 대신 401 가드·유닛 테스트·조건 분기 테스트로 범위를
   좁혀 검증하고, "실제 실행은 안 해봤다"를 보고에 명시한다.

## 주의사항 / 함정
- "관리자가 대신"이라는 말만 보고 패턴을 섣불리 고르면 반대로 구현할 수 있다 — 첫 기능(대납)이
  실제로는 두 번째 요청(대리결제)이 가리키는 제품(First)을 염두에 둔 요청이었을 가능성이
  세션 종료 시점까지 해소되지 않았다.
- 대납 패턴을 원장에 남기면 파트너 수익·사용량 집계가 오염된다. 대리결제 패턴을 원장에 안
  남기면 "관리자가 몰래 결제했다"는 감사 불가능 상태가 된다 — 방향을 반대로 구현하면 둘 다
  문제가 된다.
- 제품마다 배포 정책이 다를 수 있다(예: 특정 제품은 "컨펌 후 배포"가 예외 규칙일 수 있음) —
  "마무리하고 바로 배포" 같은 일반 지시를 모든 제품에 동일하게 적용하기 전에 해당 제품에 대한
  과거 예외 지시가 있었는지 점검한다.
