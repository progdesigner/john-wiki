# CLI 도구 간 작업 넘기기 (트랜스크립트 파일 핸드오프)

## 언제 쓰는가
같은 작업 폴더에서 **서로 다른 CLI 코딩 에이전트**(예: Codex, Claude Code)를 번갈아 쓰는 하네스를
만들 때 — 한 도구의 세션에서 작업하던 맥락을 다른 도구의 새 세션이 이어받아야 하는 경우. 두 도구는
세션 저장 포맷·SDK가 서로 달라 세션을 직접 넘길 수 없으므로(프로세스·상태 자체의 호환이 없음),
**대화 내용을 중간 매개 파일로 직렬화**해 넘긴다.

[[cross-subdomain-session-handoff]]와 혼동하지 말 것 — 그 스킬은 **로그인 세션(인증 토큰)**을
서브도메인 간에 넘기는 것이고, 이 스킬은 **대화 맥락(무엇을 하고 있었는지)**을 이종 도구 간에
넘기는 것이다. 둘 다 "핸드오프"지만 넘기는 대상이 다르다.

## 절차 (단계별)
1. **원본 대화에서 사용자·어시스턴트 텍스트만 추출한다** — 도구 호출 결과(파일 diff, 커맨드 출력 등)는
   제외. 두 도구의 내부 트랜스크립트 포맷이 다르므로 공통분모인 순수 대화 텍스트로 정규화하는 게 가장
   이식성이 높다.
2. **작업 폴더 안에 사람이 읽을 수 있는 마크다운으로 저장한다** — 예:
   `<작업 폴더>/.lampas-attachments/handoff-<uuid>.md`. 작업 폴더 안에 두면 새 세션이 자기 파일시스템
   접근 권한만으로 읽을 수 있다(별도 API 불필요).
3. **대상 도구의 새 세션을 원본과 동일한 컨텍스트로 시작한다** — 같은 작업 폴더·제목·권한 모드·
   브라우징 유형을 그대로 승계. 컨텍스트가 어긋나면("왜 이 폴더지?") 이어받기 자체가 무의미해진다.
4. **첫 프롬프트로 "기록을 읽고 현재 상태를 직접 재확인한 뒤 이어서 진행하라"고 지시한다** — 도구
   호출 결과(diff, 테스트 결과 등)는 1단계에서 버려졌으므로, 새 세션이 `git status`/`git diff` 등으로
   **현재 작업 트리 상태를 스스로 재조사**하게 만드는 것이 핵심 보완책이다. 텍스트 기록만으로는
   "무엇을 하려 했는지"는 알아도 "실제로 뭐가 반영됐는지"는 모른다.
5. **원본 세션은 건드리지 않는다** — 종료·삭제하지 않고 그대로 둔다. 넘기기가 실패해도 원본에서
   계속 작업할 수 있는 안전망이 된다.
6. **트랜스크립트가 없는(대화 자체가 없는) 세션은 넘길 수 없게 막는다** — 넘길 내용이 없으므로
   오류로 처리하고 새 세션을 만들지 않는다.

## 주의사항 / 함정
- **모델/도구별 설정은 승계되지 않는다** — 모델 선택, 시스템 프롬프트 커스터마이징 등은 도구가
  다르면 의미가 없거나 포맷이 안 맞는다. 새 세션은 대상 도구의 기본값으로 시작한다는 걸 전제한다.
- **도구 호출 결과 유실**: 파일 수정 diff, 실행한 명령과 그 출력, 생성된 중간 산출물은 텍스트
  트랜스크립트에 없다. "최근에 뭘 고쳤는지"가 중요한 작업이라면 1단계에서 요약을 더 풍부하게
  만들거나(예: 최근 N개 커밋 메시지 동봉), 4단계의 "현재 상태 재확인" 지시에 더 구체적인 체크리스트를
  넣는 보완이 필요할 수 있다.
- **넘김 파일이 자동으로 정리되지 않으면 누적된다** — 넘길 때마다 하나씩 쌓이는 설계라면, 주기적
  정리나 보관 정책을 별도로 고려할 것(이 구현 시점엔 미해결로 남겨짐).
- **실제 CLI 바이너리 구동까지 통합 테스트하기 어렵다** — 테스트 환경 PATH에 대상 CLI가 없으면
  "인자가 올바른 형태로 전달되는지"까지만 가짜(mock) CLI로 검증 가능하고, 실제 핸드오프 체감(새
  세션이 기록을 정말 잘 활용하는지)은 실기기 수동 검증이 필요하다.
- 이 기능처럼 서버 라우트/빌드 산출물을 바꾸는 변경은 배포 전 재시작이 필요하다 — 자기 턴 안에서
  직접 재시작하지 않는 운영 원칙을 따른다 → [[self-hosted-agent-server-ops]].
