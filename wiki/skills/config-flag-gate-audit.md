# 설정 플래그 게이트 감사 (config-flag-gate-audit)

## 언제 쓰는가
"이 시스템이 [조건] 상황에서 [동작]을 하는지/막는지 확인해 줘" 같은 질문을 받았을 때. 특히 자동매매·
결제·발송처럼 실수하면 비용이 큰 자동화 동작에서, 코드를 안 읽고 "그럴 것이다"로 답하면 안 되는
경우. [[2026-07-15-dark-toss-api-장전매수-코드조사]]에서 "국장 9시 이전 매수 가능 여부"를 조사하며
정립됨.

## 절차 (단계별)
1. **정보 자체가 존재하는지 먼저 확인**: 판단에 필요한 원본 정보(세션 상태, 외부 API 필드 등)를
   시스템이 실제로 받아오는지/파싱하는지 전체 검색으로 확인한다. 없으면 "이후 로직과 무관하게 애초에
   그 정보를 안 씀"이 첫 번째 결론이 된다 (예: 토스 API 응답에 `PRE_MARKET`/`session` 필드 파싱이
   전혀 없었음).
2. **대체 판정 로직을 찾는다**: 원본 정보가 없으면 시스템이 무엇으로 대신 판단하는지 찾는다 (예: 로컬
   시계 하드코딩 `09:00~15:30`).
3. **게이트 조건문의 호출부를 전부 나열한다**: 그 판정 함수/게이트가 코드베이스에서 몇 군데서, 어떤
   함수 안에서 쓰이는지 전수 검색한다. 하나만 보고 결론내지 않는다.
4. **게이트를 잠그는 설정 플래그의 기본값을 확인한다**: 게이트 로직이 존재해도 그걸 켜는 플래그가
   기본 `false`면 실질적으로 게이트가 없는 것과 같다. 반드시 기본값을 코드에서 직접 읽는다(문서·주석
   신뢰 금지).
5. **진입점이 여러 개인지 확인한다**: 자동 루프(스케줄러) 경로와 수동 트리거(API/컨트롤러) 경로가
   분리돼 있는지 확인한다. 수동 경로가 자동 경로의 게이트를 거치지 않고 실행 함수를 직접 호출하는
   경우가 흔하다 — 이 경우 게이트가 있어도 우회된다.
6. **"코드가 막는가" vs "외부에서 거부되는가"를 구분해서 결론짓는다**: 우리 코드가 막지 않아도 외부
   서버(거래소·PG 등)가 요청을 거부할 수 있다. 이 부분은 코드로 확인 불가능하므로 "우리 코드는 막지도
   인지하지도 않는다 + 실제 성사 여부는 외부 시스템에 달려 있다"로 명확히 분리해서 답한다. 외부 시스템
   동작까지 추측해서 단정하지 않는다.
7. 답변에는 항상 `file:line` 근거를 남긴다 — 나중에 코드가 바뀌면 그 줄번호가 재검증의 출발점이 된다.

## 주의사항 / 함정
- "게이트 로직이 존재한다"와 "게이트가 실제로 작동한다"는 다르다 — 기본값이 꺼져 있으면 존재해도
  무의미하다.
- 부가 기능(예: 자동 장이동 옵션)에 딸려 있는 안전장치는 그 부가 기능 자체가 꺼져 있으면 같이
  비활성화된다는 점을 놓치기 쉽다. 실제 사례: [[dark-toss-api]]의 "양쪽 마감 시 자동판단 일시정지"는
  `autoRegionSwitch`가 켜져 있을 때만 동작 — 이 세션(23:04) 직전인 21:52~22:38
  [[2026-07-15-dark-upbit-toss-트레이딩앱-기능개발-배포]]에서 구현된 기능이다.
- 수동 트리거 경로는 감사에서 빠뜨리기 쉽다 — 자동 루프만 보고 "게이트가 있다"고 답하면 틀린다.
- 사용자가 대안(플래그를 true로 바꿀지)을 제안받고도 로그가 거기서 끝나면, 실제로 바뀌었는지 다음에
  반드시 코드를 다시 읽어 재확인한다 — 제안 자체를 결정으로 착각하지 않는다.
