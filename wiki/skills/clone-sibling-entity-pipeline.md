# 형제 엔티티 파이프라인 복제

## 언제 쓰는가
"기존 A(예: Object)와 똑같이 동작하는 새 대상 B(예: Space)를 추가해달라"는 요청을 받았는데, A의
생성→저장→선택→사용 전 구간이 이미 검증된 패턴으로 존재할 때. 새로 설계하지 말고 **계층별로 그대로
복제**하는 게 정답인 경우를 식별하는 게 핵심이다.

## 절차 (단계별)
1. **새 엔티티가 정말 없는지부터 코드로 확인**한다. 사용자가 "미완성"이라고 말해도 실제로는 이미 완성돼
   있거나(다른 위치에 있거나) 애초에 존재하지 않을 수 있다 — 셋을 구분하지 않고 바로 구현에 들어가면
   헛작업이거나 중복 구현이 된다. 확인 안 되면 화면 경로 등 **한 가지 확정 질문**만 남기고 멈춘다
   (크레딧/시간 낭비 방지).
2. **기준 엔티티(A)의 전체 배선을 계층별로 추적**한다: DB 모델 → API 모듈(controller/service/dto/module)
   → 프론트 생성 플로우(상태머신) → SDK UI(목록/생성/상세 컴포넌트+라우트+내비게이션) → 실사용 지점(여기선
   촬영 합성 이미지 슬롯). 계층 하나라도 빠뜨리면 "만들기는 되는데 쓰이지 않는" 반쪽 기능이 된다.
3. **DB부터 복제**: 같은 enum·스코프/권한 체계 재사용, Workspace/User 역참조만 새로 추가.
4. **API 모듈째 복제**: controller/service/dto 네이밍만 바꿔 그대로 옮기고 `app.module`에 등록.
5. **프론트 생성 플로우 복제**: 상태머신(예: 사진→이름→확인→저장)을 그대로 재사용.
6. **SDK UI 복제**: Atomic Design 계층(molecules/organisms/pages)과 라우트를 그대로 복제, 내비게이션에
   진입점 추가. **이 시점 API가 아직 없으면 화면은 빈 상태/저장 실패로 뜬다** — 정상이며, 다음 계층
   작업이라고 명시하고 넘어간다.
7. **실사용 지점(가장 중요한 차이)**: 새 엔티티가 실제로 "쓰이는" 지점(여기선 이미지 합성 슬롯)의 기존
   경로가 **경로별로 상태가 다를 수 있다** — 한쪽은 이미 라벨드 슬롯이 있어 무개조로 연결되고, 다른 쪽은
   슬롯이 하드코딩돼 있어 신규 슬롯 추가가 필요할 수 있다. 두 경로를 각각 확인해야 "제대로 연결됐다"고
   말할 수 있다.
8. **레이어별로 통째로 진행하지 말고, 사용자가 우선순위를 지정하면 그 순서대로**(예: "SDK 먼저") 진행하고,
   각 레이어 완료 시점마다 "아직 동작하지 않는 부분"을 명시적으로 보고한다 — 다음 레이어가 뭘 채워야
   하는지 사용자가 판단할 수 있게.

## 주의사항 / 함정
- **"만들기" 플로우를 어디에만 둘지 결정**하고 명시한다. 이 사례에서는 채팅(대화형 UI)엔 생성 플로우를
  안 넣고 SDK 웹에서만 만들도록 스코프를 좁혔다 — 모든 진입점에 전부 만들 필요는 없다.
- **검증 수단이 빌드 실패로 막히면 대체 수단을 명시**한다(예: `node_modules` 부분 설치로 vite 빌드가 안
  되면 esbuild 문법 검증으로 대체) — 단, 이게 "검증 안 함"과 동의어가 아니라는 걸 사용자에게 분명히 알려야
  한다. 배포 스크립트가 별도 미러에서 재설치한다면 그 사실도 함께.
- **레이어 하나 끝날 때마다 커밋 여부를 확정 질문**한다 — 여러 레이어를 한 번에 커밋하면 롤백 단위가
  커진다.
