# 커밋 로그 기반 개발일지 블로그 초안 작성

## 언제 쓰는가
`[[progdesigner]]`가 (블로그 URL이나 붙여넣은 원문 없이) "지난주/이번 주 진행한 내용으로 블로그 글
써줘"처럼 **콘텐츠 자체를 어시스턴트가 처음부터 작성**해야 할 때. [[naver-blog-tag-seo]]의 전제("본문은
사람에게 받아야 한다")는 **기존에 발행된 남의 글/이미 쓴 글**의 태그를 추천하는 경우에 한한다 — 이번처럼
**어시스턴트 자신이 저자**라면 본문을 따로 받을 필요가 없다.

## 절차 (단계별)
1. **기간 정하기** — 요청에 "지난주"처럼 상대 표현이 있으면 최근 커밋 로그로 실제 날짜 범위를 특정한다
   (예: 이번 세션은 7/9~7/16, 47개 커밋).
2. **git log로 원재료 수집** — 해당 기간 커밋 메시지·변경 파일을 훑어 실제로 일어난 일만 근거로 삼는다
   (지어내지 않음 — [[naver-blog-tag-seo]]의 "본문에 없는 단어 금지" 원칙과 동일한 정신).
3. **주제 클러스터링** — 커밋들을 3~5개 정도의 상위 주제로 묶는다(기능 단위가 아니라 "사용자가 체감하는
   변화" 단위로 — 예: 개별 커밋 4개를 "실시간 음성 입력 완성"이라는 한 갈래로).
4. **개발일지 톤으로 초안** — "무엇을 왜 만들었는가" 순서로 서술. 문제→해결→확인 흐름을 각 섹션에 넣으면
   (예: 버그 증상 → 원인 → 수정 → 실제 확인) 읽는 사람이 과정을 따라올 수 있어 개발일지답다.
5. **플랫폼 제약 반영** — 네이버 블로그처럼 순수 텍스트만 되는 곳이면 소제목을 `◆`/`·` 기호로 대체
   ([[naver-blog-mcp]]의 plaintext-only 제약과 동일 절차).
6. **SEO 최적화 여부 확인 후 진행** — 초안을 먼저 보여주고, 필요하면 [[naver-blog-tag-seo]] 절차로
   제목·소제목에 키워드를 자연스럽게 녹이고 태그 30개를 추가한다.
7. **발행은 별도 확인** — 초안·태그가 준비돼도 **바로 발행하지 않고** 톤/분량 조정 여부와 발행 여부를
   사용자에게 되묻는다. `naver_blog_create_post`(→ [[naver-blog-mcp]])는 사용자가 명시적으로 승인한
   뒤에만 호출.

## 주의사항 / 함정
- 커밋 메시지만 보고 "왜"까지 지어내지 않는다 — 실제 문제/해결 서술은 해당 기간 세션 기록(이 위키의
  `wiki/sessions/`)이 있으면 교차 확인하는 편이 정확하다.
- 개발일지는 연재 성격이 강하므로, 이전 편(예: [[2026-07-13-블로그-ai기억글-해시태그]])과 톤·소재가
  겹치지 않는지 확인한다.
- 발행 여부는 이 스킬의 범위 밖 — 반드시 사람 확인 후 진행([[naver-blog-mcp-posting]] 참고).
