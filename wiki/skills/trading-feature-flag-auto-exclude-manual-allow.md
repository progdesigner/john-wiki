# 자동 제외 vs 수동 허용 플래그 설계

## 언제 쓰는가
"위험하거나 아직 검증 안 된 옵션을 자동 판단(스캔/스케줄러/AI)에서는 못 고르게 하되, 사용자가 수동으로
직접 고르는 건 허용해줘" 같은 요청을 받았을 때. [[2026-07-15-dark-upbit-toss-트레이딩앱-기능개발-배포]]
세션에서 [[dark-upbit-api]] 초단타(scalping) 스타일을 다루며 두 단계에 걸쳐 정립됨 — 처음엔
"완전 비활성화"로 구현했다가, 사용자가 "자동전환만 막고 수동은 허용"으로 요구를 구체화하면서 구조를
바꿨다.

## 절차 (단계별)
1. **먼저 완전 차단(전면 OFF)으로 요청을 받았어도, "자동 vs 수동" 구분이 나중에 나올 수 있다고 가정하고
   플래그 이름부터 구분 가능하게 짓는다.** `DISABLED_STYLES`(전면) 같은 이름보다 처음부터
   `AUTO_SWITCH_EXCLUDED_STYLES`처럼 "무엇에서 제외되는지"가 드러나는 이름이 나중에 요구가 정교해질 때
   리팩터 비용을 줄인다.
2. **자동 판단 경로에서만 걸러낸다**: 자동 전환 프롬프트의 후보 목록·LLM 응답 검증 목록에서 해당
   옵션을 제외한다. LLM이 그래도 그 값을 반환하면 검증 단계에서 무효 처리(전환 안 함).
3. **수동 선택 경로는 복원한다**: `setStyle` 등 수동 변경 API의 거부 로직을 제거하고, 목록 조회
   API·프런트 드롭다운에 옵션을 되돌린다. 재시작 시 저장된 수동 선택값도 유지되게 한다.
4. **수동 선택이 자동 루프에 의해 되돌려지지 않게 보호한다**: AUTO가 돌고 있으면 다음 스캔이 스타일을
   "정상화"시키며 수동 선택을 덮어쓰는 기존 로직이 흔하다. 현재 값이 수동 전용 옵션이면 스캔은 제안
   로그만 남기고 실제 전환은 건너뛰도록 예외를 추가한다.
5. **위험 경로(고비용 LLM 호출 등)는 플래그 하나에 의존하지 않고 구조적으로 막는다**: 가능하면 해당
   옵션의 실행 엔진 자체를 위험 경로를 타지 않는 것으로 바꾼다(예: `engine: 'ai'` → `engine: 'signal'`
   로 교체해 지표 기반 판단으로 전환). 이렇게 하면 나중에 제외 플래그를 풀어도(수동 재활성화 확대 등)
   위험 경로가 재호출되지 않는다 — "플래그 끄면 다 열린다"는 취약점을 없앤다.
6. **부작용을 사용자에게 명시한다**: 엔진 교체 등으로 원래 의도(예: 1분봉 지표)와 달라진 동작(예:
   "일봉 지표를 짧은 주기로 판단")이 생기면 반드시 알린다 — 나중에 "이상하게 동작한다"는 신고로 재조사
   비용이 드는 걸 막는다.

## 주의사항 / 함정
- "자동에서만 빼줘"와 "완전히 꺼줘"는 사용자 말로는 구분 안 될 때가 많다 — 애매하면 반드시 되물어
  확인한다(이 세션에서도 첫 요청은 전면 차단이었다가 곧바로 "수동은 되게" 요구가 왔다).
- 프런트엔드가 서버 API를 따르지 않고 옵션을 하드코딩해두면, 서버 플래그를 고쳐도 UI에는 그대로 남아
  사용자가 "안 고쳐졌다"고 오인한다 — 목록 노출 지점이 서버 API 기반인지 항상 확인한다.
  ([[dark-upbit-web]] 사고 사례 참고.)
- 안전장치가 다른 부가 기능(예: 자동 장이동 옵션) ON을 전제로만 동작하면, 그 부가 기능이 꺼져 있을 때
  안전장치도 같이 죽는다 — [[config-flag-gate-audit]] 참고.
