# Vite 프로덕션 빌드가 `.env.local` 값을 물고 나가는 함정

## 언제 쓰는가
운영에 배포한 화면의 수치·동작이 **로컬 개발 환경과 똑같이** 나올 때 — 특히 "운영 집계 수가
로컬 DB 레코드 수와 정확히 일치한다"처럼 숫자가 로컬 값과 우연히 같아서 바로는 눈치채기 어려운
경우. `VITE_API_URL`처럼 API 호스트를 가리키는 env 변수가 실제로는 `localhost`를 가리키고 있을 때
흔히 나타난다.

## 원인
Vite는 `.env` 로딩 시 `.env.local`을 `.env.production` 등 모드별 파일보다 **더 높은 우선순위**로
취급한다(둘 다 존재하면 `.env.local` 값이 이긴다 — 로컬 전용 오버라이드를 의도한 Vite의 기본
동작). 개발 중 `.env.local`에 `VITE_API_URL=http://localhost:PORT`를 넣어두고 작업하다가, 그
파일을 지우거나 비우지 않은 채 프로덕션 빌드를 돌리면 빌드 산출물에 로컬 주소가 그대로
번들링된다. Vite의 env 변수는 **빌드 시점에 정적으로 치환**되므로, 배포된 정적 파일은 운영
서버에서 서빙돼도 브라우저에서 계속 localhost로 요청을 보낸다.

## 진단
1. 운영 페이지의 네트워크 요청이 실제로 어디로 가는지 브라우저 개발자도구/헤드리스 렌더로 확인
   — `localhost`나 `127.0.0.1`로 가면 이 함정이 확정이다.
2. 배포에 쓰인 저장소 루트와 앱 디렉터리에 `.env.local`이 있는지, 거기에 문제의 변수가 로컬
   값으로 들어있는지 확인한다.
3. 수치가 수상하게 "로컬과 똑같다"면(예: 로컬 DB 레코드 수 = 운영 표시 수) 이 함정을 1순위로
   의심한다 — API 호출 자체는 성공하므로 에러 로그에는 안 남는다.

## 수정
1. 배포 대상 앱(또는 모노레포 루트)의 **운영 env 파일**(`.env.production`, `.env.production.secrets`
   등 프로젝트 관례에 따름)에 올바른 값을 **명시적으로** 넣는다 — `.env.local`을 지우는 것보다
   운영 쪽에 명시하는 게 더 안전하다(다음 로컬 작업이 다시 `.env.local`을 만들어도 영향 없음).
2. 재배포 후 1번 진단을 다시 수행해 실제 요청 대상이 운영 API로 바뀌었는지 확인한다.

## 주의사항 / 함정
- 이 문제는 테스트를 다 통과해도 드러나지 않는다 — 유닛/통합 테스트는 보통 env를 직접 주입하거나
  목으로 대체하기 때문에, **배포된 산출물을 실제로 띄워 네트워크 요청을 확인하는 단계**가 없으면
  놓친다.
- `.env.local`은 git에 커밋되지 않는 게 보통이라(`.gitignore`), 다른 사람/세션이 같은 문제를
  재현하지 못해 "내 로컬에서는 멀쩡한데 운영만 이상하다"는 혼란을 만든다 — 모노레포에서 여러
  세션이 같은 앱을 건드릴 때 특히 주의.
