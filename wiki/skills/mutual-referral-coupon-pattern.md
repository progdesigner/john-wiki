# 상호 추천 쿠폰(양방향 초대 할인) 구현 절차

## 언제 쓰는가
"친구를 초대하면 둘 다 할인받는" 형태의 추천 성장 기능을 요청받았을 때 — 개인별 초대코드 발급,
코드 입력 시 초대자·피초대자 양쪽 쿠폰 지급, 기간·상품 범위 제한, 관리자 조회까지 한 세트로
구현해야 하는 경우.

## 절차 (단계별)
1. **개인 식별 코드/링크 발급** — 사용자마다 고유 초대코드를 만들고, 가입 시점 또는 가입 후
   별도 화면("친구 초대·쿠폰")에서 입력 가능하도록 두 진입점을 모두 연다.
2. **등록 트리거 시점을 명확히 정의**한다 — 예: "초대코드 입력 → 로그인 수단으로 가입 완료" 순서로
   코드가 실제 등록된다. 이 순서를 사용자에게도 명시적으로 안내한다(안내가 없으면 "코드를 입력하고
   로그인해야 하나?" 같은 문의가 반복된다).
3. **쿠폰 발급은 등록 성공 이벤트 한 번에 양쪽 계정에 동시 지급**한다 — 초대자 1장 + 피초대자 1장.
4. **어뷰징 방지 3종을 서버에서 강제**한다: (a) 자기 자신의 코드 등록 차단, (b) 같은 계정으로
   중복 등록 차단, (c) 쿠폰 발급이 결제 승인과 얽히는 경우(중복 발급) 승인 재시도 시 멱등하게
   처리 — 재시도로 쿠폰이 두 번 나가거나 적립이 중복되지 않도록 한다.
5. **쿠폰 제약을 명시적으로 데이터에 건다**: 유효기한(예: 발급일로부터 1개월, 타임존 고정),
   사용 가능 상품 범위(특정 서비스 전용), 결제 1회당 적용 장수 상한(보통 1장). 결제 승인 중
   취소 요청이 겹치는 경합(사용자가 결제 확인 중 취소 버튼을 누르는 등)도 서버에서 순서를
   보장해 처리한다.
6. **관리자 조회 화면**을 추가한다 — 사용자별 초대코드 목록, 발급된 쿠폰 리스트(발급자·피발급자·
   상태·만료일)를 한 화면에서 볼 수 있게 한다. 고객용 "내 쿠폰" 화면도 별도로 둔다.
7. **배포 전 DB 변경은 추가만**(신규 테이블·컬럼)으로 제한하고, 기존 주문·결제 데이터에는
   손대지 않는다 — 결제 관련 기능은 특히 기존 데이터 보존을 배포 검증 항목에 명시적으로 포함한다.
8. 실서버 검증은 실제 테스트 계정 두 개로 초대코드 등록 → 양쪽 쿠폰 발급 → 결제 화면에서 쿠폰
   선택 시 할인액·최종 결제액이 맞는지까지 엔드투엔드로 확인한다.

## 주의사항 / 함정
- 초대코드 로그인 직후 화면에서 **쿠폰 목록이 늦게 갱신**되는 캐시/타이밍 문제가 생기기 쉽다 —
  가입 직후 첫 진입 시 쿠폰 목록을 강제 재조회하도록 한다.
- 결제액이 "제작비/상품가 + 부가세" 같은 파생값이면, 쿠폰 할인은 **최종 결제액에 적용한 뒤
  각 상품 구간별 할인 후 금액표를 다시 계산**해 표시해야 한다 — 가격 정책이 이후에 또 바뀌면
  (예: 부가세 포함 가격으로 재조정) 할인 후 금액표도 같이 재계산해야 하는데 놓치기 쉽다.
- "쿠폰 적용 시 결제액"을 표시할 때 크레딧 적립량 등 내부 회계 단위는 고객 화면에 노출하지
  않는 편이 요청 맥락에 따라 더 명확할 수 있다(크레딧-원화 환산이 사용자 혼란을 준다는 피드백 사례).
