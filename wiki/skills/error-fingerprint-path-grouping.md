# 오류 경로 fingerprint 그룹핑

## 언제 쓰는가
오류 수집·자동 수정 시스템에서 "같은 원인, 다른 요청"의 오류가 URL/스택 안의 가변 값(리소스 id,
해시, 토큰) 때문에 서로 다른 건으로 갈라져 목록이 부풀 때. 예: `HTTP 500 GET
/v1/ai/model/prediction/4617ffc80bf8423dba292f2d478e3a48`처럼 매 요청마다 id가 달라 원인은
하나인데 오류 건수만 계속 늘어나는 상황.

## 절차 (단계별)
1. 메시지·스택 문자열에서 uuid, hex 문자열, 순수 숫자, 불투명 토큰, `run_xxx` 형태의 실행 id, 번들
   해시 등 **요청마다 달라지는 패턴**을 식별해 `:id` 또는 `:hash`로 치환하는 순수 함수를 만든다(부수
   효과 없이 문자열 → 문자열 변환만).
2. 이 정규화된 문자열을 fingerprint 키로 써서 같은 키를 가진 오류를 하나의 레코드로 누적한다 —
   발생 횟수를 합산하고, 원본 메시지는 전부 버리지 말고 최근 N개(예: 5개)만 상세 보기용으로 남긴다.
3. **리포터 자신이 만든 요청 오류는 fingerprint에서 제외한다.** `HTTP nnn`, `Network request …`,
   `Resource load failed` 같은 오류는 스택이 리포터 코드 프레임뿐이라 브라우저 엔진마다 스택이
   달라지고, 그대로 fingerprint에 넣으면 같은 오류(예: 같은 401)가 엔진별로 여러 건으로 갈라진다.
4. 이 로직을 도입하는 시점에 **기존에 쌓인 레코드도 한 번 재그룹**하는 마이그레이션을 데몬 최초
   기동 시 돌린다 — 신규 오류만 그룹핑하면 과거 데이터는 계속 부풀어 있는 채로 남는다.
5. **릴리스(배포 버전)가 다르면 fingerprint가 같아도 별건으로 유지**한다 — 그래야 "수정 배포 후
   같은 오류가 재발했는지"를 배포 이전 누적 건수와 구분해서 판단할 수 있다. 이 규칙을 fingerprint
   그룹핑 도입으로 깨뜨리지 않도록 주의한다.

## 주의사항 / 함정
- fingerprint 정규화 범위를 너무 넓게 잡으면(예: 모든 숫자를 치환) 실제로 다른 원인의 오류까지
  하나로 묶여 원인 파악이 어려워진다 — id/hash로 보이는 패턴만 좁게 치환한다.
- 리포터 프레임뿐인 스택을 fingerprint에 그대로 포함시키면 브라우저 엔진 차이로 같은 오류가
  쪼개진다 — 이런 오류 유형은 fingerprint 계산에서 스택을 아예 제외하는 게 낫다.
- 재그룹 마이그레이션은 발생 횟수 합산뿐 아니라 그 레코드에 연결된 작업 기록(수정 시도 이력 등)도
  함께 이관해야 한다 — 이관을 빠뜨리면 병합된 레코드의 과거 처리 이력이 사라진다.
- DB 사본으로 마이그레이션 드라이런을 할 때 단순 파일 복사는 WAL(Write-Ahead Log)을 놓쳐 최신
  데이터가 반영 안 된 사본이 될 수 있다 — SQLite라면 전용 백업 방식(예: `.backup` 명령)으로 복사한다.
