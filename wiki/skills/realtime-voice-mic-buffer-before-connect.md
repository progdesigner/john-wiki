# 실시간 음성 입력 — 연결 전 마이크 버퍼링 + 3단계 시각 피드백

## 언제 쓰는가
버튼을 누르는 즉시 원격 음성 인식 서버(OpenAI Realtime 등)에 WebSocket으로 연결해 스트리밍 전사하는
push-to-talk UI를 만들 때. "말하는 게 처음에 좀 끊긴다"는 증상이 있거나, 애초에 토큰 발급→연결
과정이 있는 구조라면 십중팔구 이 문제를 안고 있다.

## 문제
순진한 구현은 다음 순서로 동작한다:
1. 버튼 누름 감지(길게-누르기 판정, 보통 0.3~0.5초)
2. 서버에서 임시 토큰 발급 요청 (네트워크 왕복)
3. 토큰으로 원격 WebSocket 연결
4. **연결 완료 후에야** 마이크 캡처 시작

2~3단계에 걸리는 0.5~1.5초 동안 사용자가 이미 말을 시작했다면, "녹음 시작" UI가 뜨기도 전에 나온
음성은 **캡처 자체가 안 되어 통째로 유실**된다. 판정 지연(1단계)까지 더하면 체감 손실은 더 크다.

## 해결 — 마이크 선오픈 + 로컬 버�퍼 + 연결 후 순서대로 플러시
1. **길게-누르기 판정 통과 즉시 마이크 캡처를 시작**한다. 토큰 발급/WebSocket 연결과 **병렬로** 진행.
2. 캡처된 오디오 청크는 연결이 완료될 때까지 **로컬 배열(버퍼)에 순서대로 적재**한다.
3. WebSocket이 열리면 **버퍼에 쌓인 청크를 먼저 순서대로 전송**한 뒤, 이후 청크는 실시간으로 바로 전송.
4. 손을 짧게 떼서 바로 종료해도, 아직 연결이 안 끝났다면 **연결을 기다렸다가** 버퍼를 마저 흘려보내고
   종료 처리(전사 마무리)한다 — 연결 중 뗀다고 캡처된 오디오를 버리지 않는다.

이렇게 하면 실질 유실 구간은 **"버튼에 손이 닿는 순간부터 마이크 캡처가 실제로 열리기까지"**
(길게-누르기 판정 시간 + OS 마이크 오픈 지연, 보통 0.5초 미만)로만 줄어든다. 이 구간은 물리적으로
녹음 자체가 없으므로 소프트웨어로는 더 줄일 수 없다(판정 임계값을 낮추는 것 정도가 유일한 레버).

## 남는 유실 구간을 시각적으로 구분하기 (3단계 피드백)
"어디까지가 안전한지"를 사용자가 눈으로 알 수 있게 버튼 상태를 3단계로 나눈다:

| 단계 | 색 | 조건 | 의미 |
|---|---|---|---|
| 준비중 | 노랑 | 누름 감지~마이크 오픈 완료 전 | **이때 말한 건 잘릴 수 있음** |
| 녹음중 | 빨강 (깜빡임) | 마이크 캡처 시작~음성 미감지 | 유실 없음, 아직 음성 미감지 |
| 인식중 | 초록 (깜빡임) | 원격 서버의 음성 감지 이벤트 수신 이후 | 실제로 전사되고 있음 (가장 신뢰도 높은 신호) |

3단계 경계의 핵심은 **원격 서버가 보내는 음성 감지 이벤트**(OpenAI Realtime는 `speech_started`)를
그대로 상태 전환 트리거로 쓰는 것 — 클라이언트 자체의 볼륨 임계값 추정보다 정확하고 구현이 간단하다.
문장이 끝나 조용해지면 빨강으로 돌아오고, 이어 말하면 다시 초록.

## 검증 방법
1. 버튼을 누르자마자 즉시 말을 시작 → 노랑 구간에서 앞부분이 가끔 잘릴 수 있음(정상, 물리적 한계).
2. 빨강/초록으로 바뀐 뒤 말을 시작 → **항상 온전히 처음부터 나와야 함**. 이게 깨지면 버퍼링 순서나
   플러시 로직에 버그가 있는 것.
3. macOS `say` 등으로 합성한 음성을 파이프라인에 흘려 전사 정확도를 자동 검증할 수 있다(수동 발화보다
   재현 가능).

## 추가로 함께 넣을 만한 UX — 밀어내기 취소(swipe-to-cancel)
메신저 음성메시지와 동일하게, 녹음 중 버튼에서 일정 거리(예 60px) 이상 벗어나면 회색 "떼면 취소"
상태로 전환하고, 그 상태에서 떼면 전송하지 않는다. 단, **받아쓴 텍스트는 버리지 않고 입력창에 남겨서**
사용자가 고쳐 쓰거나 수동으로 보낼 수 있게 하는 편이 낫다(완전 폐기보다 안전).

## 주의사항 / 함정
- 버퍼 전송은 반드시 **캡처 순서 보존**이 필요 — 병렬 처리 중 순서가 뒤바뀌면 전사가 뒤섞인다.
- 원격 서버가 초 단위가 아니라 진짜 청크 단위 스트리밍을 요구하면(OpenAI Realtime처럼) 버퍼도 같은
  청크 포맷으로 쌓아야 재생 시 별도 인코딩 변환이 필요 없다.
- 토큰 발급 자체가 실패하는 경우(크레딧 부족 등)까지 이 패턴이 커버하진 않는다 — 그건 별개 계층 문제.
