# 세션 독립 예약 메시지 스케줄러

## 언제 쓰는가
에이전트가 "10초 뒤에 알려줘", "5분 뒤 리마인드" 같은 **미래 시점 능동 메시지**를 보내야 할 때.
에이전트 턴 안의 타이머(`sleep`, `ScheduleWakeup` 등)는 턴/세션이 끝나면 죽어 알림이 유실된다
(→ [[harness-background-process-lifecycle]]). 타이머를 **서버로 옮겨** 이 문제를 없앤다.

## 절차 (단계별)
1. **서버에 스케줄러 모듈 신설** (`src/scheduler.ts` 류). 예약을 메모리가 아니라
   **파일로 영속화**한다: `queue/scheduled/<id>.json` 등. 각 파일에 `deliverAt`(절대 시각),
   `chatId`, `message`, 상태를 담는다.
2. **서버가 폴링**: 항상 살아 있는 서버 프로세스가 짧은 간격(예 0.5초)으로 스캔해
   `deliverAt`이 지난 예약을 채팅 히스토리에 적재하고 파일을 완료 처리/삭제.
   → 서버가 재시작돼도 파일이 남아 예약 생존, **지나간 예약은 기동 즉시 전달**.
3. **에이전트에 MCP 도구 주입**: `schedule_message` / `list_scheduled` / `cancel_scheduled`.
   시스템 프롬프트에 "예약 요청은 타이머 대신 이 도구를 써라"고 명시.
4. **정확도 — 도착 시각 기준 계산**: 서버가 **사용자 메시지가 도착한 시각**을 기억해뒀다가
   `deliverAt = 도착시각 + N`으로 계산. 에이전트가 도구를 늦게 호출하거나 오래 생각해도
   "N초 뒤"가 보낸 순간 기준으로 정확해진다. (도구 호출 시각 기준으로 하면 지연이 누적됨.)
5. **UI**: 큐/예약 패널에 "⏰ 예약 · N초 후" 카운트다운 + 취소 버튼. 전달 시각에 채팅창 자동 표시
   (곧 전송될 예약이 있으면 폴링 간격을 촘촘히).
6. **검증**: 서버 재시작을 끼운 예약이 예정 시각에 도착하는지 확인. 재시작 소요를 감안한
   버퍼(예 60초)로 첫 테스트를 걸면 재시작-후-전달 경로까지 검증된다. (단독 테스트 목표 대비 +11ms 관찰.)

## 주의사항 / 함정
- **에이전트 타이머로 절대 하지 말 것** — 세션 살아 있을 때만 되고, 턴 종료 후엔 유실된다.
- 클라이언트 탭이 옛 UI면 실시간 표시가 안 되므로 배포 후 **새로고침** 안내 필요.
- 아주 긴 지연(수 시간)은 서버 폴링보다 launchd/cron이 하네스 API를 호출해 새 턴을 트리거하는
  방식이 더 견고할 수 있음.
