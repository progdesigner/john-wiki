# CDN 뒤 S3 산출물은 고정 키로 덮어쓰지 않는다

## 언제 쓰는가
사용자가 "다시 만들었는데 결과물이 그대로다/예전 버전이다"라고 제보했는데, 서버 로그·DB
기록으로는 재생성이 실제로 일어났고 새 파일도 정상 업로드된 것이 확인될 때. 특히 최종 산출물이
**항상 같은 S3 키**(`first/{orderId}/{generation}/film.mp4`처럼 회차 단위로만 구분되고, 같은
회차 내 재렌더는 같은 키를 덮어씀)이고 그 앞에 CloudFront 같은 CDN이 붙어 있는 구조일 때
의심한다.

## 진단
1. 브라우저/curl로 해당 URL의 응답 헤더를 직접 확인한다 — `Last-Modified`가 방금 재생성한
   시각이 아니라 **훨씬 이전**이고, `X-Cache: Hit`, `Age`가 캐시 TTL과 맞아떨어지면 확정이다.
   (예: `last-modified 18:11:57 · x-cache: Hit · age 4226초` — 실제로는 19:16에 다시
   렌더·업로드됐는데도 18:11 버전이 계속 내려감.)
2. 같은 URL을 재사용하는 다른 기능(예: "이전 회차 영상 보관/제공 이력")도 함께 점검한다 — URL이
   전부 동일하면 그 기능도 실질적으로는 전부 같은(최신으로 덮어써진) 파일 하나만 가리키고 있어
   "보관"이 이름뿐일 수 있다.

## 절차
1. 즉시 조치: 해당 URL을 CDN에서 **무효화(invalidate)**해 최신 파일이 내려가는지 확인한다
   (근본 수정 전 임시 완화).
2. 근본 수정: 렌더/생성 결과물의 S3 키에 **렌더 시각 또는 고유 id를 포함**시킨다
   (`film-{timestamp}-{id}.mp4`). 회차(generation) 번호만으로는 부족하다 — 같은 회차 안에서
   여러 번 재렌더(컷 재생성→최종 편집 재실행)가 일어날 수 있기 때문이다.
3. "이전 버전 보관" 기능이 있다면, 새 키 발급 방식으로 바꾼 뒤에는 **파일이 실제로 남아있으므로**
   과거 URL이 그대로 유효하다 — 별도 백업 로직 없이 자연히 동작한다.
4. 이미 캐시에 박제된 과거 URL(수정 전에 덮어쓴 것들)은 복구 불가능함을 인지한다 — 새 키 방식을
   적용한 시점 이후의 렌더부터 정상적으로 버전이 분리된다.

## 주의사항 / 함정
- 코드·DB 기록만 보고 "재생성이 안 된 것 같다"고 오판하지 않는다 — 서버 사이드는 정상 동작했고,
  문제는 순수하게 CDN 캐시 계층에 있을 수 있다. 응답 헤더(`Last-Modified`/`X-Cache`/`Age`)를
  직접 확인하는 게 가장 빠른 확진 경로다.
- 고정 키에 CDN을 얹는 패턴 자체가 "값은 안 바뀌는데 URL 주소 체계상 계속 갱신돼야 하는 자원"
  (예: 사용자 아바타, 설정 파일)에서 반복적으로 재발하는 함정이다 — 새 리소스를 설계할 때
  "이 키가 같은 내용으로 여러 번 재생성될 수 있는가?"를 먼저 자문한다.
