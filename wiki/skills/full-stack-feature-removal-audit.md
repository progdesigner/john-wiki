# 기능 전면 제거 감사 (full-stack feature removal audit)

## 언제 쓰는가
"이 기능 이제 쓰지 마 / 완전히 지워줘"처럼, 코드베이스 여러 층(중복 프론트 파일, 백엔드
여러 실행 경로, API 라우트, 저장소 파일)에 걸쳐 심어진 기능을 **잔재(dead code·죽은 API·
유령 파일) 없이** 제거해야 할 때. 단순 "off 스위치"가 아니라 삭제 자체가 목적일 때 —
게이트만 잠그는 경우는 [[config-flag-gate-audit]] 쪽이 더 맞다.

## 절차 (단계별)
1. **조사를 삭제보다 먼저, 병렬로 끝낸다.** 기능 이름·관련 변수명(예: `preset`/`currentCat`/
   `area`)으로 프론트·백엔드 전체를 grep해 **모든 표면을 먼저 목록화**한다. 이 저장소처럼
   프론트가 이중 관리(`apps/web/index.html` vs 레거시 `public/index.html`, 빌드로 안 이어짐)라면
   두 파일 모두 대상에 넣는다 — 하나만 고치면 반쪽 배포가 된다.
2. **주입/호출 지점을 file:line으로 전수 나열한다.** "이 값이 실제로 쓰이는 곳"과 "이 값이
   전송만 되고 다른 로직엔 영향 없는 곳"을 구분해 적는다(이 경우 이미지 생성 도구 노출은
   `preset==='image'`가 아니라 API 키 존재로 게이팅되고 있었음 — 페르소나값과 무관한 로직을
   같이 지우지 않도록 이 구분이 중요).
3. **삭제 순서: UI → API 라우트 → 백엔드 로직 → 저장소 파일.** 사용자가 만질 수 있는 진입점부터
   막고, 그 다음 그 진입점이 부르던 코드를 안쪽에서 밖으로 걷어낸다. 여러 실행 경로(예: 이
   저장소의 Claude SDK/로컬-OpenAI호환/Gemini 3경로)가 있으면 각각 확인 — 하나만 지우고
   나머지에 남기는 실수가 흔하다.
4. **삭제 후 같은 키워드로 재-grep해 잔여 참조 0건을 확인한다.** 조사 단계에서 만든 목록과
   대조해 빠진 곳이 없는지 체크리스트로 소거한다.
5. **빌드/타입체크로 구조적 깨짐을 잡는다** (`tsc --noEmit`, 프론트 빌드). 특히 이중 관리
   프론트가 있으면 **둘 다** 빌드해 dist 산출물까지 반영됐는지 확인.
6. **배포는 별도 판단.** 이 저장소는 셀프호스팅 데몬이 자기 턴을 서빙 중이라 커밋/배포를
   같은 턴에서 바로 하면 위험할 수 있다 — [[self-hosted-agent-server-ops]] 참고. 조사·삭제·
   검증까지 끝내고 커밋·재시작 여부는 사용자에게 맡기는 것도 정상적인 종료 지점이다.

## 주의사항 / 함정
- **이중 관리 파일 중 하나만 고치는 실수** — 이 저장소는 `apps/web/index.html`(빌드 소스)과
  `public/index.html`(레거시 수동 사본, `dist` 없을 때만 폴백)이 완전히 별개로 관리된다.
  한쪽만 고치면 배포 환경에 따라 옛 기능이 살아있는 상태로 남는다.
- **"값은 전송되지만 무해"한 경우를 로직까지 지우지 않기** — 프론트에서 값을 서버로 계속
  보내는 것 자체는 문제가 아니다(예: `preset: currentCat`은 이 세션 후에도 계속 전송되지만
  백엔드가 무시). 값 자체를 뿌리 뽑을지, 소비하는 로직만 지울지는 요청 범위에 맞게 판단.
- **같은 이름을 쓰는 무관한 코드와 혼동 금지** — 이 저장소의 `runner.ts`에도 `preset`이라는
  필드가 있었지만 Claude Code SDK 내장 프리셋(`"claude_code"`)이라는 다른 개념이었다. 이름이
  같다고 같이 지우면 안 된다.
- 삭제 전 조사를 서브에이전트 병렬 실행으로 빠르게 끝내면(프론트 조사/백엔드 조사 동시)
  전체 절차가 짧아진다.
