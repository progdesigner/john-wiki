# 슬림 베이스 복사로 새 앱 스캐폴딩

## 언제 쓰는가
모노레포(`pnpm-workspace`, `apps/*`)에 "사용자가 입력(이미지 등) 올리면 AI가 분석/생성해 보여주는" 새
단일 화면 프론트 앱 + 그에 대응하는 백엔드 API 모듈을 처음부터 추가해달라는 요청을 받았을 때. 기존
앱이 여러 개 있다면 그중 하나를 복사 베이스로 삼는 게 새로 만드는 것보다 항상 빠르다 — 어떤 걸 베이스로
고를지가 핵심 판단이다.

## 절차 (단계별)
1. **기존 앱들을 병렬 조사로 비교**한다(package.json 의존성 수·버전, vite.config 복잡도, src 구조,
   tsconfig 분할 여부). "이 앱과 비슷한 게 이미 있는가"를 먼저 확인 — 없다면 가장 **의존성이 슬림하고
   유사한 입출력 패턴**(예: 이미지 업로드→API 호출→결과 표시)을 가진 앱을 복사 베이스로 고른다. 무거운
   앱(라우터+상태관리+대량 UI 라이브러리)을 베이스로 삼으면 걷어내는 작업이 새로 만드는 것보다 커진다.
2. **동시에 백엔드 vision/AI 분석 엔드포인트의 기존 관례를 조사**한다 — 입력 방식(multipart vs JSON
   base64/URL), 인증 가드 패턴(전역 가드 유무, `@Public()` 같은 공개 데코레이터 존재 여부), DTO 네이밍
   컨벤션. 가장 가까운 도메인 선례(예: "제품"이면 사람이 아닌 "사물" 분석 모듈)를 찾으면 새 모듈의
   서비스 메서드 시그니처를 그대로 베낄 수 있다.
3. **새 백엔드 모듈은 기존 CRUD 엔티티 모듈과 섞지 않는다** — 목적이 다르면(예: DB 기반 CRUD vs 무상태
   AI 분석) 이름이 겹치더라도 독립 모듈로 분리한다. 섞으면 책임이 흐려진다.
4. **포트/스크립트 네이밍 규칙을 그대로 따른다** — 새 포트는 기존 포트들과 겹치지 않는 값, dev 스크립트는
   `dev:<프로젝트>:web:<약칭>` 같은 기존 명명 패턴을 그대로 씀. 루트 workspace 설정(예: `packages:
   ["apps/*"]`)이 자동으로 편입해주는지 확인.
5. **배포 스크립트에도 새 앱 항목을 추가**하되, 실제 인프라(S3 버킷/CloudFront ID)가 아직 없으면
   플레이스홀더 값 + 코드 내 TODO로 명시하고 "배포는 인프라 발급 후"라고 보고한다 — 마치 배포 가능한 것처럼
   보이게 하지 않는다.
6. **검증은 새로 만든 파일만 필터링**한다 — 모노레포 전체 `tsc`/`pnpm install`이 무관한 기존 이슈로
   실패할 수 있으므로(예: 다른 워크스페이스의 미해결 의존성 문제), 새 모듈/새 앱 경로만 골라 에러 유무를
   확인하고 그 사실을 사용자에게 명시한다.

## 주의사항 / 함정
- **입력 형식을 확인 없이 multipart로 설계하지 말 것** — 모노레포 전체를 grep해서 기존에 파일 업로드
  방식이 있는지 먼저 확인한다. 없다면 관례(JSON base64/URL)를 따르는 게 일관성 있다.
- **완전 공개(비로그인) 엔드포인트가 필요하면 전역 가드 구조부터 확인**한다. 전역 `APP_GUARD`가 없고
  컨트롤러 레벨 가드만 있는 구조라면, 핸들러에 `@Public()`류 데코레이터만 붙이고 로그인 전용 가드는
  붙이지 않는 조합으로 공개 처리한다.
- **저장소 전체 `pnpm install`이 실패해도 새 앱 검증을 포기하지 않는다** — `nodeLinker: hoisted`라면
  루트 `node_modules`가 이미 존재하는 한 새 앱은 독립적으로 `tsc -b`/`vite build`가 가능하다. 실패
  원인이 무관한 기존 워크스페이스 문제인지 반드시 구분해서 보고한다.
- pnpm이 PATH에 없거나 샌드박스가 `/tmp`·`/var/folders`를 막으면 저장소 안에 corepack shim을 만들어
  우회한다 → [[deploy-sandbox-pnpm-shim]].
