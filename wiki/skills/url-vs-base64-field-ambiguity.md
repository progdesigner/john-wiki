# URL vs base64 필드 모호성

## 언제 쓰는가
업로드·외부 전송용 API가 이미지/파일을 "URL 아니면 base64" 둘 중 하나로 받는데, 필드 하나(`imageData`
같은)가 **두 형태를 모두 수용할 수 있어 보이는** 상황. 외부 서비스가 "이미지 형식을 지원하지 않는다"처럼
형식 오류를 내는데 실제 원본 파일은 멀쩡해 보일 때 의심한다. 증상은 보통 업로드 성공률이 낮거나(거의
항상 실패, 아주 가끔만 성공), 결과 파일 크기가 원본과 무관하게 비정상적으로 작다.

## 절차 (단계별)
1. 실패 건의 **최종 전달 바이트**를 직접 확인한다 — 서버가 실제로 외부 API에 보낸(또는 S3에 올린)
   파일을 받아 헤더(`PNG`/`JPEG` 매직 바이트 등)가 있는지, 크기가 원본과 비슷한지 본다. 크기가
   입력 문자열 길이의 3/4 근처(base64 디코딩 비율)면 "URL 문자열을 base64로 잘못 디코딩"을 강하게
   의심한다.
2. 데이터가 클라이언트(엔진/프론트)에서 서버로 가는 **전체 경로**를 따라가며, 각 단계가 값을
   "URL 문자열"로 다루는지 "base64 payload"로 다루는지 확인한다. 중간에 "이미 URL이면 그대로
   반환"하는 변환 함수가 있는지가 핵심 — 그 함수의 이름이 `toDataUrl`/`resolveImage`처럼 "항상
   data URL을 만든다"고 암시해도 실제로는 http(s) 입력을 그대로 패스스루할 수 있다.
3. 받는 쪽(서버)이 필드 값의 **형태를 판별하지 않고 무조건 한 가지로 처리**하는지 확인한다
   (`Buffer.from(value, 'base64')`를 조건 없이 호출하는 식). 이게 근본 원인이다 — 보내는 쪽의
   버그가 아니라 받는 쪽이 입력을 검증하지 않는 것.
4. 수정은 **양쪽에 방어선을 둔다**: 보내는 쪽은 원본이 URL이면 URL 전용 필드(`imageUrl`)로, base64만
   필요할 때만 data URL 필드(`imageData`)로 명확히 분리해 보낸다. 받는 쪽도 값이 `http(s)://`로
   시작하면 base64 디코딩을 건너뛰고 URL로 처리하도록 방어 코드를 추가한다(보내는 쪽 수정이 전
   클라이언트에 전파되기 전의 과도기 대비).
5. 같은 기능을 공유하는 다른 소비처(예: 여러 모델·여러 API 파사드)가 같은 필드를 쓴다면 전부 같은
   버그를 갖고 있을 가능성이 높다 — 영향 범위를 하나의 모델/경로로 한정하지 말고 전체 소비처를
   점검한다.

## 주의사항 / 함정
- 외부 서비스의 오류 메시지("이미지 형식 미지원")가 **그 서비스만의 문제처럼 보이게** 유도한다 —
  실제로는 호출 전 단계에서 이미 데이터가 깨져 있을 수 있으므로, 서비스별 특이사항을 조사하기 전에
  먼저 전송 직전 바이트를 확인하는 편이 빠르다.
- 과거 성공 사례가 극히 드물다면(예: 수개월간 1건) 이 경로 자체가 사실상 전부 실패해왔다는 뜻일 수
  있다 — "원래 이렇게 가끔만 되는 기능"이라고 넘기지 않는다.
- 부수 조건(최소 길이·크기 제한 등)이 같이 걸려 있으면 데이터 버그를 고쳐도 다른 이유로 계속
  실패할 수 있다 — 한 번에 하나만 고쳤다고 끝이 아니라 나머지 실패 조건도 별도로 확인한다.
