# icon-source-of-truth-before-replace

## 언제 쓰는가
"desktop 아이콘을 web 아이콘으로 통일해줘" 처럼 **두 에셋을 하나로 맞추라**는 요청을 받았는데,
문장만으로는 어느 쪽이 "원본(유지될 디자인)"이고 어느 쪽이 "교체 대상"인지 모호할 때. 특히 두 아이콘의
디자인이 시각적으로 완전히 다를 경우(색상·모티프 자체가 다름) 오인 시 되돌리기 작업이 두 배로
늘어난다.

## 절차 (단계별)
1. 두 에셋을 실제로 열어 시각적으로 얼마나 다른지 확인한다. 단순 리사이즈/포맷 차이가 아니라
   디자인 자체가 다르면(색상·모티프) 방향 실수의 리스크가 크다는 신호.
2. **빌드/재생성 파이프라인의 "원본" 방향과 사용자 의도의 "유지할 디자인" 방향을 분리해서 판단한다.**
   예: `install-desktop.sh`가 `icon.svg`를 원본으로 `icon.icns`를 만든다는 사실은 "어느 파일을
   수정해야 재생성이 되는가"를 알려줄 뿐, "어느 디자인을 최종적으로 유지해야 하는가"는 알려주지
   않는다. 이 둘을 같은 것으로 취급하면 방향을 반대로 잡기 쉽다.
3. 요청 문장을 다시 읽어 주어-목적어 방향을 정확히 파싱한다. "A를 B로 바꿔줘" = A 위치의 내용물이
   B의 디자인으로 대체된다는 뜻이지, "A와 B를 통일한다"는 중립적 의미가 아니다. 모호하면 실행 전에
   "OO 디자인을 XX 쪽에 적용하는 것 맞나요?"로 한 줄 확인하는 편이 두 배 작업보다 싸다.
4. 실행 전, 실제 재설치/배포(Dock/Finder 반영 등)까지 사용자가 승인했다면 그 부작용 범위를 기억해
   둔다 — 방향이 틀렸을 경우 되돌릴 때 재설치/재배포까지 다시 실행해야 한다.
5. 방향 오인이 드러나면 변명 없이 즉시 인정하고, git 상태 확인 → 원본 복원 → 올바른 방향으로 재실행
   순으로 롤백한다.

## 주의사항 / 함정
- "이 파일이 재생성 파이프라인의 입력이다"라는 사실이 "이 디자인이 최종 유지되어야 할 디자인이다"를
  함의하지 않는다 — 별개의 질문.
- 실행 전 확인 한 번이 실행 후 롤백보다 항상 싸다. 특히 실제 시스템 반영(Dock/Finder, 앱 재설치)이
  걸린 작업이면 더더욱.
