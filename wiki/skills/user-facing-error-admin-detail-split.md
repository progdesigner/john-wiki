# user-facing-error-admin-detail-split

## 언제 쓰는가
비동기 생성·결제·배치 작업처럼 **실패·재시도가 정상적으로 일어나는 플로우**에서, 같은 주문/작업
상세 화면을 고객과 운영자가 함께 볼 때. "오류가 사용자 친화적으로 보이게 해줘, admin 에서는
자세히 보여줘"처럼 두 화면의 요구가 명시적으로 갈리는 요청에 적용한다.

## 절차 (단계별)
1. 실패 상태를 **일시적(재시도 중)**과 **영구적(제작 중단)** 두 갈래로 먼저 구분한다. 오류 원문
   하나로 뭉뚱그리면 사용자에게 뭘 보여줘야 할지 판단할 수 없다.
2. **고객 화면**: 오류 원문·스택트레이스·내부 상태 코드를 노출하지 않는다.
   - 일시적 실패(자동 재시도 중): "잠시 지연되어 다시 시도하고 있어요" 류의 진행 중 안내.
   - 영구적 실패(재시도 소진·수동 개입 필요): 고객센터 연결 등 다음 행동을 안내.
3. **관리자 화면**: 진단에 필요한 정보를 전부 노출한다 — 주문/작업 상태, 실패 단계(어느 단계에서
   멈췄는지), 재시도 횟수, 오류 원문. 원본 데이터를 가리지 않는다.
4. 같은 백엔드 상태값을 두 화면이 각자의 뷰 로직에서 다르게 렌더링하도록 분리한다 — 상태 자체를
   고객용/관리자용으로 이중 저장하지 않는다(단일 소스, 표시만 분기).
5. 배포 전 테스트 데이터로 **양쪽 화면을 모두** 검증한다: 재시도 중·중단·정상 완료 각 상태에서
   고객 화면에 원문이 새지 않는지, 관리자 화면에 필요한 정보가 다 보이는지.

## 주의사항 / 함정
- "친화적으로"만 요청받아도 반대쪽(관리자)의 상세 노출 요구를 놓치면 운영 중 원인 파악이 막힌다 —
  두 화면을 항상 짝으로 검토한다.
- 고객 화면 안내 문구는 실패 원인이 바뀌어도 재작성이 필요 없게 **일시적/영구적** 두 범주로만
  분기하고, 세부 원인별 문구를 늘리지 않는다(문구가 늘수록 오류 원문이 새어나갈 표면이 늘어남).
