# 프로덕션 롤백이 안 먹힐 때 — 배포 소스가 git과 다를 가능성 확인

## 언제 쓰는가
프로덕션에서 크래시/장애가 나서 "직전 정상 커밋"으로 롤백했는데 **똑같은 오류가 재현**될 때. 또는
평소 다루던 모노레포의 `dev`를 배포했더니 프로덕션에서 **원래 있던 기능이 갑자기 사라졌을** 때.
둘 다 "지금 이 저장소의 git 히스토리가 프로덕션에서 실제로 돌던 코드의 완전한 기록"이라는 암묵적
전제가 깨졌을 때 나타나는 증상이다 — [[2026-09-25-엘레비노-예약취소-크레딧환불-배포장애]]에서
[[elevino-system]] 프로덕션이 실제로는 (1) origin에 없는 로컬 수동 빌드, (2) 형제 저장소
[[cwc-system]]의 `apps/elevino-*`, 두 소스로부터 부분적으로 배포되고 있었음이 드러난 사례.

## 절차 (단계별)
1. **롤백이 실패하면 "같은 오류가 이전 커밋에도 있었나"를 먼저 코드로 확인한다.** 오래된 버그가
   최근에야 트리거된 것이라면(예: 특정 provider/모듈이 새로 추가되며 기존 결함 조건을 처음 만족),
   롤백 대상 커밋 자체에 결함이 원래 있었을 수 있다 — 롤백이 무의미한 게 당연하다.
2. **현재 "정상"이라고 믿던 버전이 실제로 git 커밋에서 왔는지 버전 문자열·배포 스크립트로 검증한다.**
   `package.json` 버전이 서버에 표시되는 버전과 다르거나, 배포 스크립트가 `yarn version` 등으로
   **로컬에서 버전만 올리고 커밋하지 않는 방식**이면, 지금 돌던 "정상" 빌드가 origin의 어느 커밋과도
   대응하지 않는 수동 로컬 빌드일 수 있다.
3. **이 저장소 말고 같은 도메인/호스트로 배포하는 형제 저장소가 있는지 찾는다.** 회사 저장소가
   여러 개(`~/Works/<org>/*`)일 때, 이름이 다른 저장소 안에 `apps/<서비스명>-*` 같은 폴더로 같은
   프로덕션 타깃을 배포하는 코드가 숨어 있을 수 있다. grep으로 배포 대상 도메인/호스트명을 형제
   저장소들에서 검색해 본다.
4. **두 소스가 갈라져 있는 게 확인되면, 강제 덮어쓰기 대신 공통 조상 기준 3-way 머지로 합친다.**
   `git merge-base`로 두 브랜치/저장소가 갈라지기 전 공통 커밋을 찾고, 그 지점에서 동기화 브랜치를
   만들어 누락된 쪽의 변경을 그대로 가져온 뒤 원래 작업 브랜치에 머지한다. 충돌 지점(예: 부팅 로직
   1개 파일)은 두 구현을 비교해 더 안전한 쪽을 채택한다.
5. **배포 후 검증은 버전 문자열 변화 + 신규/기존 라우트 상태코드 폴링으로.** 신규 라우트가
   404→401(존재+인증요구)로, 신규 페이지가 404→200으로 바뀌는 시점을 배포 완료 신호로 쓴다.
6. **재발 방지**: 이후로는 프로덕션 배포를 release 브랜치(`release/api/prod` 등) 경유로만 강제하고,
   로컬 수동 배포·다른 저장소에서의 병행 배포를 금지하기로 합의해 둔다 — 그래야 다음 장애 때도
   롤백이 실제로 유효하다.

## 주의사항 / 함정
- "프로덕션이 최근까지 잘 돌고 있었다"는 사실이 "그 코드가 git에 있다"를 보장하지 않는다 — 특히
  배포 스크립트가 버전만 bump하고 커밋은 안 하는 구조라면 항상 의심할 것.
- 형제 저장소가 같은 서비스를 부분적으로 미러링하고 있으면, 한쪽만 보고 배포하는 순간 다른 쪽의
  기능이 **에러 없이 조용히 사라진다** — 배포 실패가 아니라 기능 누락이라 알아채기 더 어렵다.
- 감시 스크립트의 "CRASHED" 알림이 오탐일 수 있다: pm2가 `.env` 변경을 감지해 새 빌드보다 먼저
  재시작하면서 아직 회전되지 않은 로그의 과거 오류를 잡을 수 있다 — 재시작 순서와 로그 타임스탬프를
  같이 봐야 한다.
