# 구조화 추출 vs LLM 재작성 분리

## 언제 쓰는가
파이프라인이 "원본을 가진 쪽이 프로즈(자유 텍스트)를 만들고 → 다른 LLM 호출이 그 프로즈를 다시 읽어
문서/페이지를 통째로 재작성"하는 구조일 때, 다음 증상이 함께 나타나면 이 패턴을 의심한다:

- 입력이 길어지면(수만 자) 잘리거나 모델이 JSON 대신 프로즈·불완전 응답을 낸다.
- 파싱 실패가 조용히 삼켜져(예: `console.warn`+`false` 반환) 바깥 단계는 "성공"으로 표시된다.
- 원하는 세부 사실(날짜·상대·점수·승패 같은 정형 데이터)이 자유 텍스트 나열 속에만 우연히 존재해
  구조화된 조회·집계가 불가능하다.

## 절차 (단계별)
1. **원본을 가진 쪽에서 구조화 JSON을 직접 뽑는다.** 프로즈 요약을 만들지 말고, 이미 하고 있는 다른
   호출(예: 라벨링 비전 호출)에 구조화 필드 추출을 얹는다 — 호출 횟수를 늘리지 않는다.
2. **저장소는 LLM 없이 결정적으로 저장한다.** 새 엔티티/테이블을 만들어 구조화 JSON을 그대로 upsert.
   실패해도 최소한 원시 행은 남는다(vs 프로즈 재작성 실패 시 아무것도 안 남는 것과 대비).
3. **파생 문서(요약·서사)는 코드가 뼈대를 만들고, 서사 한 줄/한 문단만 짧은 JSON 모드 LLM 호출로
   채운다.** 프롬프트가 작아지므로 잘림·파싱 실패가 거의 사라지고, 모델이 구조화 절을 지워도 코드가
   되살릴 수 있다(코드 병합 후 LLM은 narrative 필드만 건드리게 스키마로 강제).
4. **소비 측(조회 UI·다른 서비스의 프롬프트)은 구조화 저장소를 직접 읽는다.** 프로즈를 다시 파싱하지
   않는다.
5. **실패를 보이게 한다.** 이 단계 실패를 삼키지 말고 상위 잡/작업 상태에 사유와 함께 노출 + 재시도
   진입점을 만든다. 입력이 애초에 불완전하면(예: 필수 카테고리 키 없음) 생성 단계에서 막아 잘못된 잡이
   큐에 들어가지 않게 한다.

## 주의사항 / 함정
- "위치를 옮기면 해결될까"(예: 별도 저장소로 이전)라는 유혹이 들 수 있는데, 근본 원인이 입력 형태·실패
  가시성·엔티티 부재라면 저장 위치를 바꿔도 그대로 남는다 — 역할 분리가 먼저다.
- 구조화 추출을 맡길 소스는 "그 사실을 실제로 볼 수 있는 유일한 지점"이어야 한다(영상·전사·키프레임을
  가진 클라이언트처럼). 이미 프로즈로 손실된 하류 지점에 다시 물어보면 같은 문제가 반복된다.
- 조용한 스킵(예: 필수 필드가 `undefined`라 첫 줄 가드에서 `return true`)은 4xx 에러보다 진단이
  어렵다 — 요청이 아예 안 나간 경우와 실패한 경우를 로그에서 구분할 수 있어야 한다.
- 실패해도 성공으로 보이는 코드(예외 없이 `false`만 반환하고 호출부는 무시)를 찾으면, 로그만 보지 말고
  호출부가 반환값을 실제로 확인하는지까지 추적한다.
