# 서버 워커 "닫아도 계속된다" 실제로 보장하기

## 언제 쓰는가
비동기 다단계 제작 파이프라인(이미지 여러 장 → 영상 여러 개 → 최종 합치기 같은 순차 단계)에서
"페이지를 닫아도 서버가 이어서 만든다"고 안내하고 있는데, 실제로는 오류·재시작 시 이미 만든
자산이 다시 생성되거나 재시도 횟수가 리셋되는 등 안내와 실제 동작이 어긋난다는 제보를 받았을 때.
워커 프로세스 자체는 이미 존재하는 경우가 많아 "워커가 있냐 없냐"가 아니라 **저장된 상태를
신뢰하고 있는지**를 봐야 한다.

## 절차 (단계별)
1. 각 단계 전환 지점에서 **기존 진행 정보를 덮어쓰는 코드**가 있는지 찾는다 — 특히 "다음 단계
   개요/계획을 새로 생성하기 직전"이 흔한 함정이다. 여기서 이미 완료된 앞 단계 산출물(배경·참조
   자산 등)의 완료 기록까지 같이 지워지면, 오류로 재시도할 때 이미 만든 걸 다시 만든다.
2. 재시도 카운터가 **새 요청을 시작할 때마다 초기화**되는지 확인한다. 초기화되면 실질적으로
   무한 재시도가 가능해지고, "재시도 3회 상한" 같은 안전장치가 있으나 마나 해진다.
3. 수정 방향: **저장된 "완료된 단계" 상태를 기준으로 다음에 무엇을 할지 결정**하도록 바꾼다 —
   앞 컷의 영상이 완료된 것이 DB에 기록된 뒤에만 다음 컷을 시작. 서버가 재시작되면 저장된 외부
   작업 ID로 결과 조회부터 재개(새 요청을 다시 보내지 않음). "오래 걸린다"는 이유만으로 이미 접수된
   외부 작업을 새로 요청하지 않는다 — 접수 여부가 불확실하면 중복 과금 위험이 있으므로 자동 진행
   대신 사람 확인으로 넘긴다.
4. **관리자가 트리거하는 재생성/재작업도 같은 워커 경로로 통합**한다. 일반 사용자 제작과 별도
   경로(즉시 처리)로 남아 있으면, 서버 재시작과 겹칠 때 관리자 작업만 끊기고 복구되지 않는
   비대칭이 생긴다 — 먼저 서버에 작업으로 저장한 뒤 워커가 실행하도록 통일한다.
5. 실패 후 재시도까지 소진된 주문에는 **추가 차감 없이 이어서 제작**할 수 있는 관리자 복구 동작을
   별도로 마련해둔다(사용자 재결제를 요구하지 않는다).
6. 검증은 "서버 재시작 후에도 저장된 단계에서 이어지는가"를 실제로 재현해 확인한다 — 코드 리뷰만
   으론 부족하고, 재시작 시나리오를 직접 트리거해 자산이 중복 생성되지 않는지 봐야 한다.

## 주의사항 / 함정
- "워커가 있으니 끊김없이 될 것"이라고 가정하지 않는다 — 워커 존재와 상태 신뢰는 별개 문제다.
- 오류 판단(재시도/대기/관리자 확인)을 별도 저비용 분류기(예: [[jev-typed-classification]])에
  맡기는 경우, **그 분류기 자체가 실패했을 때의 기본 동작**을 반드시 정의해야 한다(기본 복구
  규칙으로 폴백).
- 외부 생성 API에 작업을 넣었는지 불확실한 상태에서 "그냥 다시 요청"하면 중복 과금·중복 자산
  생성으로 이어진다 — 불확실하면 관리자 확인으로 넘기는 쪽이 안전하다.
