# pwa-safe-area-inset-padding

## 언제 쓰는가
iOS/Android에서 웹앱을 "홈 화면에 추가"(PWA)해서 열면 브라우저 크롬(주소창 등)이 사라지고 콘텐츠가
화면 전체를 차지한다. 이때 상단 헤더가 상태바/노치 영역과 겹치거나, 반대로 원래 없어야 할 여백이
생기는 문제가 생긴다. `env(safe-area-inset-top/bottom/left/right)` CSS 환경 변수를 안 쓰고 있는 게
전형적 원인이다.

## 절차 (단계별)
1. 증상이 나는 요소(보통 `header`/`footer`)의 CSS에 `env(safe-area-inset-*)` 사용 여부를 grep으로
   확인한다. 전혀 없으면 그게 원인이다.
2. 여백을 **추가**해야 하는 쪽(주로 상단 헤더, 노치를 피해야 함)은 기존 고정 패딩에 안전영역을 더한다:
   ```css
   header {
     padding-top: calc(10px + env(safe-area-inset-top));
   }
   ```
   `calc()`로 감싸야 일반 브라우저(값이 0)에서도 기존 여백(`10px`)이 그대로 유지된다.
3. 여백을 **제거**해야 하는 쪽(요청받은 "그냥 없게 해줘" 같은 경우)은 `env()`를 쓸 필요 없이 해당
   패딩 값을 단순히 `0`으로 바꾸면 된다 — safe-area와 무관한 요구사항이면 굳이 얽지 않는다.
4. `manifest.json`의 `display: "standalone"`(또는 `fullscreen`)이 설정돼 있어야 `env()` 값이
   실제로 0이 아닌 값을 받는다 — 일반 브라우저 탭에서는 항상 0이라 리로드 없이도 안전하게 배포 가능.
5. 빌드 후 실제 iOS 기기(또는 시뮬레이터)에서 홈 화면 추가 상태로 재확인 — 개발자 도구는 safe-area
   값을 정확히 재현하지 못하는 경우가 많다.

## 주의사항 / 함정
- `env()`는 **`calc()` 안에서만** 다른 상수와 더할 수 있다. `padding-top: 10px + env(...)` 처럼 직접
  더하면 무효.
- 상단은 노치 침범 방지를 위해 보통 여백을 **더해야** 하고, 하단은 홈 인디케이터 영역 때문에 반대로
  여백이 **의도치 않게 생기는** 경우가 많다 — 두 방향의 요구사항이 반대일 수 있으니 사용자 요청을
  "안전영역 대응"으로 일반화하지 말고 원하는 방향(추가 vs 제거)을 그대로 따른다.
- 배포에는 `apps/web/dist` 재빌드 + 서버 재시작이 필요한 구조가 흔하다 — 정적 자산만 바뀌었다고
  캐시된 dist를 안 갱신하면 반영 안 됨.
