# 공유 파일 헝크 단위 선택 커밋

## 언제 쓰는가
"이번 작업만 커밋해줘" 요청을 받았는데, 그 작업이 건드린 파일 중 일부가 **다른(이전) 미커밋 작업의
변경분과 같은 파일을 공유**하고 있을 때. 파일 전체를 커밋하면 관련 없는 미완성 변경까지 같이 올라가고,
파일 전체를 건너뛰면 이번 작업의 변경분이 빠진다 — 둘 다 부정확하다.

## 절차 (단계별)
1. `git diff <file>`로 그 파일에 몇 개의 논리적 변경(헝크)이 섞여 있는지 확인한다.
2. 이번 작업이 만든 헝크와 기존 미커밋 헝크를 내용으로 구분한다(예: 정규식에 값 하나 추가 = 이번 작업,
   나머지 큰 블록 = 이전 미커받 작업).
3. `git add -p <file>` (또는 동일 효과의 패치 적용)로 이번 작업 헝크만 스테이징한다.
4. 같은 파일에 **이번 작업 이전부터 있던 미커밋 변경이 이번 작업 변경과 같은 라인 블록에 있어
   분리 불가능한 경우**(예: 모델 목록 배열에 여러 모델이 순서대로 추가돼 헝크가 안 갈라짐)는 억지로
   쪼개지 말고 전체를 함께 커밋하되, **커밋 메시지나 보고에 "이 파일은 이전 미커밋 변경분이 같이
   포함됨"을 명시**한다. 그 변경분이 이미 배포된 빌드에 포함돼 있다면(운영과 커밋 상태가 일치하면)
   문제 없음 — 배포 여부로 포함 타당성을 판단한다.
5. 커밋 후 `git status`로 의도한 파일만 커밋됐는지, 나머지 미커밋 변경은 그대로 남아있는지 확인한다.

## 주의사항 / 함정
- 헝크가 분리 가능한데도 파일째 커밋하면, 다음에 그 미커밋 변경을 작업하던 세션/사람이 "내가 언제
  이걸 커밋했지?"라며 혼란을 겪는다 — 분리 가능하면 반드시 분리한다.
- 헝크가 분리 불가능할 때 억지로 자르려다 문법 오류를 만들지 않는다 — 이럴 땐 4번처럼 배포 상태로
  타당성을 확인하고 그대로 둔다.
- 커밋 대상 결정은 "이번 작업이 손댄 파일"이 아니라 "이번 작업이 만든 변경"이어야 한다 — 파일 단위가
  아니라 diff 단위로 사고한다.

## 변형: 경로(디렉터리) 지정 커밋이 형제 세션의 미커밋 "파일 전체"를 함께 쓸어감
같은 모노레포(`lampas-system`)를 여러 세션이 동시에 작업할 때, `git add apps/lampas-api
apps/lampas-web-edit`처럼 **경로 단위**로 커밋 범위를 좁혀도 안전하지 않다 — 그 경로 안에 다른
세션이 이미 스테이징해 둔 **완전히 다른 파일**이 함께 들어간다(헝크 분리가 필요 없는, 더 거친
단위의 오염). [[2026-09-19-lampas-edit-자막-템플릿-대량기능개발]] 세션에서 이 패턴으로 최소 두 번
사고가 났다: ① 첫 배포 커밋에 scenario·www·trends 등 무관한 여러 앱의 미커밋 파일이 함께 커밋됨,
② 템플릿 계정종속화 커밋에 동시 진행 중이던 다른 세션의 API/에디터 미완성 변경이 함께 커밋·배포됨.

- **진단**: 커밋 직전 `git status`로 스테이징될 파일 전체 목록을 사람이 읽을 만큼 나열해 확인한다 —
  "이번 작업이 만든 파일"인지 하나씩 대조하지 않으면 경로 지정만으로는 걸러지지 않는다.
- **수정**: 여러 세션이 동시에 같은 저장소를 쓰는 게 확인되면(또는 의심되면), `git add <dir>/` 대신
  **이번 작업이 실제로 수정한 파일명을 하나씩 나열**해 스테이징한다. 위 세션도 이후(0.1.40 배포부터)
  "이번 작업 파일 6개만 골라 커밋"으로 방식을 바꿔 재발을 피했다.
- 이미 원격에 푸시된 뒤 발견하면(공유 브랜치), 강제로 히스토리를 고치지 않고 **어떤 다른 세션의
  작업이 어느 커밋에 섞였는지 사용자에게 명시적으로 보고**한다 — 되돌리는 것보다 투명성이 우선.
- rebase 중 다른 세션의 대량 미커밋 파일(예: 185개)이 자동 stash→복원되는 경우도 같은 근본 원인
  (공유 워크트리)의 다른 증상이다 — stash 복원 후 스테이징이 남아있지 않은지 반드시 확인한다.
