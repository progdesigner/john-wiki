# 원격이 구조를 리팩터한 코드 위에 로컬 기능 rebase 이식

## 언제 쓰는가
로컬에 미커밋 기능 변경이 쌓여 있는데, 그사이 원격에 여러 커밋이 **같은 파일들을 구조적으로 개편**
(예: 다른 페이지네이션 방식으로 교체, 컴포넌트 분리/통합)해둔 상태. 단순 `git pull`이나 3-way 병합으로는
같은 로직이 양쪽에서 다른 모양으로 존재해 자동 병합이 불가능하거나 결과가 망가진다.

## 절차 (단계별)
1. 로컬 변경과 원격 커밋이 **같은 파일을 건드리는지** 먼저 확인한다 (`git diff`, `git log --stat` 등으로
   겹치는 파일 범위 파악).
2. 로컬 diff를 읽어 변경의 **의도 단위**를 파악한다 — 기능 A, 리팩터 B처럼 성격이 다른 변경을 하나의
   커다란 diff로 뭉치지 말고 나눈다.
3. 의도 단위별로 **별도 커밋**을 만든다(스쿼시하지 않는다). 커밋 메시지에 `feat:`/`refactor:` 등으로
   성격을 명시해 이후 rebase 충돌 해소 때 "이 조각이 뭘 하려던 건지"를 다시 찾기 쉽게 한다.
4. 원격 위로 `rebase`한다. 충돌이 나면 원칙: **원격의 새 구조를 기준으로 삼고, 로컬 기능 로직만 그 위에
   옮겨 심는다** — 로컬의 옛 구조를 되살려 병렬로 두지 않는다.
5. 로컬 커밋의 가정 중 원격 리팩터와 상충하는 게 있으면(예: DB 종류·정렬 방식 가정) 저장소의 실제 상태를
   확인해 원격 쪽 가정을 채택한다.
6. 원격이 로컬 변경과 겹치는 새 기능을 이미 만들어뒀다면(예: 새 UI 옵션), 로컬의 지엽적 수정(문구 등)이
   그 새 기능에서 이미 의미가 없어졌는지 판단해 버릴 것은 버린다.
7. 충돌 마커(`<<<<<<<`)가 안 남았는지 전체 검색으로 확인한다.
8. **rebase 완료 전에 반드시 빌드/타입체크를 돌린다** — 코드가 컴파일된다고 rebase가 맞았다는 뜻은
   아니지만, 최소한의 방어선이다(예: `tsc --noEmit`, 프로덕션 빌드). 여러 커밋을 rebase했다면 각 커밋
   또는 최소 최종 결과에서 검증한다.
9. 검증 통과 후 push. 저장소에 git user 설정이 없으면(신규 clone·CI 등) 기존 커밋 작성자와 동일하게
   로컬(`--global` 아님) 설정을 잡아 커밋 작성자 일관성을 유지한다.

## 주의사항 / 함정
- 병합(merge)이 아니라 **rebase**를 쓰는 이유: 원격의 구조 변경을 "기준선"으로 유지하면서 로컬 기능만
  그 위에 얹기 위함. merge는 두 구조가 공존하는 diff를 만들어 리팩터를 무효화하기 쉽다.
- 리팩터 전후로 존재하지 않던 가정(예: 특정 DB의 대소문자 처리 방식)을 로컬 커밋이 깔고 있었다면, rebase
  충돌 해소 중 저장소의 실제 스택을 재확인하지 않으면 조용히 틀린 코드가 살아남는다.
- rebase와 무관한 **기존 이슈**(예: 워크스페이스 의존성 누락)를 발견해도 이번 작업 범위가 아니면 고치지
  말고 사실만 기록해 알린다 — origin/main에도 있던 문제인지 확인해서 "이 작업이 만든 문제가 아님"을
  명시한다.
- **7번 단계(충돌 마커 전체 검색)는 실제로 누락될 수 있다** — [[2026-07-16-봇메시지-클릭읽어주기-커밋푸시]]
  세션에서 이전 병합 커밋에 `<<<<<<< HEAD` 등 마커가 그대로 남아 있다가 뒤늦게 별도 커밋으로
  정리된 사례가 확인됨(어느 rebase/병합이 남겼는지는 추적 불가). 8번(빌드/타입체크)만으로는
  마커가 문자열·주석 안에 숨어 컴파일을 통과할 수 있으므로, grep으로 `<<<<<<<`/`=======`/`>>>>>>>`
  패턴을 **명시적으로** 검색하는 별도 단계로 취급할 것 — 빌드 통과와 별개다.
