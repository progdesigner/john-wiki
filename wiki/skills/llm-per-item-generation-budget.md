# 배치 LLM 생성의 "뒤로 갈수록 급해지는" 문제 — 항목별 독립 호출로 해결

## 언제 쓰는가
"컷 수를 늘렸더니 뒤쪽 컷의 대사가 더 급해지고 짧아진다" 같은 제보를 받았을 때. 표면적으로는
연출·서사 문제로 보이지만, 실제로는 **한 번의 LLM 호출로 여러 항목(씬 12개, 목록 20개 등)을
한꺼번에 생성**하고 있고, 그 호출의 출력 토큰 상한이 `min(고정캡, base + 항목수*단가)`처럼
항목 수에 비례해서만 늘어나 실제로는 고정 캡에 곧 막히는 구조일 때 나타나는 증상이다.

## 원인 진단
1. 출력 토큰 예산 공식을 찾는다 (`scenarioMaxTokens(sceneCount) = min(6000, 1500+sceneCount*450)`
   같은 형태). 요청 항목 수에서 이 공식이 이미 캡에 걸려 있는지(`1500+10*450=6000`처럼 정확히
   맞아떨어지는 지점) 확인 — 캡에 걸리는 순간부터는 항목을 늘려도 실제 가용 토큰이 늘지 않고,
   그 안에서 항목 수만 늘어나므로 **항목당 예산이 줄어든다**.
2. 항목 수 상한이 여러 곳에 하드코딩돼 흩어져 있는지 확인한다(`Math.min(10, ...)`이 서비스
   메서드 3곳에 중복되는 식) — 하나만 고치면 나머지에서 다시 잘리므로 반드시 grep으로 전부 찾는다.
3. "캡과 토큰 상한 숫자만 올리는" 땜빵은 **재발한다** — 항목 수를 또 늘리면 같은 계산을 다시
   해줘야 한다. 근본 원인(하나의 호출에 예산을 나눠 쓰는 구조)은 그대로 남는다.

## 절차 (구조적 해결)
1. 생성을 두 단계로 나눈다: **개요(outline) 호출** 1번 — 제목·공통 스타일 가이드·각 항목의
   한두 줄 요약만 가볍게 받는다.
2. **항목 상세 호출**을 항목마다 독립적으로 실행한다 — 각 호출은 항목 수와 무관하게 항상 같은
   고정 토큰 예산(예: 900토큰)을 받으므로, 몇 번째 항목이든 첫 항목과 동일한 여유로 상세(대사·
   프롬프트 등)를 생성한다.
3. 항목 수 상한을 하드코딩 여러 곳 대신 **공유 상수 하나**로 통일하고, DTO 검증(`@Max`) 값도
   같이 맞춘다.
4. 호출 횟수가 늘어나는 트레이드오프는 감수한다 — 이미 폴링/체크포인트 기반 워커 구조([[resumable-worker-checkpoint-resume]])라면 단계가 하나 늘어나는 것은 자연스럽게 붙는다.
5. 검증: 항목 수를 원래보다 훨씬 더 늘려봐도(예: 12→15) 마지막 항목이 첫 항목과 동일한 품질/길이로
   나오는지 확인한다 — 구조적 해결이 됐다면 항목 수를 늘려도 재작업이 필요 없어야 한다.

## 주의사항 / 함정
- 개요 단계에서 LLM이 만든 공통 값(스타일 가이드 등)을 신뢰하지 못하는 경우(고정 비주얼
  컨셉이 있는 제품 등)라면, 개요 응답의 해당 필드를 **고정 상수로 덮어쓰는 것**도 병행 고려한다
  — LLM은 항목 분할·상세 생성에만 쓰고, 절대 흔들리면 안 되는 값은 코드가 소유한다.
- 항목별 실제 소요 시간/길이(예: 대사 낭독 시간)가 LLM의 사전 추정치보다 길어질 수 있다 —
  가능하면 실측(TTS 길이, 렌더 결과 등)으로 사후 보정하는 로직을 같이 넣는다. 실측 없이 LLM
  추정치만 믿으면, 대사가 유난히 많이 몰린 항목에서 다시 같은 증상(급해짐)이 재발한다.
