# 재시작 후 "이전 실행의 늦은 알림"이 새 상태를 덮어쓰는 문제

## 언제 쓰는가
사용자가 작업을 취소했다가 **같은 대상으로 다시 시작**했는데, 화면에 방금 취소했던 이전 실행의
상태("취소됨"/"실패" 등)가 계속 남아 있거나, 새로 시작한 작업이 진행 중인데도 갑자기 예전 상태로
되돌아가 보일 때. `[[false-abort-premature-status-check]]`(작업 ID 발급 전 오판정 + 중복 폴링)과
증상은 비슷하지만 원인이 다르다 — 이쪽은 **재시작 자체는 정상 동작 중인데, 과거 실행이 보낸 알림이
뒤늦게 도착해 최신 상태를 덮어쓰는** 순서(ordering) 문제다.

## 절차 (단계별)
1. 재현 조건을 좁힌다 — "취소 → 재시작"처럼 **같은 작업 슬롯을 빠르게 재사용**하는 흐름에서만
   나타나는지 확인한다.
2. 상태를 저장·갱신하는 코드가 **어떤 키로 상태를 식별**하는지 확인한다. 대상(work/노드) ID만으로
   식별하면, 오래된 실행이 보낸 늦은 알림과 새 실행의 알림이 같은 슬롯을 놓고 경합한다.
3. 재시작 경로에서 **연결 정보(어느 상위 작업/Work에 속하는지)가 누락되는 코드 경로**가 있는지도
   함께 확인한다 — 이것이 별개로 겹쳐 있으면 "확인 필요" 류의 표시가 두 가지 원인(연결 누락 + 늦은
   알림)으로 동시에 발생해 하나만 고치면 증상이 절반만 사라진다.
4. **수정 방향**: 상태 갱신에 **실행(run) ID**를 함께 기록하고, 들어오는 알림의 run ID가 "현재
   활성 run"과 일치할 때만 반영한다. 일치하지 않는(오래된) run의 알림은 무시한다.
5. 재시작 시 상위 연결(Work/노드) 정보를 새 실행에도 명시적으로 이어붙인다.
6. **검증**: 취소 직후 재시작 → 늦게 도착하는 이전 실행의 취소 알림이 새 실행의 "진행 중" 표시를
   덮어쓰지 않는지 자동 테스트로 확인. 실제 운영에서도 새 실행 상태가 유지되는지 관찰로 재확인.

## 주의사항 / 함정
- 원인이 "연결 정보 누락"과 "늦은 알림의 덮어쓰기" 두 가지로 겹칠 수 있다 — 한 가지만 고치고
  종료하지 말 것(→ [[false-abort-premature-status-check]]의 "원인이 둘일 수 있다" 교훈과 같은 계열).
- 같은 병목(예: 대용량 전송)이 여러 단계(다운로드 전송, 전사 엔진 로딩)에 걸쳐 있으면, 이 상태
  꼬임도 각 단계마다 독립적으로 재현될 수 있으니 단계별로 확인한다.
