# 자동 오류수집→AI 수정→검증→재배포 파이프라인 설계 원칙

앱 오류를 자동으로 모아 AI 코딩 에이전트(Codex 등)에게 수정을 맡기고, 검증에 성공하면 자동
재배포까지 이어지는 "자가치유(self-healing)" 시스템을 설계할 때 반복 적용 가능한 원칙. [[lampas-agent]]의
**Fixs** 탭(2026-09-21 최초 설계, [[2026-09-21-lampas-agent-fixs-신설]] 세션)에서 실제로 구현된
버전을 근거로 정리.

## 파이프라인 형태
```
앱(프론트·API·워커) → 오류·스택·앱이름·배포버전 수집
    ↓ 민감정보 제거·중복 통합(fingerprint)
수정 작업 큐
    ↓
AI 코딩 워커 (별도 git worktree에서 원인 분석·수정)
    ↓
테스트·빌드 검증
    ↓ (성공 시에만)
기존 배포 스크립트로 재배포
    ↓
수정 내역·검증 결과 영구 기록
```

## 지켜야 할 원칙
1. **자동 수정과 자동 배포는 분리해서 켤 수 있어야 한다.** 안정성이 검증된 오류 유형부터 배포까지
   연결하고, 나머지는 "수정안까지만 자동, 반영은 사람 승인"으로 남긴다.
2. **AI 워커는 원본과 격리된 작업공간(worktree/브랜치)에서 작업하고, 원본과 충돌하면 그 작업을
   중단한다.** 진행 중인 미커밋 변경이 많은 저장소일수록 필수.
3. **테스트·빌드 검증에 실패한 수정은 "완료"로 표시하지 않는다.** 재현 실패·검증 실패 수정안은
   원본 반영·배포를 막아야 한다(사람이 보기엔 "왜 안 고쳐졌지"로 보일 수 있으니 상태를 명확히 구분해
   보여줘야 함).
4. **모든 오류가 코드 수정으로 해결되지 않는다.** 외부 API 장애·인증/설정 문제는 코드 버그와 별도로
   분류해 자동 수정 대상에서 뺀다. 잘못 분류하면 무한 재시도만 반복한다.
5. **오류 로그 자체를 신뢰할 수 없는 입력으로 취급한다.** 사용자·외부에서 주입 가능한 문자열이
   스택트레이스·메시지에 섞여 들어올 수 있으므로, AI 워커에 그대로 프롬프트로 넣기 전에 살균이
   필요하다(프롬프트 인젝션 벡터, → [[unverified-attestation-injection]] 참고).
6. **같은 오류는 하나로 묶고 재시도 횟수·실행 비용에 상한을 둔다.** 그렇지 않으면 반복되는 동일
   오류가 매번 새 수정 작업을 만들어 큐가 무한 성장한다. 실제 구현은 경로 안 uuid/hash/토큰을
   `:id`로 치환하는 fingerprint 방식 사용 → [[error-fingerprint-path-grouping]].
7. **하루 실행 한도(rate limit)를 사람이 조절 가능하게 노출한다.** 자동 수정·배포 on/off 토글과
   함께 대시보드에 둔다.
8. **SoT(source of truth) 규칙이 있는 코드베이스라면 AI 워커도 그 규칙을 따라야 한다.** 예:
   Node Studio 코드는 `dalar-web-app`이 SoT이고 `lampas-web-studio`는 `pnpm sync:studio`로 동기화되는
   구조라, Studio 관련 오류 수정은 원본(SoT)을 고치고 동기화 스크립트를 돌리도록 규정해야 한다 —
   동기화 대상 쪽만 고치면 다음 sync에서 덮어써진다.

## 관찰된 실제 값 (Fixs, 2026-09-21 최초 배포 기준)
- 기본값: 자동 수정 **활성**, 자동 배포 **활성**, 하루 최대 **5회**.
- 첫 배포 시 테스트 387개 통과. 기존 앱들의 오류 수집은 "각 앱의 다음 배포부터" 적용(소급 적용 아님).
- 이후 실사용 중 드러난 후속 요구사항(2026-09-25): 경로 fingerprint 병합, typed 질문만으로 저비용
  분류하는 "Jev" 패턴(→ [[jev-typed-classification]]), 대기/완료/실패 작업 삭제 기능.
