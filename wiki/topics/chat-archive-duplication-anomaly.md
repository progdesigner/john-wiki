# chat-archive-duplication-anomaly — 채팅 아카이브 중복·재사용 이상 정황

[[lampas-harness]]의 채팅 로그(`logs/chats/`, 보관 시 `logs/chats/archive/`)에서 **같은 파일명이
서로 다른 시점의 서로 다른 대화를 가리키거나, 같은 대화 내용이 서로 다른 아카이브 파일·시각으로
중복 기록되는** 현상이 최소 4개 세션에 걸쳐 독립적으로 관찰됐다. 개별 사고는 각 세션 페이지에
"⚠️ 이상 정황"으로 남아 있었으나 전용 페이지가 없어 패턴 자체의 인지도가 낮았다 — 이 페이지로 묶는다
(2026-07-20 lint에서 신설). **2026-09-26**: 5번째 사례가 `logs/terminals/archive/`(터미널 세션)
경로에서 처음 관찰돼, "quick 채팅에서만 발생" 가정이 깨졌다 — 아래 참고. **2026-09-26 추가**: 같은
4번 사례가 **동일한 저녁 16분 간격으로 2회 재현**됨을 확인 — 일회성이 아니라 재현 가능한 패턴.

## 관찰된 하위 패턴 (서로 구분되는 3가지)

### 1. 파일명(UUID) 재사용 — 같은 이름, 다른 시점의 다른 내용
`quick-5bc3f296-...md`가 [[2026-07-14-은행환불-거래처매칭]](08:52~09:00 UTC, 은행 거래·인보이스
해석)의 소스로 먼저 ingest됐는데, 같은 파일명 경로의 **현재 실제 내용**은 전혀 다른 대화
([[2026-07-14-clara-바바라-위스키분쟁-번역]], 09:03~09:13 UTC, 번역·위스키 분쟁 메일)였다. 두 세션
모두 그대로 유지하고 모순으로만 기록.

### 2. 같은 사건이 다른 아카이브 파일·시각으로 이중 기록
[[2026-07-15-gpt-realtime-음성입력-길게누르기]]의 "6번 항목"(22:28~22:30, 커밋 `938d4e4`로 완료)과
[[2026-07-15-음성입력-3-4초-잘림-수정]](15:29:49~15:33:37, 커밋 언급 없음)는 원인·해결책 서술이
문장 단위로 사실상 동일한데 시각·소스 UUID·커밋 상태가 다르다 — 같은 편집 사건이 서로 다른 아카이브
파일에 다른 시각으로 기록됐을 가능성. 어느 쪽이 "원본"인지 미확정.

같은 계열: [[2026-07-16-srkk-인보이스-james확인-0243]](02:43 UTC)의 사용자 메시지가
[[2026-07-16-srkk-인보이스-james확인]](02:15 UTC)과 **글자 단위로 100% 동일**한 이메일 스레드
번역 요청 — 28분 간격으로 같은 내용이 별도 아카이브 파일로 두 번 ingest 큐에 들어온 사례. 여기선
어시스턴트 응답까지도 형식만 다르고 실질은 같아, 같은 요청이 재실행된 것인지 로그가 이중 기록된
것인지 구분이 어렵다.

### 3. 한 트랜스크립트 안에서 동일 메시지 반복
[[2026-07-16-tts-stream-elevenlabs-구현착수]] 원문에 동일한 사용자 요청 텍스트가 02:42:10~02:47:55
사이 총 6회 그대로 등장(뒤 5회는 40초 안에 몰림). [[idempotent-message-retry]]의 msgId 멱등성이
**실행** 중복은 막았으나(어시스턴트 답변은 1회), **원문 트랜스크립트 자체**엔 중복 항목이 그대로
쌓였다 — 클라이언트 쪽 재전송/재렌더링이 로그 레벨까지 새는 것으로 추정(미확인).

### 4. 터미널 세션에서 한 메시지 필드 안에 구분자 없이 이어붙음 (신규, quick 채팅 외 첫 사례)
[[2026-09-14-중지버튼-프로브]](`logs/terminals/archive/cfd9185b-...md`)에서 사용자의 두 번째 턴이
첫 번째 턴과 완전히 동일한 문장을 **공백·구분자 없이 그대로 이어붙인** 한 덩어리 텍스트로 기록됨
("...답해.Bash 도구로...답해."). 3번 패턴과 같은 계열이지만 (a) 별도 메시지 항목이 아니라 한 필드
안에서 이어붙었고, (b) 경로가 `logs/chats/`가 아니라 **`logs/terminals/archive/`**라는 점이 다르다 —
아래 "quick 채팅에서만" 가정을 깬 첫 반례. 세션 자체가 "중지 버튼 프로브"였다는 점에서, 중지 후
재전송 시 클라이언트가 입력창을 비우지 않고 기존 텍스트에 덧붙이는 결함일 가능성이 있으나 미검증.

**재현성 확인 (2026-09-26 추가, [[2026-09-14-중지버튼-프로브-1838]])**: 같은 날 저녁
18:38:24(이번 사례)과 18:54:58(위 원 사례) — **16분 간격으로 같은 이어붙임 현상이 두 번 다 나타남**.
사용자가 중지 버튼을 연속 재테스트했고 그때마다 같은 클라이언트 재전송 결함이 재현됐다는 뜻으로,
"우연한 1회성 이상 정황"이 아니라 **일관되게 재현 가능한 버그**일 가능성이 크게 높아졌다.

**대조군 확인 (2026-09-26 추가, [[2026-09-14-모델-busy-프로브]])**: 같은 날 저녁 이 둘보다
35~51분 앞선 18:03:35, 같은 작업 폴더·같은 `Tool: claude` 경로에서 "Bash로 `sleep 15` 실행 후
짧게 답하라"는 같은 계열의 프로브(제목 "모델 busy 프로브")가 실행됐는데, 여기서는 이어붙임 현상이
**나타나지 않았다**(사용자 턴 1개, 어시스턴트 응답 1개로 정상). 이 세션은 제목상 중지 버튼이 아니라
모델의 tool-busy 상태 확인이 목적으로 보여 중지 버튼을 누르지 않았을 가능성이 크다 — 트리거가
"터미널 세션에서 sleep 명령을 쓰는 것" 자체가 아니라 **중지 버튼 인터럽트·재전송 행위**임을
뒷받침하는 대조 증거.

## 공통 관찰

- 5개 사례 모두 **원인이 확정되지 않았다** (단, 4번 사례는 2026-09-26 기준 동일 세션 내 재현 확인됨) — 클라이언트 재전송 버그, 아카이브 이동/복사 로직의
  경쟁 상태(race condition), quick 채팅 세션 식별 방식의 결함 등 여러 가설이 가능하나 코드 조사는
  아직 이뤄지지 않음.
- 1~3번 사례는 [[work-folder-sandboxing]]으로 격리된 **quick 채팅**(`chats/`, 보관 후
  `chats/archive/`) 경로에서만 관찰됐으나, **4번 사례는 터미널 세션(`logs/terminals/archive/`)
  경로에서도 같은 계열 현상이 나타남을 처음 확인** — "quick 채팅에서만 발생" 가정은 더 이상 유효하지
  않다.
- ingest 시 원칙은 일관됐다: **모순 처리 원칙에 따라 기존 세션 내용은 수정하지 않고 그대로 유지**하며
  새 소스는 별도 세션 페이지로 보관해 이상 정황만 명시 — 어느 쪽이 사실인지 임의로 판정하지 않는다.

## 미해결 — 다음에 조사할 것

- `logs/chats/` 파일명 생성 로직(UUID 발급 지점)과 `archive/` 이동 로직을 코드로 확인해 재사용/
  경쟁 상태 가능성을 검증할 것.
- 클라이언트(웹/quick.html/터미널 UI) 쪽 메시지 전송·중지 후 재전송 로직이 입력창을 비우지 않고
  텍스트를 덧붙이는지 확인할 것 — 4번 사례로 새로 제기된 가설.
- 발생 시각이 몰려 있는지(예: 서버 재시작 직후, 네트워크 불안정 구간) 패턴을 찾을 것 — 대부분
  사례는 시간대가 제각각이나, 4번 사례는 같은 날 저녁 16분 간격으로 2회 재현돼 **연속 재테스트
  시 매번 재현되는 유형**일 가능성을 시사 — 서버 재시작/네트워크보다 "중지 버튼 클릭 자체"가
  트리거일 가능성이 높아짐. 같은 저녁 그보다 앞서 실행된 "모델 busy 프로브"에서는 재현되지
  않아 이 가설을 뒷받침한다(위 "대조군 확인" 참고) — 다음 조사 시 실제로 중지 버튼을 누른
  케이스와 누르지 않은 케이스를 코드 레벨에서 구분해 검증할 것.
